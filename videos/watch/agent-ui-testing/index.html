文字稿

0:00 本地保存对照实验

作者用同一个小编辑器跑了两个模拟版本。

两个都返回二百，页面也都显示保存成功。

唯一差别是，有一个服务实际上没有写入。

刷新之后，正常版能找回卡片，故障版找不到。

如果用例只看状态码或成功提示，两边都会通过，测试就没守住用户依赖的行为。

0:28 核对写入请求并回读

测试先等保存按钮引发的请求。

只匹配地址可能把同一路径的读取误当成写入，要同时核对方法和本次动作。

接着再看页面反馈，然后刷新并找对应记录。

实验用可控数据，真实站点则尽量使用本次返回的标识，避免同名的旧记录假装本次写入成功。

0:55 缓存、异步与终态

原文的演示不会用浏览器缓存恢复卡片。

实际应用可能先从本地状态显示刚才的内容，因此刷新成功还需确认读取来源。

如果保存是异步的，接受请求只说明已经排队，并不等于写完。

先等任务明确到达终态，再查本次产物。

报告中保留实际失败点和最后能确认的状态。

1:25 何时让视觉模型做定位

表单、按钮和导航可以优先交给固定脚本。

对画布内的拖放，没有好用的页面节点时，可以让视觉模型完成那一步。

但模型看见卡片似乎去了右边，并不证明服务端保存了对应列和位置。

把难定位的动作与最终断言分开，失败时才能判断到底是操作没完成，还是产品没有保存。

1:54 用反例校验测试本身

最后再次跑故意跳过写入的测试版本。

它依旧会给成功提示，回读却必须失败。

若这次也通过，检查断言是否只剩下点按钮和看提示。

用证据分层以后，报告最好写清是请求没发出、任务未结束，还是完成后找不到记录。

每种失败都应该能指向一个不同的排查入口。
