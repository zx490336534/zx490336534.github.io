两个 MCP Server 暴露了同名工具，网关怎么处理？

本文速读

结论：当两个 MCP 服务暴露同名工具，网关应能从唯一公开名找到目标后端；不论列表是否过滤，调用时都要再判断权限。

适用范围：讨论多服务聚合，不是某个后端鉴权协议的替代方案。上游在区分失败类别时应保留具体后端来源。

  • 工具公开名要能直接查到后端
  • 列表可以精简，调用时还要检查权限

文档服务和产品目录服务都可以有一个 search。两个服务单独接入时没问题，聚合到一个客户端后，网关必须知道某次搜索发给谁。最难排查的是请求没报错，返回的 JSON 也对，数据却来自另一个服务。

我用两个模拟后端测试，互换注册顺序后，两种公开名都还能找到各自的服务。再把目录工具从权限里去掉，客户端即使知道名字，调用也停在网关。

工具公开名要能直接查到后端

网关收到上游工具列表后，给工具加稳定前缀。映射里记住连接和工具原名。客户端看到两个不同的名字，后端仍各自使用自己的 search。

两个同名工具的公开名和目标服务
客户端工具名 后端 转发时的工具名
docs__search 文档服务 search
catalog__search 目录服务 search

收到 tools/call 后，用请求携带的公开名查显式路由。如果在多个会话里直接找第一个叫 search 的工具，注册顺序变化就会改变调用结果。

前缀用服务标识，配置加载时检查最终名称是否冲突。维护显式映射也便于调整命名规则。旧客户端确实依赖短名时，只给归属明确的调用留兼容入口。两个后端都叫 search 时，让含义不清的短名报错。

列表可以精简，调用时还要检查权限

做文档问答时，工具列表可以只显示文档工具。描述里写明搜索范围、输入含义和返回内容，模型更容易选对。调用时还要检查当前身份和会话的许可，因为客户端可能记着以前看见过的工具名。

下面只展示路由顺序。网关先判断工具名是否允许，再找到目标连接。完整实现还要处理认证、协议报文和参数校验。

def dispatch(routes, allowed, sessions, name, arguments):
    if name not in allowed:
        raise PermissionError('tool unavailable')
    server, native_name = routes[name]
    return sessions[server].call_tool(native_name, arguments)

用模拟后端跑两遍，可以把两个判断拆开验证。

  1. 调换注册顺序，两种公开名都应到各自的后端，两个后端收到的原名仍是 search。
  2. 只开放文档工具时，再调 catalog__search 或短名 search。网关应拒绝，任何后端都不应收到请求。

这两项在本地模拟测试里都通过。接真实 MCP 服务时，再用目标客户端验证协议、参数和会话行为。

接真服务，失败来源要保留下来

上游可以用 stdio 或 Streamable HTTP。只要路由表同样能找到正确会话，换传输方式时，公开工具名与输入 Schema 可以保持一致。会话如果带有用户身份，连接复用也要受这个身份约束。

网关找不到公开名、连接断了、后端工具执行失败，分别记录。收到正常协议响应且工具返回执行错误，就把工具错误给调用方。三类都变成空列表，调用方会以为真的没有搜索结果。

后端改工具定义或网关改权限时，更新后的工具列表和路由应来自同一份配置。如果配置支持动态加载，可以先建好一份完整的表，再把列表和调用查询一起指向新版本。这样一轮更新不会暂时暴露只有名字、没有目标的工具。发布前我会刷新一次列表，再拿新参数调用一个更新过的工具，确认请求确实到了预期的会话。工具数量继续增加时，再考虑用语义检索缩小模型看到的候选。结果该发给哪个后端，继续用显式路由确定。
