两个 MCP Server 暴露了同名工具，网关怎么处理？

听白2026-11-25 约 2 分钟 近 30 天阅读 评论

聚合多个 MCP Server 时，我遇到过工具名字撞在一起的问题。单独接一个服务时，search 很清楚。接到同一个客户端以后，文档服务和产品目录服务都叫 search，模型看到两个相近的描述，网关也得知道收到调用后转给谁。

这个问题有两部分。首先得给客户端一个稳定、唯一的工具名。其次，当前任务用不到的工具，最好别出现在它的列表里。

先让每个调用有唯一去处

假设有两个后端，工具都叫 search。网关在读取工具列表时给它们加上稳定的前缀，再保留一份显式映射。

客户端工具名 后端 后端工具名
docs__search 文档 search
catalog__search 目录 search

收到 docs__search 时，网关通过映射查到文档服务，向它发起 search，把参数和返回结果交回当前会话。路由表最好也记录工具描述和参数 Schema。这样上游改了签名，下游可以在更新工具列表时发现，少等一次实际调用报错。

前缀用稳定的服务标识。用服务在配置文件中的位置命名，重排配置后就可能换掉含义。迁移已有客户端时，我会先列出被调用的旧名和各自去处，再决定是否需要为已知用法保留兼容入口。来源不清楚的短名应当返回明确错误，避免碰巧调用了错误的服务。

分组能缩小模型的选择范围

只做文档问答时，可以只给客户端 docs__search。需要查产品目录时，再提供目录相关工具。描述里也写清能搜索什么，以及一次调用返回的是条目列表、正文，还是摘要。命名解决唯一性，描述和分组帮助模型选中合适的工具。

分组如果涉及权限，就在处理 tools/call 时再次校验身份和允许的工具。工具列表决定客户端看见什么。调用检查决定它实际能执行什么。只筛选列表，已经知道名字的客户端仍可能直接发调用请求。

我会用两个返回不同固定文本的模拟服务做验收。先在完整工具列表分别调用两个名字，确认响应来自各自的后端。再切换到只开放文档工具的配置，用已有名字直接调用目录工具，确认网关拒绝。在这两步通过以后，再接真实后端和模型。
