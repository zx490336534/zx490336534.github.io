两个 MCP Server 暴露了同名工具，网关怎么处理？

单独接入一个 MCP Server 时，search 是个好名字。文档服务和产品目录服务都用这个名字也合理，直到它们出现在同一份工具列表里。我遇到这类问题时，先追一次调用从列表到转发走了哪几步。最难排查的是服务返回了正常结果，但结果来自错误的数据源。

先解决列表和实际调用里的名字

假设网关从两个后端读工具列表，两个都有 search。读列表时就给每个工具生成唯一的公开名称，并记录后端连接和原始名字。

暴露给客户端 对应后端 转发给后端的工具名
docs__search 文档服务 search
catalog__search 目录服务 search

客户端的 tools/call 请求带 docs__search，网关用它查路由表，找到文档服务的会话，把参数连同原名 search 交给后端。避免在收到调用后遍历会话找第一个叫 search 的工具。按顺序找，注册顺序一变，同一条调用的含义也会变。即使两个后端都能返回格式相同的 JSON，产品也可能拿到错误领域的结果。

前缀用稳定的服务标识。配置更新时检查最终生成出的公开名，发现冲突就拒绝这份路由。维护一份显式映射的好处是，改前缀规则之后不用猜下划线属于哪一段。迁移旧客户端时，可以给明确知道归属的短名做兼容入口。两个后端都有 search 时，含义不清的短名适合直接停用。

分组和权限各自改变什么

处理文档问答时，模型只需要看到文档工具。给它一页与当前任务无关的搜索和写入工具，会增加选错的机会。列表根据会话或用户可用的工具生成，名称之后的描述顺手写清搜索范围、参数的含义以及返回内容。这样模型可以在它真的需要选择时，根据清楚的对象来选。

服务端处理 tools/call 时，还要在当前身份和会话下重新确认权限。客户端用过某个工具，可能记着旧名字。名单发生过调整后，旧名单不应作为当前调用的依据。下面的代码省略了协议封包、用户认证和输入校验，展示路由顺序。

def dispatch(routes, allowed, sessions, name, arguments):
    if name not in allowed:
        raise PermissionError('tool unavailable')
    server, native_name = routes[name]
    return sessions[server].call_tool(native_name, arguments)

我用两个返回固定文本的模拟后端跑了这个路由测试。调换两个服务的注册顺序，两种公开名都仍然调用各自的后端，传下去的工具名都为 search。切换到只允许文档工具的会话，再调用 catalog__search 或没有前缀的 search，两次都在网关拒绝，两个后端都没有收到调用。这个结果验证的是路由和权限检查顺序，协议互通仍要用真实客户端和服务端测。

接入真实会话后，容易漏掉哪些状态

连接管理和工具路由可以独立处理。后端可能通过本地 stdio 接入，也可能通过 Streamable HTTP 接入。网关收到的是某个公开工具名，按路由找到已经初始化的会话。更换传输方式时，客户端看到的公开名和输入 Schema 可以保持一致。至于会话是否能复用，要按连接是否携带用户身份判断。属于两个用户的连接不能只按服务名共用一份。

调用失败也要保留失败来源。如果网关找不到公开名，这是网关路由问题。连接中断或超时是传输问题。后端完成了协议往返，却返回工具执行错误，应把这一状态按原有含义传回客户端。把三类都折叠成空结果，用户只会以为真的什么也没搜到。

工具列表缓存也要有更新条件。后端变更 Schema 或网关改变权限后，更新的路由表和对外列表应来自同一份配置。否则一次列表刷新就能看到新工具，随后调用仍被旧路由拒绝。在验收时我会加一个用例，更新后端工具定义后重新获取列表，再用新参数调一次，确认网关没有继续把请求送到旧会话。

把这几个检查做完，再比较接入多少工具、有没有必要按描述做检索。语义检索可以帮模型缩小候选。调用究竟转去哪个后端，仍应由唯一名和显式路由决定。
