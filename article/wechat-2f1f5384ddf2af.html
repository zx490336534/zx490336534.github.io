目的

统计 App 自动化测试运行期间的设备性能数据

方案

使用mobileperf来进行性能数据的采集

Android 性能稳定性测试工具 mobileperf 开源 (天猫精灵 Android 性能测试-线下篇)

数据采集实现

将mobileperf中各个采集类放到代码中/src/utils/perf,对其中的配置读取部分进行适当的修改，适配当前框架中的配置读取

数据展示实现

重新实现对数据的读取与展示

以CPU数据处理为例：

  1. 读取csv文件

  2. 删除pid为空的数据

  3. 去除重复写入的表头

  4. 留下要展示的数据并转化为float类型

  5. 时间列设置为datetime类型

def cpu_handle(self, path=f"{PERF_PATH}/cpuinfo.csv"):
    df = self.read_csv(path)
    # 去除pid列为空的数据
    df = df.dropna(axis=0, how="any", subset=["pid"])
    df.drop(df[(df.datetime == "datetime")].index, inplace=True)
    df = pd.DataFrame(df, columns=['datetime', 'device_cpu_rate%', 'user%', 'system%', 'idle%', 'pid_cpu%'])
    for i in ['device_cpu_rate%', 'user%', 'system%', 'idle%', 'pid_cpu%']:
        df[i] = df[i].astype(float)
    df['datetime'] = pd.to_datetime(df['datetime'])
    return df

处理完之后将它们展示在一张图上

名词解析

CPU

top

  • device_cpu_rate：整机CPU使用率

  • user%：用户态CPU使用率

  • system%：内核态CPU使用率

  • idle%：空闲CPU

  • pid_cpu%：测试对象进程的CPU

FPS（流畅度）

dumpsys SurfaceFlinger 或 dumpsys gfxinfo

  • fps：帧数

  • jank：丢帧数，掉帧（丢10帧算一次严重丢帧）

MEM（内存）

adb shell dumpsys meminfo [pkg]

  • total_ram：设备总内存

  • free_ram：可用内存

  • pid_pss：测试对象进程的内存

Power（能耗）（不准确）

dumpsys batteryproperties

dumpsys battery

  • voltage：电压

  • tempreture：温度

  • current：电流（0表示没获取到）

PSS

adb shell dumpsys meminfo [pkg] 可以用来查看指定进程包名的内存使用情况

  • pss：实际使用的物理内存

  • java_heap：java的堆内存

  • native_heap：其他的堆内存

  • system

android程序内存被分为2部分：native和dalvik，dalvik就是java堆，普通java对象是在java堆分配，而bitmap是直接在native上分配，对于内存的限制是 native+dalvik 不能超过最大限制。

Thread Num（线程数）

Traffic（网络流量）

读取/proc/net/xt_qtaguid/stats

  • device_total：设备总流量

  • device_receive：设备接收

  • device_transport：设备传输

  • pid_rx：上行流量

  • pid_tx：下行流量

  • pid_total：总流量

阅读视频文字稿

假设自动化脚本依次打开演示页、下滑列表、再返回。

采集报告里看到处理器上升、帧率下降、内存变高，但不知道哪一步正在运行。

文章介绍把性能采集接进自动化测试生命周期。

这里要再往前一步：为动作和指标建立同一时间参照。

否则你能得到很多数字，却没办法说变化发生在加载、滚动还是离开之后。

文章用会话级设置把采集启动和停止放在测试的边界。

这样即使某步失败，也有机会结束采集。

它不会自动知道列表何时开始滚动，所以要给动作写开始和结束的时间标记，关联本次演示编号。

若测试失败，保留已经采到的区间并标为未完成，不把结果和完整通过的对照样本混在一起。

将合成的处理器、帧与内存样本放到同一时间轴。

不同采集项的采样间距未必一样，所以你不能只用数组下标将它们硬拼成一行。

几秒采一次的数据，可能错过很短的峰值，也不宜装作每一帧都测到了。

先确定参考时钟和可解释的精度。

采集没有返回的数据就标缺失，不能把它画成使用量零。

在合成样例中，滚动开始后处理器抬升，帧的间隔变大，而返回后内存仍较高。

这只把调查范围缩小到那段操作，没有证明内存造成卡顿。

可以再重复同样操作，或者把图片内容设置成更薄的离线样例，检验哪种变化会消失。

分析时保留基线、操作窗口和恢复窗口，才不会把本来就在变化的背景活动误归给一个动作。

最后核对报告能不能由另一个人读懂：同一次测试跑了什么，什么时间开始结束，指标来自何处，哪几项采集失败。

换版本时继续使用相同窗口与条件，并保存多次的对比。

工具可以变，背后的方法不变。

把观测绑到明确动作上，才能判断是在看一个值得重测的线索，还是仅仅看到了互不相关的数字。
