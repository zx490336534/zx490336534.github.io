编写Jenkinsfile

我们暂时不和开发阶段的流程串联，先完成测试部分的流程。

测试部分流程，大概有这几步

  1. 测试环境准备

  2. 测试代码拉取

  3. 测试用例执行

  4. 测试报告生成

  5. 测试结果发送

这里采用固化的执行设备去进行测试，所以可以省略「测试环境准备」

采用Jenkins的方式发送报告没有直接在脚本中实现来的灵活，所以这一步放在后面实现

现在Jenkinsfile大致如下

pipeline {
   agent {

   }
   triggers {

   }
   parameters {

   }
   stages {
      stage('克隆代码'){
          steps{

          }
      }
      stage('执行测试'){
         steps{

      }
      stage('生成Allure报告'){
        steps{

        }
      }
   }
}

  • agent:指定执行的测试电脑

  • triggers:定时执行

  • parameters:参数化构建

  • stages-stage-steps:步骤

克隆代码

有时候我们需要动态地选择代码仓库里面的代码，这就需要使用gitParameter这个参数了

gitParameter(name: 'branch', branch: '', branchFilter: '.*', defaultValue: 'origin/master', description: '代码分支', quickFilterEnabled: false, selectedValue: 'NONE', sortMode: 'NONE', tagFilter: '*', type: 'PT_BRANCH')

它的名字是branch

默认分支为origin/master

使用的时候就是${params.branch}

credentialsId需要改为自己的凭证，不然可能因为权限不足无法拉取代码

stage('克隆代码'){
    steps{
        checkout([$class: 'GitSCM', branches: [[name: "${params.branch}"]], doGenerateSubmoduleConfigurations: false, extensions: [], gitTool: 'Default', submoduleCfg: [], userRemoteConfigs: [[url: 'https://gitee.com/zx660644/uitest.git',credentialsId: 'xxx',]]])
    }
}

执行测试

编写一个allure_debug.py主入口文件，执行全部的测试用例

使用dir切换工作路径，然后使用python xxx运行用例

最后使用exit 0退出

必须使用exit 0退出后才能生成Allure报告

stage('执行测试'){
   steps{
       dir("${env.WORKSPACE}/src/casess/") {
       sh ""
              sh '''
              python3 allure_debug.py
              exit 0
              '''
                  }
          }
}

生成Allure报告

path指定报告的存放路径就可以了

stage('生成Allure报告'){
  steps{
      allure includeProperties: false, jdk: '', results: [[path: 'report/allure_results']]
  }
}

完整Jenkinsfile

  • 每小时定时执行

参数化部分：

  • 可以指定执行的电脑「test_PC」

  • 可以指定执行的分支「branch」

  • 可以指定发送邮件「email」

  • 可以指定发送企业微信通知「robot」

  • 可以指定执行的用例「cases」

pipeline {
   agent {
       label "${params.test_PC}"
   }
   triggers {
        cron('H * * * *')
   }
   parameters {
        gitParameter(name: 'branch', branch: '', branchFilter: '.*', defaultValue: 'origin/master', description: '代码分支', quickFilterEnabled: false, selectedValue: 'NONE', sortMode: 'NONE', tagFilter: '*', type: 'PT_BRANCH')
        choice(name: 'test_PC', choices: ['a', 'b'], description: '执行设备')
        choice(name: 'headless', choices: ['false', 'true'], description: '是否不显示浏览器界面')
        choice(name: 'concurrent', choices: ['否', '1', '2', '3', '4', 'auto'], description: '是否并发执行,并发数')
        string(name: 'robot', defaultValue: '', description: '企业微信群机器人地址,以逗号分隔')
        string(name: 'email', defaultValue: '', description: '邮箱地址,以逗号分隔')
        text(name: 'cases', defaultValue: '''''', description: '要执行的用例', )
   }
   stages {
      stage('克隆代码'){
          steps{
              checkout([$class: 'GitSCM', branches: [[name: "${params.branch}"]], doGenerateSubmoduleConfigurations: false, extensions: [], gitTool: 'Default', submoduleCfg: [], userRemoteConfigs: [[url: 'https://gitee.com/zx660644/uitest.git',credentialsId: 'xxx',]]])
          }
      }
      stage('执行测试'){
         steps{
             dir("${env.WORKSPACE}/src/cases_ui/") {
             sh ""
                    sh '''
                    python3 allure_debug.py
                    exit 0
                    '''
                        }
                }
      }
      stage('生成Allure报告'){
        steps{
            allure includeProperties: false, jdk: '', results: [[path: 'report/allure_results']]
        }
      }
   }
}

阅读视频文字稿

纸舟的假团队想把一次移动页面演示整理成可读记录。

原文讲利用 Jenkinsfile 运行 UI 测试，并生成 Allure 报告。

这里不运行任何服务，只在桌面放候选、检查回执和档案袋。

流水线只是组织阶段；实际检查才给结论；报告则要读取正确的结果来源。

把三件事混在一起，看见报告存在就可能误认为本轮已经全部完成。

先给虚构版本、执行和回执各画一个明确记号，并用一条线连接。

哪怕纸舟库存里有一份长得很像的旧记录，也不能混进当前档案袋。

流水线说明阶段依赖关系，不替用例决定具体断言。

哪里负责收输入，哪里产出结果，哪里读取证据，都应能从记录直接找出来。

旧文中的写法属于当时工具组合，本片不复制命令。

如果测试按预期执行并发现错误，还是有机会保留合成失败回执；如果压根未开始，则没有对应结果。

第三种是结果已在，报告本身打不开。

三种情况不应该写成一样。

处理报告缺失时先看本轮是否真实产有记录，再判断读取或展示的状态。

不能用上一轮成功记录填空，也不能因为生成了一个页面就认为所有用例已执行。

模型里的档案袋只放必要的合成观察。

报告读这一袋，不能从其他测试轮次补东西。

实际项目还要说清谁能访问产物与附件，不因能生成就自动把它对外。

这里没有运行 Jenkins，也没有将报告发到任何地方。

纸面例子要证明的是各阶段的职责可见，报告出问题时读者能从状态追到真正缺失的环节。

最后请同伴比较成功、失败但有证据、没有结果三种静态记录。

每个版本都应该说明这次检查有没有执行，结果能不能找到，报告是读了哪一份。

项目环境与旧教程会不同，但从编排回到执行、再到产物与报告的证据链仍有用。

有了这条链，看到失败时不再只问按钮是不是变绿，而能确定该回到哪一层。
