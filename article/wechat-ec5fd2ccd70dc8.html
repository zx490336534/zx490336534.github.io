主题：AI 编程与研发

最开始用 GitHub Copilot 时，我几乎看过它补出的每一行代码。现在，一个需求可以直接交给 Coding Agent。它会自己找文件、改代码、跑测试，再把结果交给我。

效率高了很多，尴尬也出在这里。我经常说不清它为什么这样改。

为了确认这段变化不只是自己的感觉，我翻了一遍这几年留下的提交记录。两年多时间里有四千多次提交，横跨几十个代码仓库。数据里混着本地分支、文档和一些辅助记录，不能直接当成上线次数，用来看工作范围和提交习惯已经够了。

这次回看把我的 AI 编程经历分成了三个阶段。

Copilot 只接手几行代码

我大概从 2024 年初开始用 AI 编程，具体时间已经记不清了。最开始用的是 GitHub Copilot。它最常做的事就是 Tab 补全，我写出函数开头，它接着补几行。

这一年我在三十多个仓库里留下六百多次提交，平均每个有提交的工作日大约四次。做过流量回放、接口自动化、知识问答和 Code Review，也补了不少自动化测试。

那时的提交普遍很小。中间位置的一次提交只改两个文件、不到二十行代码，六成多的提交不超过两个文件。完整功能已经在做，AI 通常只参与其中几行。需求怎样拆、代码放在哪里、问题怎样收住，都由我自己判断。

我对代码的掌控也最强。AI 帮我少敲一些键盘，很少替我做决定。

聊天开始接手函数和组件

2025 年 3 月，我开始在网上找资料学习 LangChain 和 LangGraph。从 Chat Model、Tools、Agent、Embedding、RAG 一路看到案例实战，当时学得不算深，倒是第一次把 AI Loop 看清楚了。

模型先根据当前信息决定下一步，调用工具，把结果放回上下文，再继续判断。现在的 Coding Agent 复杂得多，基本动作仍然能从这套代码里看见。

这一年，我开始让聊天式 AI 写完整的函数和组件。每个文件都要认真解释，来回调整几轮，才能得到一个能接进项目的版本。它写出的代码有时连运行都过不了，我只能反复测试，再把报错丢回去继续改。

过程挺折腾，却有一个好处。代码虽然由 AI 生成，我仍然知道它在做什么。问题在哪里，为什么要这样改，最后怎样验证，我大多能讲清楚。

提交记录也能看到变化。全年有一千四百多次提交，平均每个活跃日大约七次。我开始做 Code Agent、MCP 接入、AI 对话接口和完整的前端组件。一次提示已经可以生成几百行代码，改动也经常跨过多个文件。

提交说明随之规整了不少。早期常见的 fix、修改和数字逐渐减少，更多提交开始写清功能、修复对象和重构范围。它不能证明代码一定变好了，至少说明我交给 AI 的任务边界更清楚了。

Coding Agent 开始接手完整任务

2026 年又有一段变化。我一度以为只是模型突然变强了，翻过对话和提交记录以后才发现，自己的使用方式也变了。

年初，Coding Agent 开始接手完整功能。一次任务会同时改接口、状态、页面和工具调用。以前我要围着一个文件聊很多轮，这时已经可以只交代目标。Agent 会搜索项目、修改代码、执行检查，再把结果交给我。

到了第二季度，提交速度没有继续上涨，活跃仓库却从十来个增加到接近二十个。任务里开始同时出现前端页面、对话服务、评测系统、主流程测试和发布检查。

这段经历纠正了我原来的感觉。我曾经把四五月当成效率突然起飞的时间，因为那两个月的 AI 对话数量增长很快。提交记录显示，当时增长得更明显的是工作范围。同样一天里，我可以同时推进更多项目，也开始把测试、文档和发布验证交给 Agent。

明显的速度变化出现在七八月。两个月有一千多次提交，平均每个活跃日超过二十次。去掉规范文档、辅助记录和协调性质的提交，核心代码仍然有十几次，约为 2024 年的三倍。

这时的任务已经很难用一个功能概括。Agent 会参与需求说明、代码实现、浏览器回归、评估报告、版本确认和交付前检查。我也开始把反复使用的规则写成 Skills，让它提前知道代码怎样检查、任务怎样拆、完成后怎样验证。

我的工作重心随之移动。亲手写代码的时间少了，更多时间花在交代目标、限制范围和检查结果上。

知识库也交给了 AI

2026 年初，我又开始让 AI 管理个人知识库。它会整理原始材料，编写 Wiki 卡片，再把新的结论写回笔记。

我当时有一个判断。模型能力已经足够强，影响结果的主要因素开始转向上下文。我逐渐少花时间琢磨提示词，转去帮助 AI 了解项目、了解我的习惯，也让它知道我以前做过哪些选择。

这个判断到现在仍然成立，但它留下了一个缺口。AI 得到的上下文越来越多，我自己接触的上下文却越来越少。

质量控制变多了，我的判断却变弱了

翻提交记录以前，我把问题概括成「能跑慢慢成了唯一标准」。这个说法有点简单。

测试和文档没有随着 Agent 接手任务而消失。第二季度触及测试文件的提交比例比第一季度高了一倍左右，最近两个月又到了四成上下。自动评估、浏览器回归、发布检查和版本确认也成了日常工作的一部分。

我无法据此得出代码质量一直下降的结论。变化发生在我判断质量的方式上。

以前我通过阅读代码理解质量。现在我更多依赖测试通过、构建成功、页面可用和部署完成。有些验证做得很细，上百条浏览器回归会检查真实页面、接口和最终结果。一百多条测试也可以全部通过。结果看起来越来越完整，我却可能说不清方案为什么成立。

最近我经常遇到一种情况。听到一个新名词，觉得可能对手上的系统有帮助，就直接让 AI 搜索、调研和改代码。AI 很快给出方案，测试也能通过，我便接受了结果。

再追问几句，问题就出来了。

  • 当前系统究竟哪里有问题，有没有失败样本或数据
  • 为什么要选这个方案，现有做法是否已经够用
  • 改完以后怎样证明变好了，出了问题怎样退回去

这些问题如果答不上来，我丢掉的已经超过代码细节。技术判断也在跟着变弱。提交越快，这个问题越容易被通过的测试和完整的报告盖住。

这件事我还没有想完

我最先想到的办法，是让 AI 在动手前写一份决策报告，完成后再回答收益、代价和回滚方式。很快我又发现，报告可以由 AI 写，测试可以由 AI 补，验收记录也可以由 AI 生成。如果我依然只是扫一眼，文档再多也没有用。

我已经在项目里加了不少质量控制。自动评估、浏览器回归、发布检查和版本确认都在做。它们能发现很多问题，仍然无法替我回答为什么要做这次改动。

目前我没有一套成熟的解法。我只是开始强迫自己多看三件事。改动前有没有真实问题，完成后有没有独立的运行结果，出了问题能不能退回去。

这些问题不会让我重新看懂每一行代码，至少能让我在几个重要节点上重新参与判断。

代码可以继续交给 AI。选不选方案、什么算有效、什么时候停止和退回，我还不想一起交出去。

「给 AI 喂上下文」和「给自己喂上下文」是一体两面。自己也是这个系统里的一个「模型」，同样需要摄入上下文才能做好判断。

阅读视频文字稿

作者发现，自己能把整项需求交给编码助手，但接到结果时，有时讲不清它为什么这样改。

他回看多年提交记录，试着把这个变化拆开来看。

记录混着本地分支、文档和辅助事项，不能当成上线次数，也不能证明行业整体效率。

但可以帮助一个人看清自己的任务怎样越交越大。

最早补全工具像邻座帮你补上一小块拼图。

作者知道目标和文件，也看过前面和后面的代码。

工具省掉敲键盘，却很少替人决定这段代码该放在哪里。

到了对话式编程，助手开始写整个函数或组件。

人仍要解释文件、回传错误、逐轮调整，因此虽然手写更少，却还经常保留整体的理解。

再到编码助手接手完整任务，它能搜代码、改接口和页面，还会跑测试。

作者看到不只是操作变快，工作范围也开始扩张。

测试和文档并没有消失，验证甚至比过去更多。

变化在于以前通过读代码做判断，现在更多依赖通过、可用和已部署。

它们能证明一部分结果，却不替你证明方案为什么成立。

如果一项功能改完测试都绿，先不急着接受。

回到三个问题：一开始到底有什么失败证据？

改动后有没有能核对的结果，不只是助手总结？

如果出了问题，怎么退回去？

这三个问题把你带回最关键的决策点。

作者没有把它当成万能方法，而是尝试用它保留自己的判断。

实际试一轮：动手前用一句话说清问题和不做的部分；改完后亲自看一项独立运行结果；最后指出失败后从哪里恢复。

不必重读每一行，也不必为了练习强迫手写全部代码。

先保证自己能解释方案、证据和回退，再决定是否扩大委托范围。
