用 Promptfoo 把一个 Agent 失败案例变成回归测试

Agent 接到一份生成任务，后端仍在排队，它回复「已经生成」。有些团队会给这条回复打一个低分。我更想把这个错误变成一条稳定失败的测试。这样以后改模型、提示词或任务状态接口，可以直接问同一个问题。当前版本还会提前告诉用户任务完成吗？

先写任务状态的约定

我给教学例子定的规则很小。任务处于排队状态时，返回合法 JSON，status 为 pending，同时不提供 assetId。这里刻意分开了三类错误。第一类提前宣布完成，第二类状态词写对了却带了并不存在的产物编号，第三类没返回约定的结构。只检查回答是否包含 pending，抓不全这三类。

先把四份构造输出放进 Promptfoo。echo 只把输入返回给断言。四个用例都模拟排队状态，区别仅在于保存下来的输出。

prompts:
  - '{{fixture}}'
providers:
  - echo
defaultTest:
  assert:
    - type: is-json
    - type: javascript
      value: |
        try {
          const result = JSON.parse(output);
          return result?.status === 'pending' && !Object.hasOwn(result, 'assetId');
        } catch {
          return false;
        }
tests:
  - description: 正确报告排队
    vars:
      fixture: '{"status":"pending"}'
  - description: 提前宣称完成
    vars:
      fixture: '{"status":"completed"}'
  - description: 排队状态却返回产物编号
    vars:
      fixture: '{"status":"pending","assetId":"demo-01"}'
  - description: 根本没有返回结构
    vars:
      fixture: '稍等一下'

保存为 promptfooconfig.yaml，在同目录执行 npx --yes promptfoo@0.126.0 eval --no-cache --output results.json。这份配置实测为一条通过、三条断言失败、零个执行错误，退出码为 100。故意加入的坏样本用于检验断言，常规应用回归要另建一套配置。

Promptfoo 实际在执行哪些东西

配置中的 Test 提供场景变量，Prompt 把变量变成输入，Provider 执行被测对象，Assertion 检查输出。现在用 Provider echo 复查固定输出，能确认判定规则有没有变。等 Provider 换成当前版本的 Agent API，变量应换成业务输入，例如同一条生成请求与一个稳定的排队任务夹具。断言接到的是这次真实调用的输出。两场评测的目标不同，报告也应该分开。

从固定样本切换到实时执行，可以保留这组断言，只替换输入和 Provider。下面是我用在本地模拟接口上的配置片段，省略了相同的断言。scenario 指向一个可重复准备的任务状态。实际接入时，可以通过预先建立的任务或测试环境夹具控制它。

prompts:
  - '{{message}}'
providers:
  - id: http
    config:
      url: http://127.0.0.1:8765/agent
      method: POST
      headers:
        Content-Type: application/json
      body:
        message: '{{prompt}}'
        scenario: '{{scenario}}'
      transformResponse: 'JSON.stringify(json)'

我让模拟接口对两条相同用户请求返回不同状态。请求参数从 queued-ok 改成 queued-bug，后端就把 pending 换成 completed。服务端记录到两次请求，Promptfoo 显示一条通过、一条失败、零个执行错误。这个实验确认的是输入确实经过 HTTP，到达服务，并由同一份断言判定。真实 Agent 的性能和稳定性要在目标环境里验证。

对于已有应用，我会先让 Provider 调用应用正常的入口，服务端继续使用自己的提示词和工具。把服务端 Prompt 复制到评测配置，会形成两个版本来源。服务升级后，评测很容易继续测到旧副本。只有专门比较提示词时，再把多个版本作为实验变量放进配置。

没有过滤条件时，2 个用例、2 份 Prompt、2 个 Provider，每个组合执行 3 次，就是 24 个评测单元。一次应用调用内部可能调多次模型，模型裁判还会增加请求。因此这里的 24 用来预估运行组合，账单要另外看实际请求数。先跑一个组，确认测试命中了预期 Provider，再展开全部矩阵。

哪些失败应该拦住发布

明确的业务约定适合用机器断言。例如任务还在队列中、金额错误、缺少强制字段，能立刻说明是哪条规则失败。文案是否让用户明白下一步，可以另设辅助评分，并先用人工确认的正反样本校准。文案得分再高，状态错误仍应单独报出来。

也要单独记执行错误。测试环境未启动、请求超时、权限失败，先查运行条件。服务正常返回了一个错误的业务状态，则进入产品回归。两者都可能让 CI 失败，但修法不同。检查 results.json 的逐条断言和运行状态，比只看一行总通过率容易定位得多。

我会在首次接入 CI 时故意只破坏一条已知业务规则，核对评估报告与 CI 结果都能抓住它。实时检验用例还要看缓存策略。回放一般希望完全可重复。判断部署后的应用行为时，要确认这次真的打到了预期环境和最新版本。
