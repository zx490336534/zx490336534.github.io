用 Promptfoo 把一个 Agent 失败案例变成回归测试

Agent 处理异步任务时，很容易把「已提交」写成「已完成」。这两个状态差一个词，用户看到的结果却差很多。假设一个任务助手在产物生成前就宣称完成，第一条回归只需要检查一件事。任务还在排队时，回复必须保留待完成状态。

我会先把出错时的输出保存下来，给它写一个能重复检查的断言。Promptfoo 负责把输入、执行方式和断言组合起来。最小版本可以先检查已经记录好的输出，再接当前的 Agent。

先让坏样本稳定失败

下面是教学配置，使用 echo 把样本原样送到断言，不需要模型或 API 密钥。两个用例的业务条件相同，任务都还在排队。第二个用例故意保留错误回复。

prompts:
  - '{{recorded_output}}'
providers:
  - echo
defaultTest:
  assert:
    - type: is-json
    - type: javascript
      value: 'JSON.parse(output).status === "pending"'
tests:
  - description: Expected output while a job is queued
    vars:
      recorded_output: '{"status":"pending"}'
  - description: Regression fixture that must fail
    vars:
      recorded_output: '{"status":"completed"}'

保存成 promptfooconfig.yaml，然后在同一目录运行 npx --yes promptfoo@0.126.0 eval --no-cache。用这个版本跑上面的配置，结果是一条通过、一条失败，执行错误为零。如果两条都过，先查断言有没有接到真实输出。练习时留着这个失败样本可以证明检查有用。接入 CI 时，把它保留为断言的负例，常规回归则调用当前应用，检查它能否在相同条件下给出正确状态。

回放和实时执行回答两个问题

回放帮我确认规则变更之后，旧样本还能被正确判定。实时执行要看新版本会不会再产生同一种错误。两者最好有不同的报告名称。回放全绿之后，当前服务的接口、权限和任务状态仍要在实时用例里检查。

这个例子用 JSON 状态做断言，错误位置很明确。如果输出是自然语言，可以先让实际应用返回一个能检查的结构化状态，把文案留给另一条测试。需要判断说明有没有误导时，可以再加模型评分，并用已知正反样本校准。一次评测可能跑多个模型、提示词和用例的组合，我会先把这一行跑明白，再逐步展开组合矩阵。

进发布门禁以前，我会故意把 pending 换回 completed，看失败结果是否能传到 CI。否则即使评测工具识别了错误，发布流程也未必会拦住它。
