用 Promptfoo 把一个 Agent 失败案例变成回归测试

任务明明还在排队，Agent 却告诉用户「已经生成」。我把这个错误做成四条固定样本。用 Promptfoo 本地跑，一条正确样本通过，三个反例都失败，执行错误为零。

这一步先确认断言能不能抓到错。下一步再让同一条断言检查当前服务的真实回复。

先让断言识别三种错误

给例子定一条可检查的约定。排队时，返回合法 JSON，status 为 pending，且不带 assetId。只在回复里搜 pending，会漏掉「状态正确却捏造了产物」这一类错误。

四条固定样本及预期判定
保存下来的输出 预期判定
{"status":"pending"} 通过
{"status":"completed"} 提前宣称完成
{"status":"pending","assetId":"demo-01"} 排队中却提供了产物编号
稍等一下 缺少约定的 JSON 结构

用 echo 把固定输出送给断言。配置保存为 promptfooconfig.yaml，在同目录执行下面的命令。坏样本是故意放进去的，这次实测退出码为 100。发布门禁应单独跑当前应用的回归配置。

Promptfoo 固定样本 YAML 
prompts:
  - '{{fixture}}'
providers:
  - echo
defaultTest:
  assert:
    - type: is-json
    - type: javascript
      value: |
        try {
          const result = JSON.parse(output);
          return result?.status === 'pending' && !Object.hasOwn(result, 'assetId');
        } catch {
          return false;
        }
tests:
  - description: 正确报告排队
    vars:
      fixture: '{"status":"pending"}'
  - description: 提前宣称完成
    vars:
      fixture: '{"status":"completed"}'
  - description: 排队状态却返回产物编号
    vars:
      fixture: '{"status":"pending","assetId":"demo-01"}'
  - description: 根本没有返回结构
    vars:
      fixture: '稍等一下'

npx --yes promptfoo@0.126.0 eval --no-cache --output results.json

保留断言，把输入切换成真实请求

Promptfoo 的用例提供变量，Prompt 将它们拼成输入，Provider 执行被测对象，Assertion 检查输出。用 echo 时，执行对象只会回显保存下来的输出。换成 HTTP Provider，变量就应该变成一条实际业务请求和一个可重复准备的任务状态。

Promptfoo HTTP Provider 配置片段 
prompts:
  - '{{message}}'
providers:
  - id: http
    config:
      url: http://127.0.0.1:8765/agent
      method: POST
      headers:
        Content-Type: application/json
      body:
        message: '{{prompt}}'
        scenario: '{{scenario}}'
      transformResponse: 'JSON.stringify(json)'

我用本地模拟接口验证了这个切换。两条请求的用户消息相同，场景分别设为 queued-ok 和 queued-bug。后端收到两次请求，分别返回 pending 和 completed。同一份断言判出一条通过、一条失败，执行错误为零。这能确认请求确实到了服务，模型的表现需要在运行真实 Agent 时再评。

测已有应用时，让 Provider 调应用平时使用的入口。服务端继续管理自己的提示词和工具。只有问题明确是「哪版 Prompt 表现更好」，才把多个 Prompt 作为实验变量，免得服务端更新后，这边还在评估一份旧副本。

没有过滤时，两条用例、两份 Prompt、两个 Provider，每组跑三次，一共 24 个评测单元。每个单元背后可能调用多个模型，评分也可能产生新请求。先跑一组，确认被测服务和模型命中，再展开全部组合。

发布报告要能区分业务错误和运行错误

状态、金额和必填字段有明确规则，可以直接判。文案是否容易理解，可以另做评价，先拿人工确认的正反样本校准。两种结果分别记录，业务状态写错时，文案得分再高也不能放行。

固定样本的结果也能拿来查断言本身。带 assetId 的样本仍是合法 JSON，要看第二条业务断言有没有变红。直接返回中文短句时，结构断言就会失败。区分这两个输出，下一次加字段时才知道该改结构还是业务规则。

结果报超时或鉴权失败，先查运行条件。服务正常响应却给出错误状态，才进入产品回归。打开 results.json 的逐条结果，比只看通过率更容易判断该查哪一边。

首次接入 CI，我会让模拟服务只破坏一个已知条件，确认断言变红、CI 也能拿到失败退出码。验证部署时再检查缓存选项和被测版本，避免把旧结果当成这次服务的表现。
