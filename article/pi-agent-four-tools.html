Pi Agent 为什么默认只给四个工具？

本文速读

结论：用一次失败单测判断四个默认工具够不够：先读取、再改动、再执行验证；新增扩展应能解决任务中观察到的缺口。

适用范围：这是编码助手与其本地工作区的例子。切换会话分支后，需要另查实际文件状态，不能把会话分支当成文件快照。

  • 把失败单测交给四个工具
  • 一次调用从模型走到扩展，再返回给模型
  • 切换会话以后，先看工作区

Pi 默认给模型 read、edit、write 和 bash。读文件、改文件、写文件、执行命令，这四步已经能跑完一次单测修复。搜索、构建和测试直接用项目现成的命令。

工具少，运行时留下的问题也更清楚。模型靠哪条证据决定下一步，扩展能在什么时候拦一下，切换会话分支以后磁盘上还有什么。读 Pi 的源码和文档时，我主要在看这三件事。

把失败单测交给四个工具

拿失败单测做例子。模型用 bash 看到报错，通过 read 打开实现和用例，用 edit 修正错误分支，再运行原来的测试。如果缺一个新用例文件，用 write 保存。

四项是默认启用的工具。Pi 也提供 grep、find、ls，并允许按任务替换工具列表。只想理解一个模块时，可以把这一轮限制为读和搜索。

pi --tools read,grep,find,ls

当前文档还列了 pi mcp 和扩展工具。接入这些能力以后，模型实际看见的工具会受到项目配置影响。讨论「Pi 有几个工具」时，我会先确认在说默认集合还是已经配置好的环境。

我会把只读探索和实际修改分成两次运行。先确认能读到入口文件、构建命令和验收要求，再开放需要的写入工具。做到能解释改哪些文件和如何验证，就可以结束第一轮。

开放 bash 时，命令能碰到哪些目录和网络资源取决于 Pi 进程的权限。工具列表可以收窄模型的动作，文件和网络隔离还要在运行环境里做。

一次调用从模型走到扩展，再返回给模型

模型在回复里请求工具。Pi 调用它，把结果追加到上下文，再让模型继续。单测的错误文本进入下一轮以后，模型可以读文件、改代码，或者停下报告。运行时的循环很短，项目想要求哪些验收步骤，要在项目规则或外部 CI 里写清楚。

扩展的 tool_call 发生在执行前，可以拒绝或调整输入。tool_result 在执行后，可以整理送回模型的结果。团队要保留验收依据时，可以把实际命令、退出状态和报告位置完整保存，再给模型一份短摘要。只跑了一个测试文件，报告的范围也只写到这一层。

同一条助手消息有多个工具调用时，默认并行模式下，前置检查逐个执行，实际任务可以并发。工具 B 要读工具 A 刚写的配置，就把两步拆开执行。B 的前置检查不一定能看到 A 的执行结果。

切换会话以后，先看工作区

/tree 可以回到较早的消息继续，原来的尝试仍留在另一条分支。下一次请求使用当前分支上的对话。之前改过的代码还在磁盘上，切换消息位置并不会替你回滚文件。

想同时试两个实现，可以给两条路线各用一个 Git worktree。只在同一个目录里试时，切换之前先看 git status，把需要保留的改动留成可恢复的检查点。

聊天太长时，Pi 会用摘要接替早期上下文，原始会话记录仍可查看。长期兼容条件、禁止修改的目录和验收标准适合放进项目说明。摘要之后再读一次，就不用指望模型记住某条很早的消息。

用一条真实任务决定要加什么

仓库说明适合写构建和验收步骤，Skill 适合约定处理某类任务的方法，扩展适合在工具执行前后加检查。主分支发布需要的签核和权限，放在独立流程里执行。

我会先用一个有失败用例的修复试跑。看它是否读到项目说明，第一次失败后用了哪条证据，以及最终报告能不能回到具体运行。缺上下文就补项目入口。要是只跑了局部测试却报整体验收，就先补验收范围和证据规则。

文章拿一次失败单测来说明，编码工具不一定要很多。

先用命令看到失败，再读实现和用例，修改最小范围，必要时加一个新的用例文件。

最后回到同一个测试重新运行。

四种动作能串起这个过程，但测试确实通过与助手说修好了，不是同一件事。

Pi 默认开放四类工具，但配置可以替换这批工具，也能接入扩展。

只想读懂一段代码时，没必要同时允许写文件和执行命令。

限制模型可选的工具是一层，进程到底能接触哪些文件和网络则是另一层。

别把工具列表当成一个能自动隔离整个系统的安全边界。

模型提出调用以后，运行时执行它，再把结果加入上下文。

扩展可以在执行前做额外检查，也可以在执行后整理结果。

如果需要证明自己完成验证，要留下实际退出状态、产物位置和范围。

模型拿到摘要方便继续，但摘要不该替代能回看的原始证据。

假如工具 A 要写一份配置，而工具 B 需要读取它，这两步就有顺序依赖。

即使前置检查按顺序进行，也不等于实际执行已经结束。

如果让两步进入同一次并发调用，工具 B 可能读到旧文件，或者什么也没读到。

把依赖拆成两次，等 A 的结果回来，再执行 B。

切换会话分支以后，聊天可以从更早的位置继续，但磁盘上的文件不会自动变回当时的样子。

要比两个实现，最好隔离工作区，或者先留下可恢复的检查点。

最后回到最初失败的测试，确认哪次修改和哪条结果对应。

能把这条链解释清楚，比再加十个工具更有用。
