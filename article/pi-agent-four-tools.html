Pi Agent 为什么默认只给四个工具？

读 Pi 的公开文档和源码时，我注意到它的默认工具只有四个。read 读文件，edit 改现有文件，write 写文件，bash 跑命令。把这四项列出来很容易。更值得看的是，搜索、测试、Git 和会话管理是怎么接进去的，以及一旦要给团队用，哪些事仍得由自己做。

四个工具怎样跑完一次代码修复

假设项目里有一条测试失败。模型先用 bash 跑测试，从输出里读到失败位置。接着用 read 读实现和相关用例，用 edit 改错误分支，再跑同一条测试。需要加一个文件时用 write。代码搜索可以在 bash 里执行项目已有的搜索命令，构建和版本检查也一样。模型只需要知道当前目录有什么工具和项目规则允许做什么。

Pi 也提供 grep、find、ls 等可选工具。可以用 --tools 替换默认集合。比如只想让模型解释一个模块，可以显式只给读和搜索工具。

pi --tools read,grep,find,ls

四项工具描述的是默认启用的集合。当前官方文档也提供 pi mcp 来配置外部服务，扩展可以再注册专用工具。看早期文章时，要留意它写的是哪个版本，以及用了哪些本地配置。

这个默认配置利用了开发环境已经有的能力。一个项目有清楚的测试命令，Agent 就能直接运行。换到另一个项目，调用形式也一样，项目约束则从当前目录的说明读。反过来，通用命令也让权限变得粗。给了 bash，能执行多少操作取决于 Pi 进程、系统和运行环境。只开放读工具适合约束模型此次能选择的动作。有文件权限边界时，还要由隔离环境限制进程实际能碰到什么。

把一次工具调用拆开看

Pi 的 Agent 循环接收模型的流式输出。如果模型结束这一轮时请求了工具，就执行工具，把结果加入上下文，再决定要不要发起下一轮模型请求。测试失败的输出会出现在随后一轮上下文里。模型可以根据它继续读代码或给出结果。运行时本身不会因为看到一句「测试失败」就自动切换到某个固定的开发流程。

扩展能在几个时点接入。tool_call 发生在实际执行前，可以拒绝或调整输入。tool_result 发生在执行后，可以整理返回内容。要给团队保留完整证据，我会让执行记录保留实际命令、退出状态和结果出处，再给模型一份更短的摘要。测试只跑了一个文件时，模型最后的结论也应该保留范围。

当前文档还提到了同一助手消息的多个工具调用。默认并行模式下，前置检查依次执行，真正任务可以并发。两个同时发起的命令有先后依赖时，不能指望第二个在自己的前置检查阶段就能看到第一个的完成结果。像「先写配置，再跑构建」这种依赖，最好按明确顺序执行和取证。

会话分支解决的是对话选择

从 /tree 回到更早的消息继续，可以留下两条尝试路线。下一次请求只使用当前分支的对话历史。这样试过的方案还在，需要时也能回来比较。如果之前的分支已经改过文件，切换对话节点以后，磁盘上的改动仍在。想让研究结果也隔离，可以给分支准备独立的 Git worktree，或者在切换前保留工作区检查点。

上下文压缩处理的是另一个问题。对话太长时，运行时让摘要接替较早的部分，并保留最近消息，历史记录仍可访问。摘要适合让模型继续干活。某个兼容性条件、禁止写入的目录和验收标准不适合只藏在旧聊天里。我会把这些东西写进项目说明或任务记录，让会话压缩后还能重新读到。

团队要补的东西，可以从一次真实任务里找

一段仓库说明适合解释如何构建和验收。Skill 适合告诉模型什么时候按某种做法处理。扩展适合在执行前后加检查，独立的 CI 则可以重复验证实际产物。比如主分支发布必须检查特定测试报告，这条规则可以在 CI 上强制。给模型一段说明能让它知道自己应该干什么，发布权限仍应由外部流程控制。

挑一个能用同一条测试验证的修复，先观察三件事。它有没有读到项目说明，失败后用了哪条证据决定下一步，以及最终报告对应哪次运行。看完再决定要加什么。如果问题出在看不到代码，补读工具或上下文就够了。如果问题出在误把一次局部通过当整体通过，优先补验证和取证规则。
