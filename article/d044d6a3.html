web应用处理请求的具体流程

  1. 用户操作浏览器发送请求；
  2. 请求转发至对应的web服务器
  3. web服务器将请求转交给web应用程序，web应用程序处理请求
  4. web应用将请求结果返回给web服务器，由web服务器返回用户响应结果
  5. 浏览器收到响应，向用户展示

    一个wsgi服务

全称Python Web Server Gateway Interface，指定了web服务器和Python web应用或web框架之间的标准接口，以提高web应用在一系列web服务器间的移植性。 具体可查看 官方文档:https://www.python.org/dev/peps/pep-0333/

  1. WSGI是一套接口标准协议/规范；
  2. 通信（作用）区间是Web服务器和Python Web应用程序之间；
  3. 目的是制定标准，以保证不同Web服务器可以和不同的Python程序之间相互通信
  1. env：字典，包含请求的所有信息
  2. start_response：在可调用对象中调用的函数，用来发起响应，参数包括状态码，headers等

纸舟展品台有一张虚构摘要卡。

你可以把浏览器对它的请求想象成一张由服务器接收的纸条，应用处理后送回结果。

原文从 WSGI 的角度介绍 Flask 的请求处理。

本片不启动服务器，而强调一个交接边界：网络侧接到的消息要交给 Python 应用，应用知道如何接收规范化信息、如何交回回应，不必自己在每个场景重写网络收发。

服务器在模型里将请求细节整理成应用可以理解的环境信息，并给一项用于开始响应的约定。

应用按规则提供状态和头信息，然后用约定的可迭代内容交付正文。

这个约定发生在服务器与 Python 应用之间，不是浏览器直接发送另一种网络消息。

原文用极小的应用帮助理解这些角色，本片只画交接，不展示运行命令或任何服务配置。

在桌上放一张展品存在的卡，应用能说找到摘要；另一张不存在，就需要明确说找不到。

状态和正文都属于响应交接，不能头上说找到，内容却表示没有。

回到外侧由服务器将结果送给浏览器概念一侧。

不要把能收到一个响应说成业务一定对了，仍核对给的是同一份展品及正确的提示。

本片只用手写虚构卡，不处理任何真实请求。

框架让你更方便地把某类输入交给适合的业务处理，不需要每个功能都自己拼出所有层。

服务器和应用之间仍有相应的调用边界。

过去的教程可能用便于学习的方式展示一个最小服务，不能直接据此选择怎样部署。

其他接口模型也可能不同，不必在第一篇全掌握。

先能在图上分别指出谁与浏览器交互、谁决定业务含义，就能理解本文的主要线索。

最后在纸面复述去程和回程。

请求进入服务器，应用收约定输入并判断这份合成摘要，返回结果再交回网络一侧。

若找到与缺失的两张回执有差异，可以指出属于状态、内容还是没有观测。

知道这个边界，读到后面框架如何注册路由就更容易。

同时记得，概念模型不代表任何真实系统已经部署或运行。
