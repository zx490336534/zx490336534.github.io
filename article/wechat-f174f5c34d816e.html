pytest的一个demo

上周看了元类的实现方式后，对「代码块」的理解好像有了不一样的认知。

  • 函数是一段代码块

  • 类也是一段代码块

根据现在的工作中使用的pytest写一个demo

demo：

import pytest
import requests

@pytest.fixture(scope='module')
def get_request():
    request_list = []

    def _get_request(data, flag=True):
        if flag:
            x = requests.post('http://httpbin.org/post', data=data)
            request_list.append(x.json().get('data'))
        return request_list

    yield _get_request

@pytest.mark.parametrize("i", [1, 2, 3])
def test_customer_records(i, get_request):
    print('\n')
    print(f'第{i}次测试')
    customer = get_request(f'{{"a{i}", "b{i}"}}')
    print(customer)

结果：

第1次测试
['{"a1", "b1"}']
.

第2次测试
['{"a1", "b1"}', '{"a2", "b2"}']
.

第3次测试
['{"a1", "b1"}', '{"a2", "b2"}', '{"a3", "b3"}']

解释：

  1. 使用module级别的fixture可以定义一个存放多次数据的空的列表request_list

  2. 在fixture中写一个函数，并用yield将它返回以供调用

  3. 测试的时候使用参数化构建case会执行三次

  4. 从测试结果可以看出，列表内容持续增多

写的时候感觉好像很神奇，后来想想其实和以下方式实现的效果一样：

request_list = []
def _get_request2(request_list, data, flag=True):
    if flag:
        x = requests.post('http://httpbin.org/post', data=data)
        request_list.append(x.json().get('data'))
    return request_list

@pytest.fixture(scope='module')
def get_request2():
    yield _get_request2

@pytest.mark.parametrize("i", [1, 2, 3])
def test_customer_records(i, get_request2):
    print('\n')
    print(f'第{i}次测试')
    customer = get_request2(request_list, f'{{"a{i}", "b{i}"}}')
    print(customer)

也不就是：

request_list = []
def _get_request2(request_list, data, flag=True):
    if flag:
        x = requests.post('http://httpbin.org/post', data=data)
        request_list.append(x.json().get('data'))
    return request_list

@pytest.mark.parametrize("i", [1, 2, 3])
def test_customer_records(i):
    print('\n')
    print(f'第{i}次测试')
    customer = _get_request2(request_list, f'{{"a{i}", "b{i}"}}')
    print(customer)

额，好Low

不过其实也不是毫无用处，当scope等级改变之后

  • session：项目级传递数据相当于global

  • class：class级别传递数据，并可以使用pytest的turndown机制

  • function：函数级别，没啥用

假设有张离线练习表单，可以提交一条待办标题。

最小验收不是跑遍整个页面，而是这一件事：填入合法标题时，返回演示成功，且回执中的标题与输入一致。

原文通过一个 pytest 示例展示准备和执行。

我们只用本地模拟函数讲，把用例拆成准备、动作、断言，让读者能看出它具体证明了什么。

准备阶段先创建一条练习数据，确定模拟表单里没有上次残留。

若多个用例要复用同一准备步骤，可以让 fixture 统一提供，不过用例自己仍应看得出依赖什么。

不要把所有断言塞到准备函数里面。

准备失败、动作失败和断言不符合是不同情况，分得越清楚，出现错误时越容易查。

执行时只做一次真正想测试的动作，取得本轮的模拟回执。

然后检查两个条件：它明确是成功，回执的标题就是刚才那条。

不要只写回执不是空，这会让报错回执也通过。

也不必断言所有无关字段，比如返回顺序碰巧怎样。

断言越能说明哪部分契约破了，报告越有用。

准备空标题这条反例。

被测系统预期会拒绝，这种情况下测试是通过的。

反过来，若系统给了错误提示却仍偷偷创建任务，测试就应失败。

通过和失败描述的是契约是否兑现，不是页面文案本身有没有出现错误。

这两个例子放一起，能避免把看到成功字样当成测试的全部。

整理时给用例起清楚的名字，把输入保存成能理解的小样本，并保证和一组其他用例一起运行时，仍得到相同结果。

失败时告诉人预期是什么、实际差在哪里，而不是仅贴一张图。

到这里才算有了一个可靠的小测试。

下一支会给同一张演示表单增加更多数据，看看怎么组织而不多复制重复步骤。
