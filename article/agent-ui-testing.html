Agent 时代的 UI 自动化，哪些步骤值得用 AI？

我给 UI 自动化选工具时，会先找出一条用例里最难写的动作。有些步骤难在定位，比如画布上没有 DOM 节点的图形。有些步骤难在判断结果，比如保存以后到底有没有写入服务端。前者可以让模型看图，后者通常能找到更明确的检查点。把两种难处混在一个自然语言用例里，出了问题很难判断应该修脚本、修提示词，还是修产品。

一个错误实现，也能让「保存成功」通过

我用一个小编辑器复现了这种假通过。输入卡片名，点击保存，两个版本都返回 HTTP 200，也都显示「保存成功」。区别在服务端。正常版本写入记录，故障版本收到同一份请求后直接返回成功。

用 Playwright 依次检查请求、页面提示、刷新后的已保存列表，实际结果如下。两个版本走相同的前端，一个服务进程内分别提供正常和故障路由。每次用新的浏览器上下文，卡片名也由用例控制。

服务端行为 POST 响应 成功提示 刷新后查已保存列表
写入后应答 200 通过 找到卡片
丢弃写入后应答 200 通过 找不到卡片

下面是测试的关键部分。base 是本地演示服务的地址，mode 用来选择正常或故障路由。对同一接口同时存在读取和保存请求时，需要同时匹配 URL 和 HTTP 方法，否则用例有可能等到列表的 GET。

page.get_by_label('卡片名称').fill('回归卡片')
with page.expect_response(
    lambda r: r.url == f'{base}/api/{mode}' and r.request.method == 'POST'
) as save:
    page.get_by_role('button', name='保存').click()
assert save.value.ok
expect(page.get_by_role('status')).to_have_text('保存成功')
page.reload()
cards = page.get_by_role('list', name='已保存卡片')
expect(cards.get_by_text('回归卡片', exact=True)).to_be_visible()

演示页刷新时会重新请求服务端，关闭了缓存，也没有把卡片放进本地存储。实际应用要先确认刷新读的是哪一层。如果它会先用浏览器缓存恢复页面，刷新仍可能复用旧状态。此时可用新的浏览器上下文重新登录回读，或者直接检查服务端详情接口。列表里历史上存在过同名卡片时，按本次生成的 ID 查，比按文本查更稳。

AI 放在哪一步，决定失败时能看到什么

Playwright 的 get_by_role 或 get_by_label 适合角色和名称稳定的控件。Agent 可以在编写阶段检查页面、生成测试、读 trace，再修改定位方式。测试进 CI 后继续按确定的过程执行。这种写法适合表单、导航、权限提示、接口和持久化验证。

Canvas 和 WebGL 界面经常只暴露一个画布元素。可以算坐标点击，但缩放、工具栏位置或布局一变，原来的坐标就可能落错。以 Midscene 为例，可以让模型用 aiAct 规划多步操作，也可以继续由脚本决定顺序，只让视觉工具做定位或拖放。拿放置卡片来说，我会把「将这张卡拖到右边列」交给视觉工具，随后由脚本读取卡片所属的列和最终保存状态。模型在截图里识别到了目标，只能说明它观察到什么。应用回读到列标识和卡片 ID，才能作为通过证据。

用法 适合解决的问题 出错时优先核对
Agent 写脚本，运行时用 Playwright 普通 DOM 上的稳定回归 页面定位、请求和业务断言
脚本编排，视觉模型做少量操作 图形界面中的定位或操作 截图、实际点击位置、动作后的产品状态
模型规划多步探索 操作顺序不固定、需要发现异常 操作轨迹及复现证据，确认是否能编入回归

这里也不用预先规定每套测试必须是同一种模式。把视觉能力放进需要它的那几步，可以让剩下的步骤继续确定执行。视觉操作的成功与任务完成分别记，排查时不用猜一句笼统的「成功」指什么。

修脚本之前，先保住它抓过的错误

按钮改名导致定位失败时，调整定位器是合理修复。刷新后读不到卡片时，我会保留这条失败，从请求有没有提交、任务状态是否结束、最终记录是否能读取逐段排查。把失败断言改为检查成功弹窗，相当于把这次实测抓住的错误重新放过去。

如果后台返回 202，响应只说明任务被受理。把等待拆成两个条件更容易诊断。先等对应的任务进入明确终态，再按返回 ID 回读产物。不能只看到任何一个历史任务完成就结束，也不要用固定睡眠替代等待条件。测试失败时记录这次操作的 ID、最后一次任务状态，以及最终回读失败的那一步。

发布前我会保留一个故障版本做验证。让它显示保存成功、故意漏掉持久化，看用例能否失败。动作会不会点击错、页面能不能回读、回归能否拦住已知错误，分别回答，才知道这条用例适不适合守发布。
