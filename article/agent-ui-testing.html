Agent 时代的 UI 自动化，哪些步骤值得用 AI？

我用 Playwright 跑了同一个小编辑器的两个版本。两个版本点保存都返回 HTTP 200，页面也都提示「保存成功」。刷新以后，只有一个版本能找回卡片。

这个实验也决定了我怎么分配工作。模型可以帮忙定位和操作，是否保存成功要由回读结果判定。 两类检查分开，查失败时才知道是没点对地方，还是产品没把数据存下来。

保存返回 200，刷新后卡片却消失了

故障版本接到保存请求以后直接返回成功，跳过了写入。两个版本共用同一份前端，测试也走一样的路径。每轮新建浏览器上下文，卡片名称由测试控制。

保存后两种服务端行为的实测结果
服务端行为 保存响应 页面提示 刷新回读
写入后应答 200 保存成功 找到卡片
跳过写入后应答 200 保存成功 找不到卡片

脚本先等这次保存的 POST，再查提示，最后刷新并在已保存列表中查卡片。等响应时同时匹配 URL 和方法，因为列表读取的 GET 也用同一个地址。下面的 base 是本地演示服务地址，mode 选择正常或故障路由。

Playwright 保存回读脚本 
page.get_by_label('卡片名称').fill('回归卡片')
with page.expect_response(
    lambda r: r.url == f'{base}/api/{mode}' and r.request.method == 'POST'
) as save:
    page.get_by_role('button', name='保存').click()
assert save.value.ok
expect(page.get_by_role('status')).to_have_text('保存成功')
page.reload()
cards = page.get_by_role('list', name='已保存卡片')
expect(cards.get_by_text('回归卡片', exact=True)).to_be_visible()

演示页刷新时会重新向服务端取数据，关闭了缓存，也没有用浏览器本地存储恢复卡片。真实应用如果会先读缓存，可以换一个浏览器上下文重新登录，或直接查服务端详情。列表里可能有同名记录时，按本次保存的 ID 查。

普通控件用脚本，视觉模型补定位

表单、按钮和导航有稳定的角色或名称，可以让 Agent 在编写阶段生成 Playwright 测试，CI 按脚本执行。比如保存按钮改了文案，先从 trace 确认按钮是否仍可用，再改 get_by_role 的定位条件。

Canvas 或 WebGL 界面往往只暴露一个画布元素。卡片本身没有 DOM 节点，写死坐标又容易受缩放影响。可以让视觉模型完成「把卡片拖到右边一列」，随后由脚本读取列标识、卡片 ID 和保存状态。Midscene 的 aiAct 也可以规划多步操作。路径比较稳定时，我会保留脚本编排，只交出确实难定位的那一步。

三种自动化方式和排查入口
用法 适合的场景 失败时查什么
Agent 写脚本，CI 固定执行 表单、导航、接口回归 定位、请求、断言
脚本编排，模型做视觉操作 画布拖放、图形定位 截图、点击位置、产品状态
模型规划多步操作 路径不固定的探索 操作轨迹、能否复现

测试修完，还要能抓住原来的错

按钮改名可以改定位器。刷新后卡片没了，就去查保存请求、任务状态和读取接口。如果把回读断言改成检查成功提示，上面那个故障版本就会通过。

异步保存收到 202 通常只说明请求已受理。先等本次任务到明确终态，再按它返回的 ID 回读产物。失败报告留三个值就有用得多，本次操作的 ID、最后查到的任务状态，以及失败的那一步。

回读失败时，按失败点留证据。POST 没发出来，先查页面操作。已经提交但任务没到终态，留住任务编号和最后一次查询结果。任务成功后读不到对应记录，再查写入和读取的对象是否一致。

挂发布门禁前，我会再跑一次故意跳过写入的版本。它能亮出成功提示，测试仍会在回读处失败，这条回归才守住了用户真正依赖的行为。
