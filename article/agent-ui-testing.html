Agent 时代的 UI 自动化，哪些步骤值得用 AI？

我给 UI 自动化选工具时，先看 AI 在什么阶段工作。它可以在写测试时读页面、生成脚本，也可以在每次执行时观察页面、决定怎么操作。这两种方式都能从一句自然语言开始，但以后每次跑回归，耗时、成本和失败证据会很不一样。

同一条用例要通过两个判断

拿一个可以公开演示的场景。用户在网页编辑器里放置一张卡片，点保存，刷新后还要看到刚才保存的内容。这里有两件事要验证。先看卡片能不能放到目标位置，再看保存的数据能不能恢复。

表单、保存按钮、已保存记录都有明确的角色或标识。用 Playwright 按按钮名称定位，再读取刷新后的记录。只要保存动作虚报成功，后半段就会失败。只检查成功提示的话，前端即使在请求还没结束时弹出提示，用例也可能过去。

视觉操作可以单独交给模型

画布里的卡片如果只画在 Canvas 上，就很难直接拿到卡片的 DOM 元素。有视觉能力的工具能看截图，按目标位置完成拖拽。以 Midscene 为例，可以让模型规划几步操作，也可以在固定脚本里只把定位这一步交给模型。后者的好处是失败时能知道卡在定位、拖拽还是保存。

我会保留独立的结果检查。适合用于回归的版本，大致是这样的。

动作 验收信号
放置卡片 应用公开的可读状态中出现卡片标识和预期位置
提交保存 对应这次操作的请求完成
刷新并重开 从服务端重新读到同一个卡片标识和内容

没有接口可用时，也可以验证重开后的稳定 UI 状态。核心是让断言覆盖用户真正依赖的行为。坐标容差、等待条件、是否允许空结果，都要先从产品规则里找依据。

修测试的时候留住失败条件

Agent 看到按钮改名，可以去改定位器。遇到刷新后卡片消失，它可以补日志和 trace，我会先看是不是保存真的退回了旧状态。把刷新回读删掉，或者把定位失败改成跳过，也能让报告变绿，但下次它就抓不到这个问题了。

日常 CI 我会先用确定性脚本跑普通 Web 页面。遇到确实难以稳定定位的画布，再把那一步交给视觉模型。如果要加入发布门禁，我会在本地故意关掉保存，看这个用例能不能失败。能抓到这个反例，再把它留在回归里。
