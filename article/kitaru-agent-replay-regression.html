用 Kitaru 把一次 Agent 失败变成回归测试

听白2026-11-25 约 2 分钟 近 30 天阅读 评论

一次 Agent 失败留在日志里，可以用来排查。把当时的输入、预期动作和检查条件固定下来，下一次改提示词时，就可以拿它做回归测试。这里用 Kitaru 的公开退货客服示例讲一下这个过程。

先明确失败在哪里

官方退货示例给行李订单设了 200 美元的人工审批门槛。沿用这个规则，构造一条 280 美元的退款请求来说明检查方式。要检查的是 Agent 有没有直接调用退款工具，以及它有没有把请求转给人工。只扫一眼回复里的措辞，容易漏掉已经发出去的工具调用。 Kitaru 退货 Agent 教程

我会把检查条件写到可观察的动作上。对于这个样本，超出审批门槛后，应该出现转人工的动作，退款工具调用应当为空。正常退货也要留一条。如果修改后所有请求都转人工，超额退款可能消失了，原本能正常完成的请求也受到了影响。

重放时让外部条件可比

Kitaru 会重新运行 Agent。支持历史工具回放的适配器可以用原记录里的工具结果回答同样的调用。比如订单查询仍返回原来那份示例订单，模型再根据输入和提示词做一次决定。模型这次怎么选，正是我们要看的。 Kitaru 重放文档

记录的工具名和参数对不上时，重放策略决定接下来怎么走。如果这轮只想检查决策，我会明确设为只用基线记录。出现未记录的工具调用时，让重放停止，再查看新调用为什么出现。按官方文档，省略工具策略可能执行真实工具。不同适配器支持的策略也有差异，运行前需要确认。 Kitaru 工具策略

找一组能区分好坏的样本

我会先用未修改的版本做一次基线重放，看看这次是否还能重现原来的问题。基线本身跑不出原来的行为，后面就很难解释候选版本为什么看起来通过了。

接着只改一项，例如在提示词里把人工审批条件写清楚。候选版本仍使用同一组样本和判断条件。看结果时逐条对照超额样本、原本通过的样本和发生变化的工具调用。这一步能查出改动是否修了目标问题，以及有没有把正常流程一并挡掉。

这篇用的是官方示例。固定工具返回的重放适合比较模型判断。需要验证真实接口超时、权限或连接配置时，再用受控环境跑一次实际调用，把结果单独记录。
