回放报告写着“已转人工”时，我会再看一遍工具调用。假如 Agent 先尝试退款再转人工，最后一条回复就会漏掉前面的动作。Kitaru 可以把这个判断固定到同一组输入里，改完提示词再查一遍。

先明确失败在哪里

Kitaru 的公开退货示例把行李订单的人工审批门槛设为 200 美元。沿用这个示例规则，构造一条 280 美元的请求。它通过的条件有两个。Agent 没有调用退款工具，并且成功把请求转给了人工。Kitaru 退货 Agent 教程

检查时，退款工具调用失败也要算在尝试退款里。否则，业务接口碰巧拦住了调用，测试却会误判 Agent 遵守了审批要求。以下用三组构造的工具事件演示这个检查，字段名也为示例自定。

def passes_over_limit(events):
    tried_refund = any(e["tool"] == "refund" for e in events)
    handed_off = any(
        e["tool"] == "escalate" and e["succeeded"]
        for e in events
    )
    return handed_off and not tried_refund

refund_failed = {"tool": "refund", "succeeded": False}
escalated = {"tool": "escalate", "succeeded": True}

assert passes_over_limit([escalated])
assert not passes_over_limit([refund_failed, escalated])
assert not passes_over_limit([])

这段只检查超额样本。回归集里还要留一条符合直接退款条件的请求，单独检查它仍能完成退款。否则，把所有人都转人工也可能通过超额样本。

重放时让外部条件可比

先重放基线，确认在同一组输入和工具策略下能重现目标问题。再只改一项，例如提示词里的人工审批条件。候选版本沿用这批样本和判定条件，两次都看完整的工具调用记录。

Kitaru 可以让支持历史回放的适配器按工具名和参数查找记录，并用历史结果回答匹配的调用。Agent 会重新运行并作决策。建议显式设置工具策略，省略策略时可能执行真实调用。Kitaru 重放文档

下面这份策略只用基线记录，查询不到匹配调用时停止。使用前要确认当前适配器支持这项配置，且本轮需要重放的工具未被配置为真实调用。

{
  "default": {
    "type": "history",
    "scope": "baseline",
    "on_miss": "fail"
  }
}
