DeepSeek-Harness上手实测-它把Agent做成了一棵插件树

我在一个本地目录里执行了下面这条命令。

npx -y @deepseek-ai/dsh web

终端跑完以后，浏览器打开 http://127.0.0.1:3080，一个带工作区、对话、文件浏览和运行轨迹的 Agent 页面就起来了。本次实测版本是 0.1.0-rc.6。

我给它的任务很简单。只读两份文件，分析它们之间的关系，不要修改任何内容。DSH 最后用了 1 个 Turn、2 个 Step，读取 2 个文件，没有产生文件变更。模型调用耗时 12.9 秒，首个 Token 平均等待 3.3 秒，输出速度 127 tok/s。

这些数字受模型、网关、上下文和任务大小影响，不能当成通用性能成绩。我更在意另一个结果。切到轨迹页面以后，系统提示、用户输入、运行时上下文、模型回复、工具参数和工具结果都排在同一条时间线上。

很多代码 Agent 会告诉我任务完成了。DSH 还把它如何完成这件事摊开给我看。

Harness 管的事情比聊天多

模型能生成代码，也能判断下一步应该读文件还是跑命令。可它单独完成不了一个持续执行的任务。

真正运行起来，还要有人准备上下文，把工具说明交给模型，执行模型发出的调用，再把结果送回下一轮。中间还会碰到权限、超时、重试、会话保存、环境隔离和任务恢复。

这套连接模型、工具、环境和执行循环的系统，就是 Harness。

DSH 的做法很明确。底层使用 Cordis 管理插件的加载、依赖和卸载，模型适配、Agent 循环、文件系统、Shell、会话、存储、沙箱和 Web UI 都作为插件运行。启动一个 Profile，等于加载一棵按配置组合出来的插件树。

这里有三个常见配置概念。

Bundle 负责分发一组能力。Profile 决定本次启动加载哪些 Bundle。Patch 用来覆盖其中的插件配置。开发者可以用同一套源码组合出日常编码、只读审计、模型评测或企业内网版本。

一次任务内部又分成 Turn 和 Step。用户发出一条消息，会开启一个 Turn。模型请求一次并处理相应工具调用，算一个 Step。模型读完工具结果还要继续工作，同一个 Turn 里就会出现下一个 Step。

这个循环里的关键动作都留有事件入口。插件可以在模型请求前补上下文，可以在工具执行前做权限判断，也可以在执行后记录耗时或整理结果。很多原本只能写进 Prompt 的要求，到了这里可以变成确定的程序行为。

会话记录也是运行记录

DSH 会把用户消息、模型输出、工具调用、工具结果以及 Turn 和 Step 的边界，依次追加到会话事件中。

官方设计里有一条重要约束。模型看到的内容，应当能够从这份事件记录中重建。轨迹页面就是这份记录的一种展示方式，会话恢复、分叉、回放和遥测也能沿用同一份事实。

这对 Agent 测试很实用。

最终答案错了，可以继续检查上下文有没有进入请求，模型选了什么工具，参数是否正确，工具返回了什么，Agent 收到结果以后有没有继续。只保存用户问题和最终回答，通常分不清这些问题。

我这次任务的输入达到 43.4K tokens，最终输出 793 tokens。任务本身只要求读两份文件，输入量已经包含系统提示、工作区规则、Skills 和其他运行上下文。准备正式评测时，我会把任务所需内容和 Harness 附加内容分开统计，否则很容易把模型成本都算到任务头上。

DSH 里的插件到底是什么

传统软件里的插件，常见作用是增加一个命令、按钮或导入格式。DSH 的插件范围要大得多，它是一个可以被 Cordis 加载和卸载的运行单元。

最小插件只需要导出一个 apply 函数。

import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] loaded')
}

实际插件还会声明自己依赖哪些服务、接受什么配置，并在 apply 中注册工具、服务或事件监听器。依赖满足以后插件才会加载，依赖消失时它会卸载，相关监听器、工具和定时器也会跟着清理。

所以 DSH 里的插件和模型工具不能画等号。工具是模型可以主动调用的一项能力。插件可以注册工具，也可以完全待在模型背后，负责存储、权限、日志、界面或 Agent 循环。

我在本地设置页看到的插件配置包括终端、Agent 循环、网页搜索和 Web UI。这些都是当前 DSH 如何运行的组成部分。

为什么需要这么重的插件设计

Agent 运行环境的变化很多。

文件可以放在本机、容器或远程虚拟机。命令可以直接执行，也可以先过审批。模型可能来自 DeepSeek、其他云服务或企业网关。会话可以存在本地文件，也可以进入数据库。不同团队甚至会采用不同的停止条件和重试方式。

这些差异全部写进主程序，每增加一种部署方式都要改核心代码。版本升级以后，私有修改也要一直跟着维护。

DSH 把变化拆到插件里。需要换模型就替换模型适配器，需要换执行环境就替换文件和进程 Provider，需要加审计就监听统一的工具事件，需要做另一种 Agent 循环就替换循环插件。上层工具和 Web 页面可以继续使用原来的服务接口。

它带来的自由度很高，配置难度也会跟着增加。插件多起来以后，依赖顺序、配置覆盖、事件优先级和版本兼容都要有人管理。准备放进稳定环境时，至少要固定版本，保存最终生效的配置，并用一组真实任务做升级回归。

插件具体能做什么

我把常见用途归成几类。

模型适配插件负责接入新的协议、认证方式和流式响应。工具插件可以让模型查询数据库、运行测试或创建工单。文件、Shell、终端、沙箱和存储 Provider 决定任务在哪里执行。Prompt 与上下文插件负责加入项目规则、Skill 和当前任务信息。

控制类插件可以拦截模型请求和工具执行，用来做审批、重试、限流和停止判断。会话插件负责记录新的持久事件，并从历史记录恢复状态。Web 插件可以增加设置页、命令和工具结果的展示。后台任务插件则适合长时间测试、批量处理和定时任务。

一项需要长期替换的能力，通常会拆成三个角色。

Service Definition 定义稳定接口。Provider 给出本地、容器或远程实现。Consumer 使用这个服务，并可能把它包装成模型工具。

以 Shell 为例，模型看到的 Bash 工具只依赖 Shell 接口。命令最终跑在本机还是远程沙箱，由 Provider 决定。换执行位置时，Bash 工具不需要重写。

这种拆法适合模型、文件系统、进程和存储等通用能力。一个只做简单查询的业务工具，直接注册成工具插件往往就够了，没必要预先拆成多个包。

图片输入要同时接通几处

DSH 支持在 Web 页面添加图片，视觉模型接入却不是安装一个名为“视觉”的插件就结束了。

图片先进入附件和会话事件，模型配置要声明自己接受图片，LLM Provider 要能把图片转换成对应协议，最后的模型端点也要真的支持视觉输入。

自定义 Provider 可以按模型声明输入类型。

llm-pi-ai:
  providers:
    vision-gateway:
      apiKeyEnv: VISION_API_KEY
      api: openai-completions
      baseURL: https://vision.example/v1
      models:
        - id: vision-preview
          input: [text, image]

同一个网关可能同时提供文本模型和视觉模型，逐个模型声明会更稳妥。这里的 input 只是一项配置声明，不会给纯文本模型增加视觉能力。

端点已经兼容现有协议时，配置 Provider 和模型模态就能接入。端点采用私有请求格式时，还要开发 LLM Adapter 插件，负责认证、图片消息转换和流式响应。Web 附件、会话事件、模型声明、适配器和真实视觉端点都接通以后，图片任务才算完整可用。

我用当前文本模型拖入一张图片并发送，页面在请求发出前提示当前模型不支持图片。这个结果说明 DSH 会先检查模态，明显不兼容的请求不会继续交给 Provider。

接入视觉模型以后，还应继续检查四件事。图片有没有写入会话事件，Provider 有没有收到正确格式，轨迹页面能不能还原这次输入，会话恢复以后附件还能不能使用。页面能选图片，只能证明入口存在。

本地启动和模型配置

DSH 当前要求本机有 Node.js 和 npm。最快的方式是在准备作为工作区的目录里启动。

cd /path/to/workspace
npx @deepseek-ai/dsh web

第一次进入页面后，打开左下角设置，再进入模型页面。选择 DeepSeek Provider，填写 API Key 并保存。回到新会话，选择模型和工作区，就可以开始任务。

企业网关或其他 OpenAI 兼容服务可以通过自定义 Provider 接入。需要填写稳定的 Provider ID、Base URL、API 协议和模型 ID。Provider ID 会进入请求、会话和凭据引用，保存后最好不要直接改名。

如果服务支持兼容的模型列表接口，可以从页面拉取模型。接口不兼容时手工填写模型 ID 也能使用。修改模型配置后，下一次请求就会生效，一般不用重启 DSH。

从源码启动适合准备开发插件的人。

git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web

DSH 还提供标准、PTC、极简和创造四种模式。标准模式适合日常文件和代码任务。PTC 会让模型生成一段 TypeScript 来组合多步工具调用。极简模式只保留 Bash 和文本编辑器，适合减少工具差异后比较模型。创造模式加入运行时检查和插件实验能力，更适合研究新的 Agent 组合。

放到同类 Harness 中看

Harness 这个词覆盖的产品范围很宽。有些项目专注可改造的 Agent 运行时，有些已经做成完整编码产品，还有一些主要解决远程执行和多个 Agent 的管理。

我按五种常见场景看了 DSH、Pi、OpenCode、Gemini CLI、OpenHands、Claude Agent SDK 和 Codex。除了 DSH 的本地流程，其他产品的判断来自各自官方文档与开源仓库，下面不把它们写成同条件性能成绩。

想直接处理日常代码任务

Codex、Claude Code、OpenCode 和 Gemini CLI 的完成度更高。终端、IDE、权限、项目操作和账号体系已经连在一起，安装后可以把注意力放到代码结果上。DSH 也能编码，但它当前更像供开发者继续装配的运行时。

想在多个模型之间切换

OpenCode 和 Pi 提供了很宽的模型选择，使用入口也更成熟。DSH 同样支持目录 Provider、自定义适配器和兼容端点，优势在模型适配器与其他运行能力可以一起替换。Gemini CLI 主要围绕 Gemini 和 Google Cloud，适合已经使用 Google 模型、搜索和 Vertex AI 的团队。

想把 Agent 嵌入自己的产品

Pi 提供 TypeScript SDK、RPC 和 JSON 事件流，核心很小，放进 IDE 或内部工具比较直接。Claude Agent SDK 可以在 Python 和 TypeScript 应用里调用 Claude Code 已有的文件、Shell 和 Agent 循环。DSH 也有 Headless 和 SDK 入口，更吸引人的部分仍是插件树与配置组合。

想管理远程任务和多个 Agent

OpenHands Agent Canvas 更接近控制中心。它能连接本机、Docker、VM 和云端 Backend，也能用定时任务、Webhook、Slack、GitHub 与 Linear 发起自动化。DSH 关注的是一个 Agent 内部如何运行，两者解决的问题层级不同，也可以组合使用。

想研究或改造 Agent 的执行过程

这是 DSH 最有辨识度的场景。模型请求、工具过程、会话存储、执行环境和 Web UI 都能进入插件树，轨迹又提供了统一的观察入口。Pi 也很适合做小型、透明的运行时实验。DSH 的配置组合更完整，Pi 的嵌入接口更直接。

选择这类产品时，功能数量很难直接说明好坏。日常编码看完成任务的稳定性，企业接入看模型、权限和数据去向，平台研发看扩展边界，评测工作则看轨迹能否复现。先把当前缺的那一层找准，产品差异会清楚很多。

现在还适合保持一点距离

DSH 目前仍是 Developer Preview，官方明确提醒后续会有破坏性变化。配置格式、包名和扩展接口都可能调整。它适合研究、验证和受控试用，还不适合在没有版本锁定与回归测试的情况下替换稳定系统。

本地优先也不代表所有数据都留在本机。调用外部模型、网页搜索、MCP 或第三方插件时，相应内容仍可能发送到外部服务。Agent 还能读写工作区并运行命令，测试陌生仓库时应限制挂载目录、网络访问和凭据权限。

从 Git 安装 TypeScript 插件也要谨慎。插件可能在安装阶段执行构建代码，这段代码不受 Agent 运行沙箱保护。准备长期使用时，我会优先选择可审查的源码，固定 Commit 或安装已经构建好的包。

我下一步最想做的，是给 DSH 写一个最小测试工具插件，再把文件和 Shell 从本机 Provider 换到容器里。等这两步跑通，才能更准确地判断这棵插件树在真实项目里有多好改，以及配置开始变复杂以后要付出多少维护成本。
