主题：项目实战

从需求分析中可以看出，业务基本上是围绕着「产品」的

  • 订单中的伴手礼是由多个产品组成

  • 库存中的入库和出库也都对应某一个产品

产品应用

创建产品应用

python -m manage.py startapp product

INSTALLED_APPS = [

编写产品表结构

编写通用表结构

在全部业务相关的表中有几个通用的字段

  • 主键

  • 创建时间

  • 更新时间

  • 是否逻辑删除

提取到backend/utils/models.py

from django.db import models


class BaseModel(models.Model):
    """
    基类，公共字段
    """
    id = models.AutoField(verbose_name='id主键', primary_key=True, help_text='id主键')
    c_time = models.DateTimeField('创建时间', auto_now_add=True)
    u_time = models.DateTimeField('更新时间', auto_now=True)
    is_delete = models.BooleanField('逻辑删除', default=False)

    class Meta:
        # 抽象类，用于继承，迁移时不会创建
        abstract = True

使用abstract = True后这个表结构就是一个表结构的基类了，其他表的创建就可以继承它了

产品表结构

产品包含了

  • 货品编码

  • 类别

  • 品牌

  • 品名

  • 产品单价

  • 样图

  • 备注

from django.db import models
from utils.models import BaseModel


class Product(BaseModel):
    product_id = models.CharField('货品编码', max_length=200, unique=True, help_text='货品编码')
    category = models.CharField('类别', max_length=40, null=True, blank=True, default='', help_text='类别')
    brand = models.CharField('品牌', max_length=100, null=True, blank=True, default='', help_text='品牌')
    name = models.CharField('品名', max_length=100, null=True, blank=True, default='', help_text='品名')
    price = models.DecimalField('产品单价', max_digits=10, decimal_places=2, default=0, help_text='产品单价')
    sample_png = models.CharField("样图", max_length=500, null=True, blank=True, default='', help_text='样图')
    desc = models.CharField('备注', max_length=1000, null=True, blank=True, default='', help_text='备注')

    class Meta:
        db_table = 'tb_product'
        verbose_name = '产品信息'
        verbose_name_plural = verbose_name

    def __str__(self):
        return self.product_id

产品序列化器

  • 创建时间这个字段在新建的时候不需要暴露，只有查询的时候才用到，所以使用read_only

  • 逻辑删除字段是内部使用的，对外删除了就不可见了，所以暴露字段的时候排除is_delete

from rest_framework import serializers
from product.models import Product


class ProductModelSerializer(serializers.ModelSerializer):
    class Meta:
        model = Product
        exclude = ('is_delete',)
        extra_kwargs = {
            'c_time': {
                'read_only': True
            }
        }

产品视图

from rest_framework.viewsets import ModelViewSet

from product.models import Product
from product.serializers import ProductModelSerializer
from utils.pagination import TenItemPerPagePagination


class ProductViewSet(ModelViewSet):
    queryset = Product.objects.filter(is_delete=False).order_by("-c_time")
    serializer_class = ProductModelSerializer
    pagination_class = TenItemPerPagePagination

  • 对外展示的时候排除被逻辑删除的数据，也就是is_delete=False

  • 排序根据创建时间倒序

阅读视频文字稿

原文建立产品模型，让订单和库存引用同一条产品。

我们画一张虚构产品主卡，上面是名称黄色纸舟、类别折纸和一个课堂标记；再画两张别的业务卡，一张入库、另一张订单明细。

重点不是写安装或数据库程序，而是弄清楚哪份资料描述同一个对象，哪些字段只在某件业务事情发生时才有意义。

两张业务卡都连同一份产品主记录，但入库数量五和订单数量二不一样。

它们都不应当被放在一个叫产品数量的共用字段里。

假如又有一张颜色相同、材质不同的纸舟卡，近似名称也不代表同一个对象。

用稳定引用与清晰的记录范围区分，可以避免一次名称编辑使原来的对应关系突然找不到。

如果主卡从黄色纸舟改名金色纸舟，某些列表可显示当前名；若订单需要保留交易当时的展示或成交价，应当按业务规则留自己的记录。

这不与共享元数据矛盾，因为当前价格和当时成交价本来就在回答不同问题。

不能因为产品有一个计价字段，就把旧单按新价覆盖。

哪一列要随主卡更新、哪一列不能动，最好事先写清。

桌上若拿走那张主卡，库存行里写的五件仍是记录过的数量，但已没有能核对的产品说明。

报告可以标明引用待核对，而不是选一张最像的卡代替。

也要想清楚产品退场时历史订单需要继续可读。

这里不做真实删除或修改，只比较元数据变化和引用缺失可能让读者看到什么。

让同伴换掉主卡上的名称，再分别读库存行和订单行。

若他知道引用没变、数量还各归各处，便理解这份模型最有用的区分。

最后临时拿走主卡，检验报告是否能如实说资料缺失。

产品字段集中不是为了复制少一点，而是让业务对象拥有清楚的共同指向，同时避免把不同时间和场景下的事实挤成一份。
