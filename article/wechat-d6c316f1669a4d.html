安装

npm install -g @qwen-code/qwen-code

配置

export OPENAI_API_KEY="sk-你的key"
export OPENAI_BASE_URL="你的大模型地址"
export OPENAI_MODEL="qwen3-coder-plus"

接入MCP

https://github.com/QwenLM/qwen-code/blob/main/docs/cli/tutorials.md

在项目路径下新建 .qwen/settings.json

以StreamableHTTPClientTransport类型MCP为例

{
    "mcpServers": {
        "tools": {
            "httpUrl": "http://saas-help-mcp-dev.k8s-qunhe.qunhequnhe.com/tools-mcp",
            "timeout": 30000,
            "trust": false
        }
    }
}

其他更多配置参考：https://gemini-doc.haleclipse.de/zh/tools/mcp-server.html

qwen3-coder-plus 在本文示例中的计费说明：按输入量采用阶梯单价。

简单计算一下本次消耗

  1. 确定价格阶梯:

    • 输入 Token 数为 257,519，超过了 256,000 (256K)，因此属于 256K～1M 这个价格区间。
    • 根据该区间，输入价格为 0.01元/千Token，输出价格为 0.1元/千Token。

  2. 计算输入费用:

    • 输入费用 = (输入 Token 数 / 1000) * 输入单价
    • 输入费用 = (257,519 / 1000) * 0.01 = 257.519 * 0.01 = 2.57519 元

  3. 计算输出费用:

    • 输出费用 = (输出 Token 数 / 1000) * 输出单价
    • 输出费用 = (8,301 / 1000) * 0.1 = 8.301 * 0.1 = 0.8301 元

  4. 计算总费用:

    • 总费用 = 输入费用 + 输出费用
    • 总费用 = 2.57519 + 0.8301 = 3.40529 元

本次 qwen3-coder-plus 模型调用按上述示例单价估算的总费用为 3.40529 元。

阅读视频文字稿

文章围绕 Qwen3 Coder 的自主编程视角。

本集不判断今天的模型规格、排行或可用能力，只问一个工程问题：助手说已经修好了，读者凭什么相信。

虚构展签工具在空标题时应显示未命名。

助手可以提出检查思路，但计划不等于调用，调用也不自动等于结果符合。

我们会在纸面把建议、证据和人工确认放在各自的位置。

拿一张合成计划卡，写准备比较两种输入。

这只说明拟做什么。

再拿一张纸，写已经启动检查，也不说明得到最终结果。

课堂的另一张合成证据明确说空标题显示未命名，普通标题仍保持。

把这张证据与同一轮需求绑定，才有理由说覆盖了两种情况。

如果没看到这张纸，就要说没有证据，不让语言流畅代替结果。

假如本轮只有普通标题的假检查通过，空标题究竟显示什么还不能推断。

反过来，一条合成失败也要记清是哪个输入、期望值与实际值。

验收范围先写清，可以防止助手用唯一的成功给整个工程背书。

即使另一批有同名验证，检查结果也要能对回本次的改动与条件，而不是拿上次的绿灯填当前空缺。

本片不调用任何模型或工具，只画假工作流。

假如读者发现验证只覆盖两个简单分支，应该保留未经检查的边界。

结果有用也不能让助手自行扩大任务范围，比如去访问外部项目。

建议和动作的边界，从一开始就要说得清楚。

用一个合成例子就能检查：相关证据是谁给的，出自哪一轮，人工最后是否真的完成复核。

结尾让同伴拿走空标题的结果纸，再读助手总结。

如果总结依旧说两项都确认，就把未知写成了事实。

哪怕是更有能力的编程助手，交付仍需要能指出改动对应的要求和实际验证范围。

文章的历史描述不应当作今日规格。

真正可转移的是这条习惯：先找与本轮同一条件的证据，再作测试结论，不抢在看见证据前宣布完成。
