主题：测试平台与工具

我们如何让 AI 测试用例从"能用"变成"好用"

记录了一个 AI 驱动的测试用例设计 Agent，从 MVP 到生产级闭环系统的完整演进路径。

起点：我们要解决什么问题

测试用例设计是质量保障的核心环节，但实际工作中常面临几个痛点：

  • • 覆盖不全：依赖 QA 个人经验，容易漏边界和异常场景
  • • 格式不一：不同人写的用例结构差异大，复用和评审困难
  • • 耗时长：一个中等复杂度的需求，从读文档到完成用例设计可能要一整天

我们的目标很明确：让 Agent 读取需求文档、设计稿、代码和项目知识，自动生成结构化的测试用例，并以脑图形式交付，支持人工审阅和增量修改。

演进主线概览

整个演进可以分为五个阶段，核心脉络是从"生成一段可被前端解析的脑图数据"，逐步变成"读取需求 → 策略规划 → 脑图交付 → 回读校验 → 按缺口补齐"的闭环测试设计系统。

下面逐版本展开。

v1：基础生成与脑图工作区

做了什么

确立了 Agent 的基本定位：从知识库文档、需求管理平台、设计工具、代码仓库和用户描述中获取需求，再生成标准化测试用例。

架构上以系统提示词为主，配合格式规范技能和代码分析技能提供规则与能力。

起步阶段的交付方式是"文本生成"：Agent 在回复中输出脑图 JSON，前端从聊天内容中提取并加载到编辑器。随后很快接入脑图操作工具集，能够读取、加载、追加、更新、删除、移动节点。测试用例生成就从"输出数据"变成了"操作编辑器"。

关键架构决策

决策一：交付对象从聊天内容迁移到脑图

这看起来是个小变化，实际上影响很大。Agent 的输出目标从"一段让人看的文本"变成了"一个可编辑的结构化文档"。这意味着：

  • • 用户可以在 Agent 生成的基础上继续修改
  • • Agent 可以回读已有内容，做增量操作
  • • 用例的结构可以被程序化校验

决策二：会话化与状态持久化

Agent 开始接收会话标识，脑图工具能够基于会话读取真实数据，同时接入状态检查点保存对话状态。这解决了多轮对话中"Agent 忘了之前生成了什么"的问题。

这阶段的不足

v1 不是一个质量闭环版本。它解决的是"能不能生成并写入脑图"的基础问题，为后续的"可编辑、可恢复、可按规范操作"打基础。

v2：从一次生成到分模块增量交付

发现的问题

v1 阶段最突出的问题是：模型一次性写大 JSON 容易结构错、空节点多、覆盖薄。

一个中等复杂度的需求可能有 5-8 个业务模块，每个模块下有若干场景，每个场景又包含前置条件和具体用例。让模型一次生成整棵树，中间一旦出错，后面的节点都会跟着偏。

关键架构决策

决策三：生成流程拆成两步——先骨架，再填充

这个设计的核心思想是：每次写入都要有清晰边界。每个一级模块成为一个可审查的交付单元，写完后回读，发现问题再局部修正，而不是推倒重来。

决策四：标准化的节点层级结构

统一结构后，不管哪个项目、哪个模块，用例树的层级和命名都一致，方便评审和复用。

同时做了这些补丁

  • • 明确不要把"骨架、草稿、待补充"等过程词写进脑图
  • • 强制前置条件和测试用例保持父子关系，避免同层平铺
  • • 增强异常、边界、权限、安全、兼容性等覆盖要求

v3：需求资料治理与业务知识补充

发现的问题

v2 让生成质量上了一个台阶，但暴露了一个新的瓶颈：Agent 的输入质量不稳定。

早期加载全量工具和原始文档数据，容易导致：

  • • 请求体过大，模型处理慢
  • • 上下文噪声过多，模型抓不住重点
  • • HTML 富文本、设计稿数据等原始格式包含大量无关信息

同时，不同项目的测试规则不一样。内置的格式规范负责通用结构，但项目特定的业务规则、历史缺陷清单、模块约束等，没有渠道传递给 Agent。

关键架构决策

决策五：工具白名单 + 结果清洗

架构改成只加载 Agent 真正需要的工具，并对工具描述和返回结果做裁剪：

Agent 从"能接很多资料"变成了"有选择地接入资料，并把资料清理成适合推理的输入"。

决策六：运行时加载项目业务知识

引入自定义技能（Skill）机制：

  • • 用户可以上传项目业务规则包
  • • Agent 在运行时根据项目名、业务域和功能关键词，判断是否需要读取相关技能
  • • 技能支持版本管理和在线编辑，不必每次重新打包上传

这个设计的关键在于"按需加载"：Agent 不是无脑加载所有技能，而是先分析当前需求，再决定读取哪些业务知识。

引入的其他能力

  • • 代码检索工具，辅助理解实现逻辑
  • • 模型切换配置，支持按场景选择不同模型
  • • 错误参数修复中间件，提升工具调用稳定性

v4：测试经验沉淀与交付强约束

发现的问题

v3 让输入质量可控了，但 Agent 仍然是"一次性"的：上一次生成中被用户纠正的问题，下一次还会犯。

同时，生成后的交付行为不够稳定：有时 Agent 会停在方案说明阶段，有时只生成"首批用例"，有时把核心场景当完整覆盖。

关键架构决策

决策七：知识提炼——从用户纠偏中学习

引入知识提炼引擎，从历史对话中提取三类可复用内容：

关键设计：业务规则不能误入偏好。具体产品的字段、权限、状态流转等规则，应沉淀为测试模式或历史修正，而不是作为"偏好"注入到所有任务。这个区分对多项目场景至关重要。

知识注入也不是把所有历史内容塞进系统提示。测试模式和历史修正会被写入临时文件，Agent 需要按当前需求关键词检索相关片段。这让"历史经验"可用，但不会把上下文撑爆。

决策八：格式规范强制内嵌

之前格式规范作为技能需要 Agent 主动读取，但模型有时会"忘记"读取，导致格式漂移。

改为强制内嵌核心章节到系统提示中，确保每次生成都遵守基本格式。这牺牲了一点系统提示的简洁性，但换来了格式一致性。

决策九：强交付约束

在系统提示中明确写入交付边界：

  • • 读完资料必须写入脑图，不能停在方案说明
  • • 不能只给"首批用例"
  • • 不能用核心场景替代完整覆盖
  • • 不能留下空的一级模块

决策十：表格和矩阵的全量展开

专门强化了表格和矩阵需求的处理：如果用户要求按版本、平台、套餐、状态、配置项完整展开，表格单元格和维度组合就是覆盖单元，不能压缩成少量代表性用例。

v5：策略规划与质量评测闭环

发现的问题

v4 解决了经验复用和交付约束，但质量的验证仍然依赖人工。Agent 写完用例就结束了，有没有遗漏、覆盖够不够，要人到脑图里逐一检查。

同时，面对复杂需求（多版本、多平台、多角色、多套餐），Agent 缺乏一个"先想清楚再动手"的规划步骤，容易跳过某些维度的组合。

关键架构决策

决策十一：生成流程拆成四个阶段

复杂需求先读取策略规划技能，形成内部测试策略，再按格式规范执行。这避免了一上来就写用例、写到一半发现维度遗漏的问题。

决策十二：由工具结果驱动下一步操作

这是 v5 最核心的变化。之前 Agent 的行为完全由提示词驱动，质量靠提示词约束。现在变成了：

  1. 1. 写入脑图后，自动回读完整内容
  2. 2. 执行覆盖审计和质量审计
  3. 3. 如果发现缺口，读取质量补齐技能
  4. 4. 按缺口增量补齐
  5. 5. 再次审计，直到达标

质量不再只靠提示词约束，而是由回读结果、覆盖审计和质量评分共同推动。Agent 从"按提示词尽量生成好用例"，演进为"由工具结果触发下一步修正"的闭环系统。

决策十三：运行时质量门禁

引入中间件承担运行时守门职责：

  • • 读完需求却没有写入脑图 → 提醒继续
  • • 表格展开明显只生成了局部结果 → 提醒继续
  • • 质量审计分偏低 → 推动补齐
  • • 缺少关键覆盖类型 → 推动补齐

关键原则：中间件不重新编排完整流程，只在关键边界做薄提醒和拦截。避免系统提示、技能文档和中间件形成三套流程。

当前最终架构

当前架构可以概括为六层。中心是"需求理解 → 测试设计 → 脑图交付 → 质量补齐"，通用能力作为外圈增强：

闭环如何运转

自定义技能解决"当前项目有哪些特殊规则"，知识提炼解决"用户以前纠正过什么"，企业知识库解决"通用业务术语和历史材料"，脑图质量审计解决"生成结果是否真的达标"。它们共同把 Agent 从通用生成器推向带项目记忆和质量反馈的测试设计系统。

写在最后

回顾这四个月的演进，最大的体会是：AI Agent 的架构演进不是线性的能力叠加，而是在"生成质量"和"可控性"之间不断寻找平衡。

每次解决一个问题，都会暴露下一个层面的挑战：

  • • 能生成了，但生成结果不稳定 → 引入分步生成
  • • 稳定了，但输入质量不行 → 引入资料治理
  • • 输入可控了，但没有项目上下文 → 引入自定义技能
  • • 有上下文了，但不能从错误中学习 → 引入知识沉淀
  • • 能学习了，但最终质量还是得人看 → 引入自动化质量闭环

每个阶段的解法都不是完美的，但它解决了当时最紧迫的问题，并为下一阶段的演进留出了空间。

Agent 架构不在于一开始就设计得多完美，而在于能不能在真实使用中快速定位瓶颈、做出取舍、持续迭代。这也是我们把每个版本的决策和原因都记录下来的原因——下一次遇到类似问题时，至少知道哪些路走过、哪些坑踩过。
