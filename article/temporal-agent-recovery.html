Agent 任务跑到一半崩了，Temporal 怎么让它接着跑？

比如一个图片生成任务，先调用模型，再存产物，最后更新任务状态。Worker 退出后从头跑，会多花一次生成费用。只从最后一步跑，又得知道模型结果是否可读，存储服务是否真的写完。Temporal 在这里解决的是进度的记录和恢复。要避免重复写入，还得看业务侧怎么处理同一次操作。

Workflow 记住步骤，Activity 执行外部动作

Workflow 是编排代码，Temporal Service 保存事件历史并协调任务，Worker 拿任务运行代码。调用模型、写文件、访问数据库这类会碰到外部系统的操作放到 Activity。Workflow Worker 接手时，按历史重新执行编排逻辑。它跑到一个已经记录完成的 Activity，可以使用保存的结果继续，外部接口不会因为这次重放再次调用。

因此，Workflow 的代码要能根据同一份历史产生一致的决策。需要时间、定时器或等待条件时，用 SDK 提供的机制。在编排代码里直接访问当前网络状态，同一份历史在不同时间可能走到不同分支。修改已经运行过的 Workflow 代码也要考虑兼容。增加一步或调整调用顺序之前，挑正在运行的历史做 replay 验证，必要时让旧历史继续由兼容版本处理。

存储已经成功，完成记录还有可能丢

最容易误解的是这段间隔。Activity 把数据写进存储，外部事务已经提交，Worker 还没把完成结果写回 Temporal。若此时执行失败，历史中没有这一条成功记录，流程可以安排重试。重试重新运行的是 Activity 代码。Temporal 知道谁还没确认完成，存储端是否已经产生文件，则要用业务数据判断。

我用 Temporal Python SDK 1.37.0 的本地测试环境验证了这一段。假模型返回固定产物。保存 Activity 把记录写进 SQLite，首轮提交后主动抛错，第二轮用同一个操作键回读。这个实验模拟的是提交后未能成功结束 Activity，并没有杀掉真实 Worker 进程。

检查项 本地实验结果
假模型 Activity 执行次数 1 次
保存 Activity 执行次数 2 次
SQLite 产物记录 1 条
Workflow 返回 原来的产物编号
用已完成历史执行 replay 成功，Activity 次数没有增加

实验中的 Workflow 用两个 Activity 分开保存执行进度。render 返回固定产物编号，store 的 maximum_attempts=2 包含第一次执行和一次重试。

@workflow.defn
class Generate:
    @workflow.run
    async def run(self, job: str) -> str:
        timeout = timedelta(seconds=5)
        asset = await workflow.execute_activity(
            render, job, start_to_close_timeout=timeout
        )
        return await workflow.execute_activity(
            store, args=[f'{job}/store', asset],
            start_to_close_timeout=timeout,
            retry_policy=RetryPolicy(maximum_attempts=2),
        )

保存动作以 job-07/store 作为操作键。数据表用这个键做主键。写入和读取发生在同一个数据库允许的事务内，第二次调用遇到同一个键，直接读到原记录。核心 SQL 是下面这两条。

INSERT INTO assets(operation, asset) VALUES (?, ?)
ON CONFLICT(operation) DO NOTHING;
SELECT asset FROM assets WHERE operation = ?;

真实业务还要检查同一个键是否匹配同一次业务操作。比如用户修改输入后重新生成，这是第二个合法请求，不能误用原操作的键。支付、邮件等外部系统还有自己的限制。要能把操作键传给下游，或者在无法确认时先做状态查询和对账。超时表示这边没拿到结果，不能据此推断下游没有执行。

重试粒度写进流程，故障时才看得出来

如果调用模型、保存产物、写业务状态都放在一个大 Activity，最后的状态更新报错，之前的动作可能都要再走一遍。按可确认的边界拆成多个 Activity，能保留已经确认的模型结果。拆太细也有成本，每增加一个步骤就要考虑超时、日志、版本兼容和错误处理。我用三个条件判断是否值得拆。中间结果能否单独查到，下一步失败会不会要重复昂贵的操作，以及这两步是否需要不同的重试规则。

单次执行的超时限定一次 Activity 能占多久，总时限要覆盖调度等待和重试。长操作如果能报 heartbeat，可以更早发现停滞，也能在实现支持时记录恢复进度。参数非法或业务明确拒绝，可以直接结束。网络超时和服务暂不可用才进入有上限的重试。用户取消后，已经发出的外部任务是否还能继续、迟到产物怎么处理，需要单独约定。

为什么我会先测一次提交后报错

现有队列如果只处理一次短任务，而且业务数据库已经有可追溯的状态和修复手段，引入 Temporal 未必划算。多步骤会跨重启、长时间等人工确认或回调，而且团队反复手写恢复流程时，才有必要评估它省了多少工作。

试点先跑最难解释的一次故障。在外部提交后、回执写入前注入失败，分别检查流程是否恢复、外部动作发生多少次、最终写入多少条记录。再加一个真实进程退出的场景，看看本地注入不能覆盖的超时与接管问题。流程结束和业务数据正确，各留一份能回查的证据。
