Agent 任务跑到一半崩了，Temporal 怎么让它接着跑？

我用 Temporal 的本地测试环境模拟了一次保存成功后报错。保存步骤执行了两次，假模型只执行了一次，数据库最后也只有一条记录。

Temporal 用历史恢复流程，数据库用同一个操作键防止重复写入。 这两件事要分别检查。流程能继续，并不能单凭这一点知道下游写了几次。

Worker 从什么地方接着跑

Workflow 描述步骤，Temporal Service 保存历史，Worker 拉取任务运行代码。模型调用、数据库写入这些外部动作放进 Activity。Worker 接到 Workflow 任务后，可以用记录重建编排状态。遇到已经记录完成的 Activity，就用历史中的结果继续。

同一份历史需要产生一致的编排决策。时间和定时等待可以用 SDK 的机制，外部网络读取放进 Activity。如果直接在 Workflow 里查网络状态，重放时可能走到另一条分支。

调整正在运行的编排前，可以拿已有历史做 replay 验证。添加步骤或调整顺序导致旧历史不兼容时，给旧流程保留能接手的版本。

数据写进去了，成功回执还没回来

外部事务已经提交，Worker 还没有向 Temporal 报告完成。这一段发生失败时，历史里看不到成功结果，服务会按重试策略再调一次 Activity。存储端已经写过什么，要从业务记录判断。

我在 Temporal Python SDK 1.37.0 的本地测试环境里，用固定产物模拟模型。保存 Activity 向 SQLite 提交后主动抛错。第二轮用了同一个操作键，读回了原来的记录。这次注入发生在代码里，实际进程退出和超时接管要另测。

Workflow 把模型调用和保存分开，maximum_attempts=2 包括第一次执行和一次重试。保存操作用 job-07/store 做主键。数据库允许事务内先写再读，第二次遇到同一个键便返回已有记录。

Temporal 两个 Activity 的编排示例 
@workflow.defn
class Generate:
    @workflow.run
    async def run(self, job: str) -> str:
        timeout = timedelta(seconds=5)
        asset = await workflow.execute_activity(
            render, job, start_to_close_timeout=timeout
        )
        return await workflow.execute_activity(
            store, args=[f'{job}/store', asset],
            start_to_close_timeout=timeout,
            retry_policy=RetryPolicy(maximum_attempts=2),
        )

INSERT INTO assets(operation, asset) VALUES (?, ?)
ON CONFLICT(operation) DO NOTHING;
SELECT asset FROM assets WHERE operation = ?;

同一次操作被重试时可以复用这个键。如果同一个键带来不同的输入，先核对它是否仍指向同一次业务操作。允许新数据覆盖旧记录之前，测试要知道哪个版本才是用户要的产物。

实际系统还要区分用户修改输入后重新提交的合法请求。这样的请求要用新的操作键。支付或发信如果由外部服务处理，先确认它能否接收幂等键。拿不到回执时也可以先查单和对账。超时只能说明这边没有及时拿到结果。

按可确认的结果来拆重试

模型生成、存产物、更新状态全写在一个 Activity 里，最后一步失败，前面的调用也可能重来。单独拆的条件可以很具体。中间结果能单独查到，重做成本较高，或者两步需要不同的重试规则。步骤越细，需维护的超时、错误处理、日志和兼容性也越多。

单次超时限制一次执行多久，总时限覆盖排队和多轮重试。长操作支持 heartbeat 时，可以报告进度并提前发现停滞。参数错误或明确的业务拒绝适合直接结束。网络故障和服务暂不可用才考虑有上限的重试。取消时还要约定已发出的任务怎么停，迟到的产物谁处理。

先跑一次外部提交后的故障

单个短任务已经有可追溯的业务状态和恢复手段，引入 Temporal 未必划算。任务需要跨重启、中间等回调或人工确认，团队经常手补状态时，再拿实际故障比较恢复成本。

试点可以从保存后报错开始。分别核对 Workflow 能否恢复、外部动作跑了几次、数据库最终有几条记录。通过以后再停止真实 Worker，验证超时和接管。两次测试分别留证，后续才知道它们各证明了什么。
