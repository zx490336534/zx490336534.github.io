Agent 任务跑到一半崩了，Temporal 怎么让它接着跑？

我查 Temporal 时，最关心它能解决哪一种中断。一个图片生成任务可能要调用模型、等待结果，再把文件存起来。Worker 在第三步前退出，服务重启后要知道前两步走到了哪里。要是从头再来，可能多花一次推理费用，也可能留下两份结果。

Temporal 会记录 Workflow 的运行事件。Worker 接手后，可以用这些事件重建流程状态。已经记录完成的 Activity 会复用历史结果。编排代码可以继续往下运行，外部调用放在 Activity 里。

先看外部动作成功、回执还没写进去的情况

用保存结果举例。Activity 把文件交给存储服务，存储已经成功，Worker 在向 Temporal 报告之前退出。从 Temporal 的历史看，这个 Activity 还没有完成。到了超时和重试条件，另一个 Worker 可能重新执行它。重放能告诉系统哪些结果已经确认，外部系统收到了什么，还得靠双方约定查证。

给每次业务动作一个稳定的幂等键，可以让重试继续处理同一个结果。比如存储服务能按任务编号和操作名称找到已保存的对象，就可以返回它的标识。每次重试都生成新编号的话，这个办法就失效了。对计费或发通知，应该先查下游接口有没有相同的去重承诺。没有的话，把可能重复的动作写清楚，再决定重试、对账或人工处理。

恢复到哪里，取决于步骤怎么拆

如果模型调用、存文件和回写状态都塞到同一个 Activity，前两步跑完后崩溃，第三步的错误就可能让整个 Activity 重试。我会先找两个容易单独取证的地方，一个是模型结果已经可读，一个是最终业务状态已更新。各自需要什么重试策略，哪些错误应该结束任务，再按实际边界拆分。

对于已经有图状态持久化的 Agent，也要先划清职责。图框架可以保存会话中的步骤，Temporal 可以管更外层的等待与恢复。同一步外部调用如果在两层都配置重试，问题出现时就很难从记录判断究竟执行了几次。

我会用一个很小的试点验收。先在存储成功、回执未写入时终止 Worker，再检查 Workflow 有没有继续、业务上有没有产生第二份文件，以及外部调用实际发生了几次。三项数据分别记录。拿到这些证据，再决定有没有必要为这个流程接入持久化执行框架。
