当 Agent 穿上了 Workflow 的外衣

最近在网上看了一些关于"数字员工"的资料，发现一个很有意思的现象：很多 Agent 的底层逻辑，本质上还是关键词匹配触发、固定 SOP 编排、工具调用链串联。

说白了，这不是在打造一个高智商的 Agent，而是在用大模型强行跑一个带点理解能力的 RPA。

看起来有"智能体"的外壳，实际跑的还是 if-else 的编排逻辑。

一个容易踩的坑：把策略写成路径

很多团队设计 Agent 时，恨不得手把手教模型第一步干啥、第二步干啥。比如做一个提测助手，会在提示词里写死：

第一步：更新需求状态为"待测试"
第二步：触发 UI 自动化测试
第三步：触发接口自动化测试
第四步：询问是否需要性能检查
第五步：汇总结果通知相关人员

为什么人会天然地把策略写成路径？因为我们过去几十年都是这么开发软件的——习惯了掌控每一个执行分支。

但这在开放任务里，就是灾难。

真实的研发场景远比 SOP 复杂。用户说"这个需求差不多了"，Agent 应该自主判断是否满足提测条件，而不是等用户说出"提测"这个关键词。提测时发现用例覆盖率不够，Agent 应该动态决定补充哪些用例，而不是执行固定的生成流程。

路径一旦写死，遇到非标场景就会崩溃。

有个跨境客服 Agent 的真实案例：Skill 规定"先查订单状态、再查物流轨迹、最后判断退换货时效"。结果客户发来长语音，要求"把破损的两件退了，剩下三件换个颜色，顺便改个新地址"——Agent 直接崩溃了。它被固定路径锁死了，不知道怎么并行处理非标诉求。

Anthropic 在官方文档里把 Workflow 和 Agent 分得很清楚：Workflow 适合步骤固定、需要绝对复现的任务；Agent 是用来处理未知和开放性问题的。你选了 Agent 的赛道，就别再用 Workflow 的思路去约束它。

好的 Agent 设计，应该定义的是三个边界：什么场景下必须触发、什么场景下绝对不要碰、什么算成功。 只要把这三个条件卡死，中间的执行路径让模型自己去规划。

路径不是资产，边界才是。

工具越多，歧义越大

另一个常见误区：给 Agent 挂了几十个工具，觉得它就成了无所不能的数字员工。

实际上，工具集本身就是模型能力上限的绊脚石。工具边界一旦模糊，模型就会陷入选择困难——该用哪个工具？该传什么参数？工具描述里的歧义会让模型在关键节点上不断猜错。

我看到过一个案例，给 Agent 注册了 20 多个工具，分布在多个团队的 MCP server 上。任何一方接口变了，主线就受影响。随着各团队不断往里加能力，工具数量还在快速增长。

当工具规模继续膨胀，真正的瓶颈就不是 Agent 的推理能力了，而是工具描述和参数 Schema 本身。

团队应该强制构建"最小完备工具集"——不是抠搜着不给工具，而是工具与工具之间零歧义，模型在关键节点上几乎不需要猜。

工具越多绝不等于能力越强。很多时候，你只是把做产品设计时的犹豫不决，粗暴地外包给了大模型。

系统性腐化：补丁越多，死得越快

很多团队维护 Agent 的日常，就是看着它犯了一个错，然后火急火燎地去提示词里加一条规则。这是一个极其典型的腐化轨迹：

第一阶段：短期补丁的迷梦。 缺啥补啥，解决单一 Bug。短期有效，系统看似可控。

第二阶段：上下文被贪婪吞噬。 补丁越来越多，Context 窗口被透支。长文本模型"Lost in the middle"的通病开始显现。

第三阶段：新旧规则开始内耗。 边缘 Case 和防错说明淹没了核心指令。规则互相打架，准确率反而下降。

第四阶段：陷入反应式修补的死局。 修好一个失败案例，暗处制造两个新崩溃。系统越来越脆弱。

有个项目实测过：在一个原本跑得不错的 Skill 里，为了防范某种极其罕见的异常，强行塞进去几个复杂 Case，结果整体准确率反而掉了十几个百分点。

更多信息，绝不等于更好的上下文。 不可维护的 Agent 是东拼西凑写出来的，而真正坚固的 Agent，是靠系统性的评测硬生生测出来的。

单点能力没站稳，别急着串联

很多团队的终极目标是把各个环节串成一条完整的流水线：需求创建自动触发动开发流程，代码提交自动触发测试，测试通过自动触发发布。

听起来很美好，但一个前提性的问题是：单个环节的能力够强吗？

如果单个环节的准确率是 80%，串联三个环节的端到端准确率是 0.8³ = 51%。每多一个环节，可靠性指数级下降。

在单点还没做到足够可靠之前，急着做全流程串联，不是在解决问题，而是在放大问题。

验证一个 Agent 的维度，不是"它有没有按我设定的顺序走"，而是：它有没有选对工具？参数传递有没有错？边界交接合不合理？

先做深再做宽。 选 1-2 个单点场景做到 90 分，链路短、价值明确。等你有了 3-5 个可靠的单点能力，串联才是锦上添花，而不是雪上加霜。

五个核心拷问

真正值钱的不是在提示词里堆砌多少步骤，而是如何设计边界。设计一个 Agent 之前，先回答这五个问题：

  1. 它的绝对触发条件和绝对排斥条件分别是什么？
     — 而不是靠关键词匹配
  2. 做到哪一步才算拿到了最终的确定性结果？
     — 而不是按固定流程走完就算完
  3. 它能调用的最小、无歧义工具集是什么？这些工具各自的雷区在哪？
     — 而不是把所有能力全挂上去
  4. 遇到事实断层时，必须去哪个 API 核验？查不到时退路在哪？
     — 而不是假设每个步骤都会成功
  5. 哪个节点必须等待人类介入确认？
     — 而不是全自动流水线

这五条不是让你照抄的句式，而是划定 Agent 活动范围的五道护栏。把这五件事想透彻了，比你写五十条操作路径要管用得多。

最后

自动化是按固定路径执行确定性任务，智能化是在不确定场景中自主决策。这两者需要的技术方案完全不同。

用 Workflow 的思路做 Agent，就像给一辆越野车焊上了高铁轨道——看着稳当，但彻底废了它翻山越岭的本来价值。

你真正要交付给 AI 的，是清晰无误的地图、互不打架的工具箱，以及坚不可摧的路标，而不是一份试图规定它怎么呼吸的死板台词本。
