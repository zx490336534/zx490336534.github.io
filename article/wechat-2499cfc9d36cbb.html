主题：质量工程

最近在做一个 AI Agent 项目的评测方案，过程中踩了不少坑，也沉淀了一些思路。

为什么 Agent 需要"体检"

传统软件测试中，不少用例有确定的预期输出，可以直接用断言检查。但 AI Agent 不一样——它的输出是概率性的，同一个问题可能走不同的路径，都能给出合理的结果。

更麻烦的是，Agent 不是"回答一个问题"这么简单。它会调用工具、路由到子智能体、做多轮交互。最终结果好不好，不只取决于"回答对不对"，还取决于"过程对不对"。

所以，给 Agent 做评测，不能只看最终答案，得看整个执行过程。

评测方案的核心思路

我们的方案是代码规则为主，AI 判断为辅。

为什么不用纯 AI 判断？因为 AI 判断有随机性，同样的输入可能给不同的分，而且成本高、速度慢。代码规则是确定性的，输入和环境相同时，判定结果可重复，适合做回归测试。

具体来说，我们设计了几类评估器：

1. Agent 路由准确性

一个 Agent 系统通常有多个子智能体，比如"户型图生成"、"渲染优化"、"设计点评"等。用户的请求进来后，主 Agent 要决定路由到哪个子智能体。

这一步错了，后面全白搭。所以第一个检查项就是：路由对不对？

判定逻辑很直接——预期路由到 A，实际路由到 B，不一致就是 0 分。

2. 工具调用正确性

Agent 会调用各种工具完成任务。我们检查两件事：

  • • 必须调用的工具调了没有？
  • • 有没有调用不该调用的工具？

比如用户说"根据户型图生成三维结构"，那"户型图生成结构"这个工具必须被调用。如果没调用，说明 Agent 没理解用户意图。如果调用了"视频生成"这种明显不相关的工具，说明 Agent 跑偏了。

3. 内容正确性

检查 Agent 的回复是否满足期望。这里有几个层次：

  • • 回复为空？直接 0 分
  • • 配置了必须包含的关键词？按命中比例打分
  • • 配置了期望答案？按文本相似度打分
  • • 什么都没配置？只检查非空

4. 意图识别准确性

检查 Agent 是否正确理解了用户意图。这个和路由准确性有点像，但更侧重于"理解"而不是"执行"。

数据怎么管理

评测数据放在 Langfuse（一个开源的 LLM 可观测平台）的数据集里。我们设计了一个同步机制：

  • • 本地维护一份 JSONL 格式的样本文件
  • • 同步时按 id 判断：新增、更新、跳过
  • • Langfuse 页面上手工补充的用例会保留，不会被覆盖

这样，维护人员既可以用本地文件批量管理，也可以在页面上临时补充用例。

每条样本包含：

  • • 用户问题（真实发给 Agent 的指令）
  • • 附件（图片、文件等，真实传给 Agent）
  • • 期望输出（预期路由到哪个子智能体、必须调用哪些工具、禁止调用哪些工具）

执行和报告

一条命令跑完全流程：

  1. 1. 读取 Langfuse 数据集里的用例
  2. 2. 逐条调用 Agent API
  3. 3. 收集响应、写入 Trace 和评分
  4. 4. 生成 HTML 报告

报告是"总览指标 + 问题表格 + 展开详情"的结构：

  • • 顶部：需优先处理的数量、需关注的数量、通过的数量
  • • 表格：每条用例的结论、最低分、问题点、耗时、Trace 链接
  • • 详情：点击展开后看完整输入、期望、输出、工具调用、评分明细

发版前的流程很简单：

  1. 1. 确认测试数据集是最新的
  2. 2. 跑一次评测
  3. 3. 打开报告看有没有红色问题
  4. 4. 有就阻断发布，没有就放行

当前方案的边界

这套方案已经能比较可靠地发现：

  • • Agent 请求失败或无响应
  • • 路由到错误的子智能体
  • • 必要工具没有调用
  • • 调用了禁止工具
  • • 回复为空
  • • 关键词没有满足

但还有一些场景覆盖不到：

  • • 回复是否真正高质量（除非样本配置了关键词或期望答案）
  • • 设计生成结果的视觉质量
  • • 多轮对话上下文是否持续正确

总结

给 AI Agent 做评测，核心思路是：

  1. 1. 代码规则优先：确定性的检查便宜、稳定、可复现
  2. 2. 过程和结果并重：不只看最终答案，还要看路由、工具调用、意图识别
  3. 3. 报告要能定位问题：不只是一个分数，要能快速找到哪个用例出了什么问题
  4. 4. 发版前必须跑：把评测变成发版流程的一部分，不是可选的

评测的目的不是证明 Agent 有多好，而是发现问题。发现得越早，修得越快。

阅读视频文字稿

想象一个用户说，请根据户型图生成三维结构。

最后一句回答写着任务已完成，很像成功。

但打开执行轨迹，却看到智能体调用的是视频生成，而不是结构生成。

两句话看起来都可以很礼貌，只有执行证据能揭示差别。

这篇文章要解决的，就是如何把过程和结果一起纳入评测。

先把确定条件交给代码。

比如指定的子智能体是否收到请求，必调工具是否出现在记录里，不该调用的工具有没有出现。

回复内容则要分层：空回复可以直接判定，配置了必含词就检查命中，没有额外期望时，非空只能说明确实回了东西。

不要把一个非空回复，标成完整的正确性验证。

作者用本地 JSONL 管理样本，把问题、附件和期望放在同一个记录里，再同步到 Langfuse 数据集。

同步靠稳定的样本编号区分新增、更新和跳过；页面人工添的用例会保留。

这样的好处是，同一条失败在下一轮能追踪到，而不是每跑一次就变成另一份匿名统计。

评测任务读取同一批数据，逐条执行，再把响应、工具调用和评分写进轨迹。

出错时，报告里需要能展开这条用例，核对实际输入、期望和具体断言。

比如点击一条红色记录，马上就看到是必调工具没有调用，而不用先逐页翻日志。

这里的关键是结论可查，不是把整个系统的内部数据全贴出来。

代码规则擅长判断已经写清楚的期望。

可开放式回复是否真正有帮助，设计图好不好看，多轮对话持续到后面是否还记得前面的要求，文章里的这套第一层规则还不能充分覆盖。

可以另加明确的人工评审或者模型辅助判断，但要标出来它们的边界，不与确定性的工具断言混成同一种证据。

发版时先核对样本版本，再跑一轮评测，查看报告里需要优先处理的问题。

真正决定放不放行的，不是一个孤立的平均分，而是哪些关键样本失败、失败在哪一步。

问题修完，回到同一条样本再跑，并补上覆盖到的边界。

这样报告从展示成绩，变成能复查的交付工具。
