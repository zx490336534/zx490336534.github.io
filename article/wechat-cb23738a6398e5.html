主题：Agent 架构与开发

背景

LangChain是一个强大的框架，可以帮助开发者更高效地构建基于大型语言模型（LLM）的应用。在实际开发中，我们常常希望模型的输出不是一段纯文本，而是结构化、格式化的数据（如JSON、表格等），以便下游进一步处理。

一、为什么需要格式化输出？

  • 结构化数据易于处理
    可以直接转换为数据库记录、前端展示等。
  • 方便后续逻辑判断
    如根据意图分类或信息抽取结果做不同操作。
  • 提升交互体验
    让用户或系统能更好地理解和利用LLM的输出内容。

二、LangChain中的输出解析器（Output Parser）

https://python.langchain.com/api_reference/core/output_parsers.html
LangChain提供了多种内置的OutputParser，也支持自定义。常用的有：

  • StrOutputParser
    ：直接返回字符串（默认）
  • JsonOutputParser
    ：解析JSON格式内容

三、代码实战——让LLM返回JSON格式的测试用例

1、安装依赖

pip install -U langchain langchain_core langchain-openai openai pydantic

2、使用LangSmith观察结果

https://smith.langchain.com/

3、编写想要输出的 JSON 格式

from pydantic import BaseModel, Field  

class TestCase(BaseModel):  
    Method: str = Field(description="测试方法名称,例如：等价类划分、边界值分析、场景法、状态转换、安全测试、性能测试 等")  
    caseDesc: str = Field(description="用例描述")  
    caseStep: str = Field(description="用例步骤")  
    expectResult: str = Field(description="用例预期结果")

4、拼接提示词

from langchain_core.prompts import PromptTemplate 
from langchain_core.output_parsers.json import JsonOutputParser

parser = JsonOutputParser(pydantic_object=TestCase)  

template = """你是一名资深测试工程师。请根据下述模块说明，使用适当的测试方法，编写完整的功能测试用例，数量不少于10条：  
模块说明: {module_desc}  
{format_instructions}  
"""  

prompt = PromptTemplate(  
    template=template,  
    input_variables=["module_desc"],  
    partial_variables={"format_instructions": parser.get_format_instructions()},  
)

5、调用大模型

from langchain_openai import ChatOpenAI  


llm = ChatOpenAI(  
    model="gpt-4.1",  
    api_key="sk-xxx",  
    base_url="https://oneapi.qunhequnhe.com/v1"  
)  

chain = prompt | llm | parser  
chain.invoke({"module_desc": "登录场景"})

五、小结

LangChain 之所以能够按照指定格式输出，核心原因就在于它对 提示词（Prompt）进行了优化和封装。

  • 优化提示词：加入具体的格式说明。
  • 引导模型生成规范结构文本/JSON等。
  • 用解析工具辅助检查/提取。
    这三步可以改善格式一致性，但不能保证每次输出都合格；调用方仍应处理解析和校验失败。

利用LangChain中的Prompt设计与Output Parser机制，可以方便地让大模型按照指定的数据结构（如JSON）返回结果，大大提升了工程效率和可维护性。在实际项目中建议优先使用Pydantic来约束数据类型，提高安全性与健壮性。

阅读视频文字稿

我们让模型生成订单测试用例，下一步要在评审面板展示标题、操作步骤和预期结果。

普通文本给人看挺好，可如果模型把标题放到最后，程序就可能提错。

原文介绍的是 LangChain 的输出解析。

先说清楚需要什么结构，再把模型结果交给解析和类型校验，而不是靠几条字符串替换猜字段。

先定义三项最小字段：标题、步骤和预期。

步骤必须是列表而不是一段拼起来的文字。

把结构要求告诉模型，收到候选输出后，先检查文本能否解析，再按数据模型检查类型和必需字段。

一个格式正确的对象，也可能没有预期结果，或者把数组写成字符串，不能因为能读取就直接给下游。

把三类输出来比对。

第一，模型输出了无法读的对象；第二，读得了却漏掉预期；第三，结构合格。

前两类都不应该被默默转成一条空白结果。

可以提示模型按照失败原因修一次，仍不符合就停住，交给调用者处理。

这个出口一旦能单独统计，你就知道问题是偶发噪声，还是契约本身经常被误解。

例如用例标题和三个字段都合格，但预期写成重复支付会成功。

模拟需求里明明写了重复提交应被阻止。

输出这一句是合法文本，所以类型校验检查不出来。

必须再核对原始业务条件，或者运行一个演示用例检查真实行为。

格式校验能拦住坏数据的形状，不能证明字段说的是事实。

可以把这几种情况都留作测试。

看看系统对坏结构会说明哪里不对，对正确结构中的错误事实会不会主动暂停，对真的通过结果能不能关联对应的需求编号。

之后更换模型、提示说明或解析方式，跑一样的样本。

你要的是稳定可用的数据入口，不是看起来像对象的一段文字。
