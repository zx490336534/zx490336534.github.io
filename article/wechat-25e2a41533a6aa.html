背景

据了解是由于设计师使用的chrome版本比较低导致

这个视频编解码方式是HEVC，标准比较新。会存在低版本浏览器不支持的情况，被降级当成了AAC音频格式来播放了

在本地使用docker进行复现&验证

环境搭建

在服务器上使用docker虚拟化出一个ubuntu系统

docker run --restart=always --name xfce -d -p 3389:3389 -e USER_PASSWORD=password -v /Users/zhongxin/docker_data/vnc:/home/chrome  soff/ubuntu-xfce-vnc 

下载chrome :https://www.chromedownloads.net/chrome64linux/

将下载到的google-chrome-stable_current_amd64.deb文件拷贝到/Users/zhongxin/docker_data/vnc中

  • 该路径为-v后的路径

使用win远程工具远程该ubuntu系统

  • 登录用户名：user

  • 登录密码：password (对应USER_PASSWORD参数)

命令行中输入:

sudo su 
cd /home/chrome 
apt-get update 
apt-get install -y -f ./google-chrome-stable_current_amd64.deb 
sed -e '/chrome/ s/^#*/#/' -i /opt/google/chrome/google-chrome 
echo 'exec -a "$0" "$HERE/chrome" "$@" --user-data-dir="$HOME/.config/chrome" --no-sandbox --disable-dev-shm-usage' >> /opt/google/chrome/google-chrome

本文视频讲解

打开或下载 MP4 ↗

阅读视频文字稿

页面能打开，播放器也在走进度，可画面一直不出来。

这篇文章记录了一次这样的排查：同一个文件，设计师的旧版浏览器能听见声音，却不能正常显示画面。

先把现象说清楚：它不是整份文件都拿不到，也不是页面上的播放按钮坏了。

声音和图像是两条独立的证据。

MP4 更像是一个盒子，里面分别装画面和声音。

案例文件的画面用 HEVC 编码，声音是 AAC。

客户端可能能解开其中一条，却不能解开另一条。

所以不要说视频被转换成了音频。

更准确的是，音轨仍可播放，而视频轨在这个环境下没有正常解码。

复现时准备同一份能稳定出现的问题文件。

记录用户的浏览器版本和系统，把同样的播放操作分别放进旧环境和对照环境。

如果用容器或虚拟机，只能说复现的是那套环境，不能自动代表用户的硬件。

同一文件在对照组能播画面，才有理由优先怀疑环境兼容性。

验证可以从三个地方取证。

先看看文件到底有什么轨道。

再观察浏览器是否拿到视频尺寸，或者是否真正出现画面。

最后把媒体请求的状态码和进度跳转记下来，排除拿不到文件或中途读不到部分字节。

一个会动的进度条，是有效证据，但只证明播放在向前走。

处理时保留原文件，再准备一份为目标环境验证过的兼容输出。

不要改个后缀就重新上传；要核对实际编码。

用同一个页面对照原样本和兼容样本，记录哪种组合有效。

新文件能显示首帧以后，还要检查音画同步和进度跳转，避免只修了刚开始播放的一瞬间。

最后留一条可复跑的回归项：这份文件有哪些轨道，在哪个系统、哪个浏览器版本出现过问题，修复样本在相同环境有没有正确显示首帧、声音和跳转。

用户反馈不能化成一句视频能播了。

换设备以后，能拿同样的样本和条件重新确认，才算留下了结果。
