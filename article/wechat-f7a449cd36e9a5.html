主题：测试平台与工具

前言

测试用例设计是软件测试的核心环节，传统方式依赖测试人员手动编写，存在覆盖不全、效率低下、难以维护等问题。本文介绍一套基于 LangChain Agent 的智能测试用例生成系统，实现从需求文档到 XMind 脑图的全流程自动化方案。

核心特色：用户通过自然语言对话即可实时控制脑图编辑器，AI 自动理解意图并执行增删改查操作，无需手动操作复杂的 UI 界面。

2.1 系统架构图

对话控制脑图工作流程：

用户通过自然语言表达需求 → AI 理解意图并调用工具 → 前端解析工具调用 → 脑图实时更新 → 用户继续对话迭代

整个过程中，用户无需点击任何按钮或菜单，完全通过对话完成所有操作。

三、核心技术要点

3.1 渐进式披露架构

借鉴 LangChain Skills 设计，按需加载完整指令：启动时只注入技能元数据（名称 + 描述），AI 调用时才加载完整文档，节省 Token 并保持系统提示简洁。

3.2 骨架 + 逐模块填充的两阶段策略

传统方式一次性生成所有用例导致响应延迟。本系统采用两阶段策略：

实现要点：

  • 阶段 1：分析需求后立即创建骨架（只含模块节点，无测试用例），前端快速显示结构
  • 阶段 2：按模块索引逐个调用 add_nodes 填充测试用例，每个模块独立一次调用

强制约束：

  1. 1. 骨架中的模块数量 N 必须等于后续 add_nodes 调用次数
  2. 2. 禁止在所有模块填充完毕前输出文字
  3. 3. 每个模块必须且只能调用一次 add_nodes

3.3 前端工具调用机制

AI 通过标准 JSON 格式调用前端工具，无需处理复杂的 UI 操作：

实现要点：

  • 工具定义：使用 LangChain tool 装饰器定义工具，返回 JSON 字符串给前端解析
  • 前端解析：TestCaseEditorLayout 使用正则匹配 AI 回复中的工具调用 JSON，解析后路由到具体操作
  • 标准格式：{ "action": "tool", "toolName": "...", "toolInput": {...} }

可用工具：

  • get_current_data：读取当前脑图数据
  • load_xmind_data：整体替换脑图
  • add_nodes：添加子节点
  • update_node：更新节点属性
  • delete_node：删除节点
  • move_node：移动节点

{
    "id": "testcase-1",
    "topic": "正常登录测试\n1. 打开登录页面\n2. 输入正确账号密码\n3. 点击登录按钮",
    "priority": "P0",
    "precondition": "用户已注册",
    "steps": "1. 打开登录页面\n2. 输入正确账号密码\n3. 点击登录按钮",
    "expected": "登录成功，跳转到首页"
}

前端自动解析：

  • steps 和 expected 字段自动生成子节点
  • priority 决定节点颜色标记（P0 红色、P1 橙色、P2 黄色、P3 灰色）

结语

本系统通过 LangChain Agent + 渐进式披露架构，实现了从需求文档到测试用例的全流程自动化。最核心的创新在于通过自然语言对话实时控制脑图编辑器，用户无需学习复杂的 UI 操作，只需用日常语言表达需求，AI 即可自动理解并执行增删改查操作。两阶段策略确保快速反馈，为测试人员提供了高效、智能的用例设计体验。

技术亮点回顾

  1. 1. 对话控制脑图：自然语言交互，实时操控脑图编辑器
  2. 2. 渐进式披露：按需加载完整指令，保持系统提示简洁
  3. 3. 两阶段策略：骨架先行 + 逐模块填充，优化用户体验
  4. 4. 多源集成：统一接口对接内部文档、内部需求管理系统、Figma、Git

阅读视频文字稿

这篇文章介绍的是一类对话式用例生成方案。

用户说一条需求，Agent 不能只回一段建议。

它要把意图变成明确的编辑操作，让脑图真正更新。

用户再提下一次修改，系统基于已有的节点继续改，而不是每次全部重写。

生成文本与修改一份测试产物，是两件不同的事情。

用文章里的一版流程来说明。

它先把需求分成模块，只把骨架展示出来，随后每个模块填完整的用例。

这样能比较早看到结构，但出现一个清单不意味着所有用例已经就绪。

反过来，如果某一模块没填完，要保留这个信息，而不是靠一条看似成功的最终回答把问题藏过去。

例如用户说，把某条用例升级成最高优先级。

Agent 应先知道目标是哪一个节点，然后发出修改该节点的结构化操作。

接收操作的编辑器按节点更新属性，用户可以看到目标变化。

验收时，还要检查其他节点没有被意外改动，这比只看回复里写了“已修改”更可靠。

文章用登录用例展示数据格式。

除了标题，还要指明前置条件、具体步骤和预期结果。

比如输入正确账号密码再提交，预期可以观察到页面进入首页，而不只写四个字“登录成功”。

最后依据业务重要性标记优先级。

这样的结构可以转成脑图节点，也便于人工回看。

文章提到可以引用需求文档、设计或代码，这提升了覆盖可能性，但不是无限推断的许可。

比如页面没说明登录失败后是否锁定账号，就不能凭经验给出固定的锁定时长。

让脑图先保留这个待确认的规则，并让用户补资料。

这样测试人员知道缺的是哪条依据，而不是被一个编得很完整的预期误导。

最后，把产物放回业务需求核对：该有的模块都出现了吗，同一条规则有没有重复或互相冲突，异常场景是不是能操作、能判断。

需要改时，先做最小的节点修改，再回看它对其他节点的影响。

文章里的价值不只是省下写第一稿的时间，更在于让需求、工具动作和测试产物有地方可以追踪。
