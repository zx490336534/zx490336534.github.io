AIHom 公司内部概念速查

这页专门解释课程里会遇到的公司内部词。读课程时如果卡在某个专有名词，先来这里查“它是什么、在 AIHom 哪条链路里出现、开发/测试时该看哪里”。

使用方式

不要把这些词当成必须背诵的理论。它们是定位代码和问题的路标：看到词，知道该去哪个仓库、哪类配置、哪条通信链路继续查。

1. 产品与工程分层

概念小白解释AIHom 中的位置开发/排查抓手
ai-home用户真正打开的 AI 设计前端。设计画布、AI 对话抽屉、2D/3D Viewer、前端工具执行。先看 package.json、src/app/App.tsx、ConversationManager、FRONT_TOOLS。
agent-conversation-sdk前端和 Agent 后端说话的协议层 SDK，不负责 UI 长相。WebSocket 建连、会话生命周期、流式消息、取消/重试、前端 MCP 工具桥。查连接状态、消息是否发出、toolCall/toolResponse 是否往返。
ai-native-serviceAIHom 的后端 Agent 服务。StateGraph 编排、模型调用、MCP 工具调度、消息/项目/权益持久化。从 SendMessageHandlerImpl、StateGraphFactory、Tool/Agent 相关类往下追。
auto-layout-serviceAI 自动布局和户型生成相关后端服务。布局任务、Processor 异步处理、选品匹配、布局图/结构化结果。看 Processor、任务状态、轮询接口、队列状态。
viewer-2d2D 户型图/平面查看器。PixiJS、Scene2D、Entity/Drawable/Selectable、2D 交互。2D 不显示、选中/拖拽异常、户型元素错位时优先查。
render-3d3D 渲染和离线出图容器。3D 场景、相机、模板、渲染任务、截图/出图状态机。3D 截图、渲染图、离线任务、iframe 同步异常时查。

2. 会话与实时通信

概念小白解释AIHom 中的位置开发/排查抓手
STOMP / WebSocket浏览器和后端之间保持一条实时双向通道。用户消息、流式回复、notification、toolCall/toolResponse 都走这里。浏览器 Network 的 WS frames，后端 socket handler，destination 获取接口。
RawSocketMessageAIHom 自己封装的 WebSocket 业务消息外壳。把消息类型、业务 key、data 包起来，让 SDK/后端识别该怎么处理。排查“消息发了但没反应”时看 key、data、requestId 是否对齐。
ProcessorMessageType消息类型枚举，告诉系统这条消息是发送、取消、通知还是工具响应。前后端消息分发的关键 switch 条件。新增消息类型时要同时看前端 SDK 和后端 handler。
会话并发锁同一用户同一图一次只允许一个活跃会话，避免 StateGraph 状态被并发写乱。graphId + userId 维度的 Redisson 锁。报 only one conversation is allowed at a time 时先查 Redis 锁 key 和 TTL。

3. Agent、工具与 MCP

概念小白解释AIHom 中的位置开发/排查抓手
StateGraph / Graph把 AI 工作流画成“节点 + 边 + 状态”的流程图。后端 Agent 编排主干，决定先理解意图、再调哪个工具、何时结束。看 graphId/version、节点构建类、条件边、状态对象。
Agent / Supervisor / HarnessAgent 是执行者；Supervisor 是路由者；Harness 是用代码兜底循环和前置校验的执行框架。架构演进从多 Agent 路由逐步收敛到单 Agent + Harness，减少“说完成但没出图”。重点看 AihomHarnessLoopStrategy 的 continue/break 条件。
MCP让大模型调用外部工具的协议。AIHom 里既有后端工具，也有必须让浏览器执行的前端工具。看 tool name、schema、执行端、tool result 是否回传。
MCP 桥接后端 Agent 需要前端资源时，通过 WebSocket 让前端执行工具。例如搜索/替换模型、3D 截图、读 viewer 状态。排查顺序：后端 toolCall → SDK MCPService → FRONT_TOOLS callback → toolResponse。
Nacos MCP Registry内部 MCP 工具注册/发现相关体系。用于管理 MCP 工具元信息、连接端点和存量服务转换方向。工具名、端点、权限、schema 对不上时，需要查注册信息和中台配置。

4. 配置、环境与基础设施

概念小白解释AIHom 中的位置开发/排查抓手
Pilot公司 Java 服务运行和部署的一套基础框架/平台约定。启动参数、环境信息、中间件版本、/_appConfig/cicd.yml。服务本地启动、环境配置、多数据源、部署差异先查 Pilot 相关配置。
toad公司配置中心，适合放环境差异配置，支持拉取、缓存和热更新。如白名单、开关、环境阶段等会随环境变化的配置。看配置 key、stage、是否热更新；Python 手册说明客户端会拉远端、写本地缓存、监听变更。
Nacos配置/注册体系，在 AIHom 中重点承载 Agent 配置。Agent、prompt、model、tool、graph 配置可能来自 Nacos。查“为什么代码没改但 Agent 行为变了”时，不能只看 Git，要看 Nacos 配置。
Redis / Redisson缓存、队列、锁。会话并发锁、异步任务排队、消息临时缓存、上下文 TTL。排查卡住、排队、幽灵锁、消息丢失时必须看 Redis key。
RocketMQ异步消息队列。部分异步持久化或跨服务异步事件。关注消费状态、重试、死信队列。

4.1 部署与运行命令

概念小白解释AIHom 中的位置开发/排查抓手
mvn clean deploy -U -DskipTests后端 Maven 构建并发布制品到远程仓库。ai-native-service 和 auto-layout-service README 都记录了该命令。它不是“启动本地服务”，而是构建/发布产物。启动还要看 IDE VM options、环境变量和 Pilot 配置。
_appconfig/cicd.ymlPilot 部署时读取的应用启动配置。后端两仓 README 都提示修改该文件设置启动参数。发布到不同 stage 前，确认 spring.profiles.active、内存参数、toad stage 是否符合目标环境。
kjl dev前端本地开发服务。ai-home 的 yarn dev 实际执行它。页面白屏先看 Console 和入口资源；联调环境看 -T 指向。
kjl dev -T ...本地前端资源对接指定目标站点。ai-home 的 yarn beta 指向 https://prod-test-seoul.example.com。适合验证“本地前端 + 环境后端”。
kjl buildai-home 生产构建。ai-home/package.json。合并前检查类型、资源、bundle 构建问题。
kjl pub:dev / kjl pub:buildpub 体系下的前端开发和构建命令。viewer-2d、render-3d 的 dev / pub-script。viewer 问题要分清是自身资源、父页面嵌入、还是 iframe/postMessage。
pub:deploy前端发布任务声明。三个前端仓库 def.config.js 都声明了 pub:deploy。具体发布动作以团队发布平台/CI 为准；课程只把它作为部署入口概念。

4.2 Coops Agent 配置与 MCP 注入

配置/代码点负责什么AIHom 证据第一排查点
Coops Agent 管理中心查看和编辑 Agent、Prompt、Model、MCP Server、Skill 配置。页面网络请求读取 agent-base.json、model.json、mcp-servers.json、agent-skill.json。先确认 region、namespace、agentName 是否正确。
agent-base.jsonAgent 描述、promptKey、最大迭代次数。Nacos group 为 ai-agent-{agentName}。Agent 行为变了但代码没变时，先查这里。
prompt-{promptKey}.jsonSystem Prompt 模板。Nacos group 为 nacos-ai-meta。路由规则、输出约束、拒答策略优先看 Prompt。
mcp-servers.json声明 Agent 直接挂载的 MCP Server、白名单 tools、headers、queryParams。当前 Ai_Home_Agent Supervisor 直接 MCP Server 数量为 0。工具不可见时看 whiteTools 是否漏配，MCP tool 是否 enabled。
state_graph / graph_nodesAIHom Graph 与 Supervisor/SubAgent 配置。查询 graph_id='graph_ai_home' 的激活图。确认当前激活 graph version、Supervisor、SubAgent、localTools。
CustomNacosReactAgentBuilder从 Nacos 加载 Agent、Prompt、Model、MCP Server，并汇总 local tools + MCP tools。build() 内调用 NacosAgentInjector、NacosPromptInjector、NacosMcpToolsInjector。看 allTools 是否包含目标工具。
CustomNacosMcpGatewayToolsInitializer解析 MCP Server 详情，按协议、白名单、enabled 开关创建 ToolCallback。支持 soa、http、https、mcp-sse、mcp-streamable、postmessage。工具加载失败时看协议、server detail、toolSpec、toolsMeta。
AgentLlmNode / AgentToolNode前者把工具定义给模型，后者在模型返回 tool call 后执行工具。ToolDefinition 给模型看的核心是 name、description、inputSchema。模型没调用工具看描述和 schema；工具调用失败看 callback 执行端。

5. 前端内部框架与 viewer

概念小白解释AIHom 中的位置开发/排查抓手
@qunhe/reactive-framework内部响应式状态框架，类似“数据变了，组件跟着刷新”。@observable、@observer、combine、connect、StateManager。UI 不刷新时看组件是否 observer/connect，字段是否 observable，manager 是否同一个实例。
KAF公司前端应用/场景框架，viewer-2d 中用于 Entity 能力注册和状态组织。Scene2D、Entity、DrawableAPI2D、RootStateManager 等。实体不渲染或交互不生效时，看 Entity 是否注册正确的 API。
iframe / postMessage页面里嵌另一个页面，通过消息沟通。ai-home 嵌 viewer-2d / render-3d。同步异常时看消息方向、type、payload、目标窗口是否正确。
PixiJS浏览器 2D/WebGL 渲染库。viewer-2d 的平面图绘制。图形不显示、层级/坐标异常时查 Pixi 容器和 Drawable。

6. 长任务、计费与质量

概念小白解释AIHom 中的位置开发/排查抓手
异步任务排队生图/布局太慢，先入队，轮到再执行，期间告诉前端排第几。Redis ZSet、Lua 原子出队、TaskQueueInfo WebSocket notification。看 queuePos/queueSize、taskId/taskType、取消状态、TTL 恢复。
CreditsAIHom 的点数/权益计费体系。按结果计费，预扣、确认、回滚；纯对话通常不扣费，有产出才扣费。排查扣费问题时看 submit/confirm/rollback 是否成对，失败是否补偿。
Langfuse / promptfooAI 调用链观测和 Agent 测评工具。用于分析 LLM 调用、token、节点表现、架构改造回归。Agent 说错、循环异常、工具没调时，用 trace/测评集复现定位。

7. Git、Kaptain 与发布分支

概念小白解释AIHom 开发中的用法注意点
Kaptain 事项号需求、任务、缺陷的唯一追踪入口，可以是数字 id，也可以是 COOAI-xxx 这类 key。建议出现在分支、commit、MR 标题中；如果只有数字 id，先查出 key 和标题再建可读分支。便于从代码回到需求背景，也便于发布和回滚追溯。
功能分支单个需求的开发分支。从团队约定基线拉出，开发完成后通过 MR 合入。不要直接推关键分支；先看近期 MR 的目标分支。
release/YYYYMMDD某个上线日期窗口的发布分支。Confluence 有自动创建 release/YYYYmmdd 的 Git 插件实践。具体日期、目标分支、合入规则以团队当期发布安排为准。
cherry-pick只把指定 commit 拿到另一个分支。适合把某几个 commit 带入 release，或复杂回滚时重建分支。必须记录 commit 来源，避免漏拿依赖 commit。
Revert用一个新提交撤销旧提交。Release 分支回滚规范建议能用 GitLab Revert 就先用。如果后续提交修改过同一内容，GitLab 自动 Revert 可能失败。
git worktree同一仓库开多个工作目录，分别检出不同分支。适合一边开发功能，一边验证 release 或处理 hotfix。不要把 worktree 建在主仓库目录里面；每个 worktree 的依赖和环境变量独立检查。
