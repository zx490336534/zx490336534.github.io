真实项目练习：批量生成与安全回退

按房间隔离进展和失败，从小范围发布到可回退。

先看场景走一遍读代码复现失败动手练习自测

先看场景

RoomLab 要一次替两个房间生成布局。当第二个失败，第一个成功不该被撤销，也不应切换全局就把成功和失败一起覆盖。

试点范围：正式扩大前允许新功能生效的一小组对象。

走一遍

  1. 将批次拆成独立房间任务。
  2. 先只发布到允许的试点房间。
  3. 分别更新成功项。
  4. 停止扩大范围并保留已确认版本。
合成示例 可折叠
versions = {"A": 2, "B": 4}

第二遍 · 把代码读懂

代码拆解

批量生成坏一个房间，怎么做到问题可止损、影响范围清楚？

调用链

  1. 每个任务携带房间与试点代次。
  2. 验证任务归属和结果。
  3. 更新成功项并留存失败原因。
  4. 关试点后拒绝旧代提交。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

versions = {"A": 2, "B": 4}
allowed = {"A", "B"}
epoch = 1

def publish(room, task_epoch, valid):
    if task_epoch != epoch or room not in allowed:
        return "blocked"
    if not valid:
        return "invalid"
    versions[room] += 1
    return "released"

assert publish("A", 1, True) == "released"
assert publish("B", 1, False) == "invalid"
assert versions == {"A": 3, "B": 4}

epoch += 1
allowed.clear()
assert publish("A", 1, True) == "blocked"
assert publish("B", 2, True) == "blocked"
assert versions == {"A": 3, "B": 4}

批次成功不等于每项成功

UI 需要展示房间粒度的状态。先决定业务是否允许部分成功；本场景允许，因为两个房间布局彼此独立。

只控制应用发布，不要倒推任务已取消

停止试点后旧任务可能仍执行。写前核对试点代次和范围，旧通知不能借此前授权继续更新。

有记录的回退更安全

本例的回退只禁止新写、保留成功数据。若业务要恢复旧版本，应为每个房间另启一次可审阅、可追踪的发布，不覆盖这次证据。

复现失败

两个房间一成一败
怎么触发：让 A 通过、B 生成坏方案。
怎么判断：只更新 A 的已确认版本，B 留在原版本。
关闭试点后迟到
怎么触发：撤销范围，再交来旧代成功结果。
怎么判断：拒绝提交，不修改已确认数据。
重发同一项
怎么触发：重复发相同业务操作。
怎么判断：在真正发布器中用上一阶段的持久幂等键去重；这段控制点不承担去重。

写下这些测试断言

  • 试点覆盖范围和任务代次必须同时匹配。
  • 失败房间不影响成功房间。
  • 停止新写仍保留已确认版本。

这一课带走：从项目验收角度同时证明两件事：允许的变更确实生效，不该发生的变更能够被挡住。

动手练习

指定仅 room-A 试点，再模拟两个房间都生成、后一房间失败和回退之后迟到旧结果。
