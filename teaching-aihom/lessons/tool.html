工具与 MCP：从发现到审批

区分工具可见、可调用和被允许写入三件事。

先看场景走一遍读代码复现失败动手练习自测

先看场景

假设 Agent 能读取房间约束和写入草稿。模型只负责提出动作，应用必须验证动作能否执行。MCP 是工具交互的一种标准接口，不代替业务权限检查。

MCP：让应用用统一方式发现和调用工具的协议。能看到一个工具，不等于有权执行它。

走一遍

  1. 明确工具的输入输出、错误类型和结果上限。
  2. 查询类工具可按只读范围执行；写入的范围和确认由应用核对。
  3. 把工具响应当成数据，不把返回文本里的命令当成授权。
合成示例 可折叠
{"tool":"read_room_rules","arguments":{"room":"sample-a"}}

第二遍 · 把代码读懂

代码拆解

Agent 看到了「保存草案」工具，也传了形状正确的参数，为什么还不一定能执行？

调用链

  1. 可用工具约定名称、入参类型和结果。
  2. 模型提出工具请求，而应用从自己的可信状态读取授权。
  3. 应用校验访问范围、参数、草案版本和确认。
  4. 工具返回结构化数据；旁白不作为新的用户授权。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

def dispatch(name, args, *, current_room, accepted, calls):
    if name not in {"read_rules", "publish_draft"}:
        return "unknown-tool"
    if not isinstance(args, dict):
        return "invalid-arguments"
    if not isinstance(args.get("room"), str):
        return "invalid-arguments"
    if args["room"] != current_room:
        return "out-of-scope"
    if name == "read_rules":
        calls.append(("read", current_room))
        return {"min_width": 1}

    draft, revision = args.get("draft"), args.get("revision")
    if not isinstance(draft, str) or type(revision) is not int:
        return "invalid-arguments"
    if accepted != (current_room, draft, revision):
        return "needs-confirmation"
    calls.append(("publish", current_room, draft, revision))
    return "published"

calls = []
args = {"room": "room-A", "draft": "sample", "revision": 4}
assert dispatch("publish_draft", args, current_room="room-A", accepted=None, calls=calls) == "needs-confirmation"
assert not calls
assert dispatch("publish_draft", args, current_room="room-A", accepted=("room-A", "sample", 3), calls=calls) == "needs-confirmation"
assert dispatch("publish_draft", args, current_room="room-A", accepted=("room-A", "sample", 4), calls=calls) == "published"
assert len(calls) == 1

这是应用边界，不是协议实现

工具协议解决发现和调用，调用前的资源身份与用户许可是应用职责。示例调用的是普通函数，用这一层模拟协议客户端发出调用前应该做的判断，不涉及外部服务配置。

每次审批要绑定到要写的内容

用 room、draft、revision 绑定确认。课例用元组表示三者一致；真实应用还要绑定发起者、允许的动作及确认有效期。处理重复写入依旧依赖上一节的幂等持久化，不由确认元组替代。

错误分得开，评测才能写得准

未知工具、参数不合法、范围错误、缺少确认产生不同结果。模型输出可能提出新的范围，也可能把工具文本当指令。dispatch 只允许预先定义的行为，不把模型文本中的判断当作可执行规则。

复现失败

模型自行声称已确认
怎么触发：参数齐全，但应用记录中没有确认。
怎么判断：返回 needs-confirmation，写工具调用次数为 0。
确认后草案变化
怎么触发：用户批准版本 3，模型提交版本 4。
怎么判断：继续要求确认，不放行新版草案。
读取别的房间
怎么触发：让读取工具携带和当前房间不相等的编号。
怎么判断：返回范围错误，即使是只读工具也不能越过资源权限。

写下这些测试断言

  • 工具未知时不发送请求。
  • 版本不匹配时没有副作用。
  • 严格匹配已确认动作后，只记录一次写调用。

这一课带走：工具在清单上不等于行动被允许；权限、参数与确认要在调用处落实。

动手练习

用两个模拟工具分别返回合法规则与越权建议，检查写操作在未确认时不会触发。
