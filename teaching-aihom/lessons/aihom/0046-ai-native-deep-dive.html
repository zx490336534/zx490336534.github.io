046 ai-native-service 深度追踪

从 WebSocket 到 Tool 调用，逐层追踪一条消息的完整代码路径

1. 完整调用链概览

当用户在前端输入消息，代码执行顺序如下：

WebSocket 消息到达
  │
  ▼
WsMessageListener              // 从 StompSendCommand 解析 RawSocketMessage
  │  根据 RawSocketMessage.key / type 分发
  ▼
SocketHandlerFactory           // 路由到对应 Handler
  │  getRequestHandler("SendMessage")
  ▼
SendMessageHandlerImpl        // 发消息处理（入口）
  │  .handleMessage()
  │  ① 解析 ClientSendMessageDto
  │  ② messageProcessService.tryLock()  ← Redisson 分布式锁
  │  ③ stateGraphFactory.getStateGraphCacheDto()  ← 加载图配置
  │  ④ 构建 MessageContext
  │  ⑤ conversationService.createConversation / addMessage
  │  ⑥ messageProcessService.handleMessage()
  ▼
MessageProcessService         // 消息处理核心
  │  .handleMessage()
  │  ① stateGraphFactory.buildCompiledGraph()
  │  ② compiledGraph.stream(inputs, config)  ← 执行状态图
  │  ③ .doOnNext(processNewMessage)  ← 流式处理每个节点输出
  │  ④ .doOnSuccess(successMessage)  ← 完成
  │  ⑤ .doOnError(errorMessage)      ← 异常
  │  ⑥ .doOnCancel(cancelMessage)    ← 取消
  ▼
StateGraphFactory             // 构建状态图
  │  buildCompiledGraph()
  │  根据图类型选择 Supervisor 或 ReAct 构建策略
  ▼
CustomSupervisorAgent         // Supervisor 路由决策
  │  根据用户意图选择子 Agent
  │  如: Floorplan_to_Design, Image_Editor, comment_AI
  ▼
子 Agent 节点                 // 执行具体任务
  │  调用绑定的 Tool
  ▼
Tool（本地/前端 MCP）         // 实际执行
  │  如: FloorplanToStructureTool, LayoutFloorplanTool
  ▼
ResponseServiceImpl          // 流式返回结果
  response / pendingResponse / errorResponse

2. 关键代码逐层解析

2.1 SendMessageHandlerImpl.handleMessage()

这是消息处理的入口方法，做了 6 件关键的事：

步骤代码作用
① 解析消息JSONUtils.copyOf(data, ClientSendMessageDto.class)从前端消息提取 graphId、graphVersion、content 等
② 加锁messageProcessService.tryLock(socketInfo, conversationUuid)Redisson 分布式锁，同一用户同一会话同时只能一个消息
③ 加载图配置stateGraphFactory.getStateGraphCacheDto(graphId, graphVersion)从缓存/数据库加载 StateGraph 配置
④ 构建上下文MessageContext.builder()...build()组装 userId、socketInfo、graphId、historyMessages 等
⑤ 保存消息conversationService.createConversation / addMessage新会话创建 + 保存用户消息到 DB
⑥ 执行处理messageProcessService.handleMessage(messageContext)进入核心处理逻辑
注意：如果最后一条历史消息是未完成的 tool call，processResponseMessage() 会自动补充一条 timeout 的 tool response，避免下次对话卡死。

2.2 MessageProcessService.handleMessage()

核心处理方法，使用 Reactor 响应式流执行状态图：

CompiledGraph compiledGraph = stateGraphFactory.buildCompiledGraph(stateGraph);

Disposable disposable = compiledGraph
    .stream(inputs.toMap(), config)          // 执行状态图，返回流
    .doOnNext(nodeOutput ->                  // 每个节点输出
        processNewMessage(ctx, nodeOutput))  // 处理新消息/流式输出
    .last()                                  // 等待全部完成
    .doOnSuccess(nodeOutput ->               // 成功
        successMessage(ctx, nodeOutput))
    .doOnError(error ->                      // 异常
        errorMessage(ctx, error))
    .doOnCancel(() ->                        // 取消
        cancelMessage(ctx))
    .subscribe();

conversationCache.put(conversationUuid, userId, disposable);  // 缓存用于取消

2.3 流式消息处理

processNewMessage() 处理两种输出：

  • StreamingOutput — 流式 token，逐字推送给前端
  • 普通 NodeOutput — 完整消息，包含 tool call/result

2.4 并发锁机制

// Redisson 分布式锁
String lockKey = "ai-home-lock:" + conversationUuid;
RLock lock = commonRedisService.getLock(lockKey);
lock.tryLock(wait=2s, lease=3s, TimeUnit.SECONDS);

// 解锁时机
// 正常完成 → cleanUpAndUpdateUsage() 中 forceUnlock()
// 异常完成 → catch 块中 unlock()
// 取消完成 → cancelMessage() 中 cleanUpAndUpdateUsage()
幽灵锁风险

浏览器刷新、网络断开、服务重启等导致清理逻辑未执行，锁会残留。只能等 3 秒 TTL 过期或手动删 Redis key。
