059 模板系统与灯光/背景管理

理解 render-3d 中模板配置、obsConfigCache 缓存、灯光样式映射、背景配置与默认回退机制

1. 模板配置的整体结构

在 render-3d 中，"模板"决定了渲染画面的灯光氛围和背景环境。每个模板由一个 obsId 唯一标识，包含灯光样式映射和背景配置两大部分。

核心状态

模板相关状态全部维护在 OfflineRenderStateManager 中，关键字段包括：currentObsId、lightStyleId、hdriBackgroundId、backgroundConfig、obsConfigCache。

模板配置的来源链路：

┌──────────────────────────────────────────────────────┐
│  实时渲染层 (StateManager/realtime/*)                │
│  维护当前实时模板的 obsId                              │
└──────────────────────┬───────────────────────────────┘
                       │ core.realtime.getCurrentObsTemplateIdList()
┌──────────────────────▼───────────────────────────────┐
│  OfflineRenderStateManager.init()                   │
│  拉 snapshotList → 取当前 obsId → 初始化灯光/背景配置    │
└──────────────────────┬───────────────────────────────┘
                       │ fetchAndCacheObsConfig(obsId)
┌──────────────────────▼───────────────────────────────┐
│  obsConfigCache                                      │
│  缓存灯光样式映射 + 背景配置                            │
└──────────────────────────────────────────────────────┘

2. obsConfigCache 缓存机制

obsConfigCache 是模板系统的核心缓存，避免同一模板反复请求后端。

缓存写入

fetchAndCacheObsConfig(obsId) 执行时：

  1. 以 obsId 为 key 检查缓存是否已存在
  2. 缓存命中 → 直接返回，跳过网络请求
  3. 缓存未命中 → 请求后端获取灯光样式映射和背景配置，写入缓存
注意事项

切换模板时必须同时检查 currentObsId、obsConfigCache、实时模板来源和默认背景回退。只改一个地方容易出 bug。

缓存结构

字段类型说明
lightStyleMapMap灯光样式 ID → 灯光参数的映射表
backgroundConfigDataObjectHDRI 背景 ID、环境光参数、地面配置等

3. 灯光样式映射

灯光样式通过 lightStyleId 控制。同一个模板可以对应多种灯光风格（如暖光、冷光、自然光），渲染时根据用户选择的 lightStyleId 从映射表中取出对应参数。

// 灯光样式映射示意
obsConfigCache[obsId].lightStyleMap = {
  "warm":    { intensity: 0.8, colorTemp: 3200, ... },
  "cool":    { intensity: 0.6, colorTemp: 5500, ... },
  "natural": { intensity: 0.7, colorTemp: 4500, ... },
}
设计要点

灯光参数不在前端硬编码，而是从模板配置动态获取。这使得后端可以独立更新灯光方案，前端无需发版。

4. 背景配置

背景配置通过 hdriBackgroundId 和 backgroundConfig 两个字段管理：

字段作用
hdriBackgroundId标识当前使用的 HDRI 环境贴图
backgroundConfig完整的背景参数（环境光强度、地面反射、天空配置等）

背景配置同样来自 obsConfigCache，与灯光样式绑定在同一个模板下。切换模板时，灯光和背景会同时更新。

5. 模板切换流程

当用户在 UI 上选择一个新模板时，完整流程如下：

用户选模板 → 更新 currentObsId → 查 obsConfigCache → 缓存命中? 直接用 / 未命中? fetchAndCacheObsConfig → 更新 lightStyleId → 更新 backgroundConfig → 3D 场景生效
常见坑

改模板切换逻辑时，如果只更新了 lightStyleId 而忘了同步 backgroundConfig，会出现灯光变了但背景没变的情况。两者必须一起更新。

6. 默认配置回退

当 fetchAndCacheObsConfig 失败时（网络异常、服务端错误等），系统不会直接报错炸页面，而是静默回退到默认配置。

// 回退逻辑示意
try {
  await fetchAndCacheObsConfig(obsId);
} catch (e) {
  // 回退到默认配置
  this.backgroundConfig = DEFAULT_TEMPLATE_CONFIG.backgroundConfigData;
  // 错误上报但不阻断页面
  errorReporter.report(e);
}
用户感知

回退发生时，用户看到的是"渲染风格悄悄回到默认值"，而不是错误弹窗。这是一种优雅降级策略 — 宁可画面风格不对，也不能让页面白屏。

7. 离线渲染状态机中的模板状态全景

把模板相关的所有状态放在一起看：

OfflineRenderStateManager {
  // === 模板相关 ===
  currentObsId: string          // 当前模板 ID
  lightStyleId: string           // 当前灯光样式
  hdriBackgroundId: string       // 当前 HDRI 背景
  backgroundConfig: object       // 背景完整参数
  obsConfigCache: Map<id, cfg>   // 模板配置缓存

  // === 渲染相关 ===
  snapshotList: []               // 快照列表
  objectShowRuleMap: Map          // 来自父页面同步
  renderTasks: []                // 渲染任务队列
  hasNewRender: boolean          // 图册红点
  isSubmitting: boolean          // 提交中锁
  hdPermission: boolean          // 高清渲染权限
}

8. 自检 Quiz

Q1: obsConfigCache 的作用是什么？
  • A. 缓存渲染任务的提交状态
  • B. 缓存模板的灯光样式映射和背景配置，避免重复请求
  • C. 缓存父页面同步的 objectShowRuleMap
  • D. 缓存 3D 场景的相机视角
Q2: 当 fetchAndCacheObsConfig 请求失败时，系统会怎么做？
  • A. 直接抛出错误，页面白屏
  • B. 自动重试 3 次后放弃
  • C. 回退到 DEFAULT_TEMPLATE_CONFIG.backgroundConfigData，渲染风格回到默认值
  • D. 停止渲染功能，隐藏渲染按钮
Q3: 切换模板时，为什么必须同时更新 lightStyleId 和 backgroundConfig？
  • A. 因为灯光和背景绑定在同一个模板下，只更新一个会导致画面不一致
  • B. 因为代码有 bug，必须两个一起改才行
  • C. 因为 lightStyleId 是 backgroundConfig 的子字段
  • D. 不需要同时更新，它们是独立的
