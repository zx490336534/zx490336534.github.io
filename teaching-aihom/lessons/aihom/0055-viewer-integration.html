055 2D/3D Viewer 集成与通信

理解 ai-home 如何通过 iframe 嵌入 viewer-2d 和 render-3d，以及它们之间的 postMessage 通信协议、数据同步与 MCP 工具桥接机制

1. 为什么用 iframe 嵌入 Viewer

AI Home 的前端页面需要同时展示2D 户型图和3D 渲染图。这两个 Viewer 并不是 ai-home 自己实现的，而是由独立的子应用（viewer-2d / render-3d）提供。ai-home 通过 <iframe> 将它们嵌入到自己的页面中。

设计优势

技术隔离：viewer-2d 基于 Canvas/WebGL 绑定、render-3d 基于 BimFace 引擎，两者技术栈与 ai-home（React）完全不同，iframe 天然实现了运行时隔离。
独立部署：Viewer 子应用可以独立迭代版本，不影响宿主页面。
复用性：同一个 Viewer 可以被多个产品页面嵌入，只需遵循统一的通信协议。

2. iframe 嵌入方式

Viewer2D 嵌入

在 Viewer2D.tsx 组件中，通过一个标准的 <iframe> 标签嵌入 2D 查看器：

<iframe
  ref={iframeRef}
  id={getViewer2DIframeId(designId, levelId)}
  src={`${origin}/pub/tool/bim/viewer-2d?designId=${designId}&levelId=${levelId}`}
  width="100%" height="100%" frameBorder="0" allowFullScreen
/>

Render3D 嵌入

在 Render3D/index.tsx 组件中，嵌入方式类似，但 URL 路径和参数不同：

<iframe
  ref={iframeRef}
  id={getRender3DIframeId(designId, levelId)}
  src={`${origin}/pub/tool/bim/render-3d?designId=${designId}&levelId=${levelId}&generateGallery=${...}`}
  width="100%" height="100%" frameBorder="0" allowFullScreen
/>
关键细节

iframe 的 id 由 getViewer2DIframeId() / getRender3DIframeId() 工具函数生成，格式为基于 designId 和 levelId 的唯一标识。这个 id 是后续 postMessage 定向发送消息的关键。

3. postMessage 通信协议

父窗口（ai-home）和子窗口（Viewer iframe）之间的所有通信都通过 window.postMessage 实现。ai-home 封装了 IframeMessenger 单例来统一管理消息收发。

消息格式

所有消息都遵循统一的结构：

// IframeMessage 接口定义
interface IFrameMessage<T> {
  type: string;   // 消息类型枚举值
  data: T;         // 消息载荷，类型随 type 变化
}

消息方向

方向枚举名含义
子 → 父
INPUT_MESSAGE_TYPE		VIEWER2D_LOADING_SUCCESS2D Viewer 加载完成
RENDER3D_LOADING_SUCCESS3D Viewer 加载完成
RENDER3D_UPDATE_RENDER_IMAGE3D 渲染图更新（含 base64 图片）
SYNC_STATUS_CHANGE2D 同步状态变化（Syncing / UpToDate / Failed）
BATCH_CAPTURE_STATUS_CHANGE批量截图状态变化（Ready / Completed / Failed）
父 → 子
OUT_PUT_MESSAGE_TYPE		VIEWER2D_UPDATE_DESIGN通知 2D Viewer 刷新设计数据
RENDER3D_REFRESH通知 3D Viewer 刷新渲染
RENDER3D_GET_RENDER_IMAGE请求 3D Viewer 返回渲染截图
TRIGGER_BATCH_CAPTURE触发 3D 批量截图
SCREEN_MODE_CHANGE通知 Viewer 全屏/退出全屏

IframeMessenger 核心实现

class IframeMessenger {
  // 订阅子窗口消息（按 type 分发）
  on<T>(type: T, handler: MessageHandler): () => void;

  // 向指定 iframe 发送消息
  postToIframe(iframeId: string, type: T, data: T): void {
    const iframe = document.getElementById(iframeId);
    iframe.contentWindow.postMessage({ type, data }, origin);
  }

  // 内部：监听 window.message 事件，按 type 分发给注册的 handler
  private handleMessage(event: MessageEvent) {
    const message = event.data;
    const handlers = this.handlers.get(message.type);
    handlers.forEach(h => h(message.data, event));
  }
}
安全机制

postMessage 调用时始终指定 window.location.origin 作为目标源，防止消息泄漏到非同源页面。IframeMessenger 在构造函数中就开始监听，是整个 Viewer 通信的中枢。

4. 数据同步机制

当 AI Agent 执行了户型布局等操作后，2D 和 3D Viewer 需要同步最新数据。这个过程涉及多个状态和 loading 管理。

同步流程

Agent 完成布局 → 发送 VIEWER2D_UPDATE_DESIGN → 2D Viewer 重新加载 → SYNC_STATUS_CHANGE (Syncing) → 父窗口显示 loading → SYNC_STATUS_CHANGE (UpToDate) → loading 消失

SyncStatus 状态机

ViewerStateManager 维护了一个 syncStatusMap，以 designId-levelId 为 key 跟踪每个 Viewer 的同步状态：

enum SyncStatus {
  Default    = 'default',       // 正常态
  OutOfSync  = 'out_of_sync',   // 数据不同步
  Syncing    = 'syncing',       // 正在同步中 → 显示 loading
  UpToDate   = 'up_to_date',    // 同步完成 → 3 秒后回到 Default
  SyncFailed = 'sync_failed',   // 同步失败 → 显示 toast 错误
}

3D Viewer 刷新的额外保障

3D Viewer 的刷新有一个 20 秒超时机制。如果发送 RENDER3D_REFRESH 后 20 秒内未收到 RENDER3D_LOADING_SUCCESS，会自动清除 loading 状态并提示超时错误。同时还监听 RENDER3D_REFRESH_FAILED 来处理渲染失败的情况。

布局进度

除了同步状态，ViewerStateManager 还维护了 layoutProgressMap，跟踪布局生成的实时进度（如 3/10 个房间已布局），在 loading 界面上显示给用户。

5. MCP 工具桥接流程

当 AI Agent 需要获取 3D 场景的截图时，不能直接操作 WebGL 上下文（它在 iframe 里），而是通过 MCP 工具桥接 来完成：后端发起工具调用 → 前端 SDK 接收 → 通过 postMessage 让 iframe 截图 → 结果回传。

注册的前端 MCP 工具

工具名功能
capture_3d_screenshot截取 3D 截图，返回图片 URL 列表
capture_3d_render截取 3D 截图并通过 AI 优化渲染质量
search_decoration_model搜索装饰模型
replace_decoration_model替换装饰模型

capture_3d_screenshot 完整链路

Agent 调用工具 → WebSocket 推送 Tool Call → agent-conversation-sdk 触发 callback → capture3DScreenshotApi() → postMessage → iframe

具体步骤：

  1. 触发截图 — 通过 iframeMessenger.postToIframe() 向 render-3d iframe 发送 TRIGGER_BATCH_CAPTURE 消息
  2. 等待回调 — 监听 BATCH_CAPTURE_STATUS_CHANGE 消息，等待 iframe 完成截图
  3. 接收 base64 — iframe 截图完成后，通过 postMessage 返回 base64 图片数组
  4. 上传图片 — 将 base64 图片通过 FileUploadUtils.uploadBase64Image() 上传到 CDN
  5. 返回 URL — 将上传后的 URL 列表作为 MCP 工具结果返回给 Agent
// MCP 工具注册（MCP/index.ts）
export const FRONT_TOOLS: MCPTool[] = [
  {
    name: 'capture_3d_screenshot',
    callback: capture3DScreenshot,  // 由 agent-conversation-sdk 调用
  },
  {
    name: 'capture_3d_render',
    callback: capture3DRender,      // 截图 + AI 渲染优化
  },
  // ...
];
超时与重试

capture3DScreenshotApi 设有 5 分钟超时（SCREENSHOT_TIMEOUT = 300000ms）。如果 iframe 未就绪（BATCH_CAPTURE_STATUS_CHANGE 的 status 为 Ready 时才触发截图），会等待直到超时。截图失败时有完善的诊断信息上报机制。

capture_3d_render 的额外步骤

在 capture_3d_screenshot 的基础上，capture_3d_render 还会：

  1. 将截取的每张图片调用 optimizeRenderImage() 进行 AI 渲染优化
  2. 使用 Promise.allSettled 并行处理，容忍部分失败
  3. 汇总消耗的积分（credits）和成功/失败数量
  4. 返回优化后的图片 URL 列表

6. 全局 iframe 消息处理

除了 Viewer 组件内部的消息处理，GlobalIframeMessage.ts 在应用启动时注册了一些全局的 iframe 消息处理器：

export function setupGlobalIframeMessage() {
  setupToastMessage();     // iframe 发来的 toast 弹窗
  setupCommentsMessage();  // 评论选中项信息变更
  setupCaptureMessage();   // 截图就绪状态
}
消息类型处理逻辑
TOAST_MESSAGEiframe 可以请求宿主显示 toast 通知（success/error/warn）
COMMENTS_INFO_CHANGEiframe 中用户选中了某个构件或家具，同步到宿主的评论系统
BATCH_CAPTURE_STATUS_CHANGE维护 captureableMap，标记哪个 designId-levelId 已就绪可截图
