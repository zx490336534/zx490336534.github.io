054 reactive-framework 深入

理解响应式状态管理框架的核心机制 — observable、observer、computed、combine 与 connect 的协作

1. 回顾：为什么需要响应式框架

在 Lesson 10 中我们初步了解了 reactive-framework 的概念。这一课我们深入其内部实现，搞清楚 @observable、observer()、StateManager、combine、connect 和 @computed 这些核心 API 是如何协作的。

核心思想

当你读取一个 observable 属性时，框架自动记录谁在读它；当你修改这个属性时，框架自动通知所有读过它的地方重新执行。这就是"响应式"的本质 — 依赖自动追踪 + 精确更新。

2. @observable 装饰器

@observable 将一个普通属性变成"可观察"属性。它在底层通过 Proxy（或 Object.defineProperty）拦截属性的读写操作。

import { observable } from '@coohome/reactive-framework';

class DesignState {
  @observable
  designId: string = '';

  @observable
  isLoading: boolean = false;

  @observable
  wallList: WallItem[] = [];
}

它做了什么

  1. 读取拦截 — 当任何"观察者"读取 designId 时，框架将当前观察者注册为该属性的依赖
  2. 写入拦截 — 当 designId 被赋新值时，框架通知所有已注册的依赖进行更新
  3. 批量更新 — 同一事件循环内的多次赋值会被合并，只触发一次更新
注意

@observable 只追踪属性本身。如果你用 @observable arr，替换整个数组会触发更新，但 arr.push(x) 不会（因为引用没变）。需要使用框架提供的 observableArray 或手动触发。

3. observer 函数

observer 是一个高阶函数（或装饰器），用于包装"需要响应 observable 变化的代码块"。最常见的用法是包装 React 组件和副作用函数。

import { observer } from '@coohome/reactive-framework';

// 用法一：包装 React 组件
const DesignPanel = observer(() => {
  const state = useDesignState();
  return <div>{state.designId}</div>;
  // 当 designId 变化时，自动触发重新渲染
});

// 用法二：创建独立的副作用反应
observer(() => {
  console.log('当前 designId:', state.designId);
});

执行机制

observer 包裹函数执行 → 执行过程中读取 @observable 属性 → 框架自动收集依赖 → 属性变化时重新执行

4. StateManager 基类

StateManager 是我们项目中组织状态的标准基类。它本质上是一个"可观察对象容器 + 生命周期管理器"。

import { StateManager, observable } from '@coohome/reactive-framework';

class DesignStateManager extends StateManager {
  @observable
  designId: string = '';

  @observable
  isLoading: boolean = false;

  // 初始化：组件挂载时自动调用
  onInit() {
    this.loadDesign();
  }

  // 清理：组件卸载时自动调用
  onDestroy() {
    // 取消订阅、清理定时器等
  }

  async loadDesign() {
    this.isLoading = true;
    this.designId = await fetchDesignId();
    this.isLoading = false;
  }
}
为什么要用 StateManager 而不是纯 @observable 类
  • 提供 onInit() / onDestroy() 生命周期，确保副作用能被清理
  • 内置 combine() / connect() 支持，方便组合多个状态源
  • 与 React 组件通过 useStateManager() hook 无缝集成

5. combine — 组合多个状态源

combine 将多个 observable 的值"组合"成一个新值，类似函数式编程中的 lift。当任何一个输入变化时，组合结果自动重算。

import { observable, combine } from '@coohome/reactive-framework';

class RoomState {
  @observable
  width: number = 4000;

  @observable
  height: number = 3000;

  // combine：任何输入变化时自动重算
  area = combine(
    () => this.width,
    () => this.height,
    (w, h) => w * h / 1000000  // 平方米
  );
}

const room = new RoomState();
console.log(room.area); // 12
room.width = 5000;
console.log(room.area); // 15 — 自动更新
combine vs @computed

combine 是函数式 API，适合在方法内或构造函数中动态组合；@computed 是装饰器 API，适合在类中声明式定义派生属性。两者底层机制相同，选择取决于风格偏好和是否需要传参。

6. connect — 连接外部数据源

connect 用于将外部数据源（如 Redux store、URL 参数、WebSocket 消息）桥接到 observable 体系中。它是"非响应式世界"进入"响应式世界"的入口。

import { StateManager, connect } from '@coohome/reactive-framework';

class DesignStateManager extends StateManager {
  // 从外部 Redux store 读取 userId
  @connect((store) => store.user.userId)
  userId: string = '';

  // 从 URL 参数读取 designId
  @connect(() => new URLSearchParams(location.search).get('id'))
  designId: string = '';

  // 内部可观察属性
  @observable
  isLoading: boolean = false;
}

connect 的特点

  • 只读 — @connect 属性通常不支持从 observable 侧反写回外部源
  • 自动同步 — 外部源变化时，@connect 属性自动更新并通知下游观察者
  • 桥接作用 — 让 StateManager 可以"消费"任何数据源而不耦合其 API

7. @computed 计算属性

@computed 定义一个"派生属性"— 它的值完全由其他 observable 属性计算得出，并且框架会缓存结果，只在依赖变化时重算。

import { observable, computed } from '@coohome/reactive-framework';

class WallState {
  @observable
  wallList: WallItem[] = [];

  @observable
  selectedId: string | null = null;

  // 只有 wallList 或 selectedId 变化时才重算
  @computed
  get selectedWall() {
    return this.wallList.find(w => w.id === this.selectedId) ?? null;
  }

  // computed 可以依赖另一个 computed
  @computed
  get selectedWallArea() {
    const wall = this.selectedWall;
    return wall ? wall.width * wall.height : 0;
  }
}
性能要点

@computed 的缓存是惰性的 — 如果没有人读取它，就不会执行 getter。但如果被读取过且依赖没变，直接返回缓存值，O(1) 开销。避免在 getter 内做昂贵操作后又频繁修改依赖，否则缓存失效会很频繁。

8. 与 React Hooks 对比

很多同学会问："我们已经有 useState、useMemo、useEffect 了，为什么还需要响应式框架？" 下表做了直接对比：

能力 React Hooks reactive-framework
声明状态 useState(initial) @observable prop = initial
派生计算 useMemo(() => ..., deps) @computed get prop()
副作用 useEffect(() => ..., deps) observer(() => ...)
依赖追踪 手动列出 deps 数组 自动追踪，无需手动声明
更新粒度 组件级重新渲染 精确到属性级，只有读过该属性的 observer 重执行
跨组件共享 需要 Context / 外部 store StateManager 天然可共享
测试 需要 renderHook 等工具 直接实例化 StateManager 测试
关键区别

React Hooks 的依赖数组是你最容易出 bug 的地方 — 漏写依赖导致 stale closure，多写依赖导致不必要的执行。reactive-framework 通过 Proxy 自动追踪依赖，从根本上消除了这类问题。

在我们的项目中，两者是协作关系而非替代关系：StateManager 管理状态逻辑，React 组件通过 observer() 包装消费状态，两者各司其职。
