047 auto-layout-service 深度追踪

深入理解自动布局引擎的 Processor 模式、数据流与双通道并行架构

1. 项目定位

auto-layout-service 是 AI Home 的自动布局引擎。当用户上传户型图后，这个服务负责完成从户型识别到家具摆放的全部自动化流程。

一句话定位

接收户型图请求 → 调用 AI 识别户型 → 自动生成家具布局方案 → 返回结果。Processor 模式驱动的异步任务引擎。

三模块结构

模块职责
auto-layout-service-common共享 DTO、VO、枚举
auto-layout-service-clientFeign 客户端，供外部服务调用
auto-layout-service-web核心业务 — Processor、Manager、Service 全在这里

2. Processor 继承体系

Processor 是 auto-layout-service 的核心设计模式。每一个异步任务（如自动布局、户型识别）都由一个 Processor 实例驱动。继承体系如下：

BaseProcessor  （最底层，定义 doProcess 抽象模板）
    │
    ├── BaseAsyncProcessor  （异步任务生命周期管理）
    │       │
    │       ├── BaseDbTaskAsyncProcessor  （DB 持久化任务状态）
    │       │       └── SubmitAutoDesignV2AsyncProcessor
    │       │
    │       └── BaseRedisTaskAsyncProcessor  （Redis 管理任务状态）
    │               └── AutoLayoutWithImageProcessor
    │
    └── (同步 Processor，直接执行)
关键区别

BaseDbTaskAsyncProcessor 用 MySQL 存任务状态，适合需要持久化的长任务；BaseRedisTaskAsyncProcessor 用 Redis 存任务状态，适合高并发、短生命周期的任务。两者继承路径不同（一个走 BaseAsyncProcessor，一个走 BaseAsyncV2Processor）。

BaseAsyncProcessor.doProcess() 核心流程

getExistTask() → executeNewTask() → initTask() → doAsyncProcess() → onSuccess() / onError()
  1. getExistTask() — 检查是否已有相同任务在执行，防止重复提交
  2. executeNewTask() — 判断是否需要创建新任务
  3. initTask() — 初始化任务记录（写 DB 或写 Redis）
  4. doAsyncProcess() — 提交到线程池执行真正的业务逻辑
  5. onSuccess() / onError() — 完成回调，更新任务状态

3. AutoLayoutWithImage 完整数据流

当用户提交"带图片的自动布局"请求时，完整链路如下：

API 请求 → SubmitAutoDesignV2AsyncProcessor → AutoLayoutWithImageProcessor → 返回结果

AutoLayoutWithImageProcessor.doProcessInner() 三步走

步骤方法做了什么
1. 上色 coloringLayoutImage() 调用 AiNativeManager，把黑白户型图上色，生成彩色户型图
2. 分析 getLayoutWithImage() 调用 OpenaiManager，把彩色图发给 OpenAI Vision，识别房间类型和位置
3. 构建 buildAutoLayoutDesign() 根据 AI 识别结果，匹配家具、计算布局坐标，生成最终方案
设计亮点

步骤 1 和步骤 2 分别调用不同的 AI 服务（AiNative + OpenAI），通过 Manager 层封装实现了AI 服务的解耦。Processor 不关心 AI 具体怎么调，只管编排流程。

4. 双通道并行布局

系统设计了两条并行的布局通道，通过不同的策略生成布局方案：

通道策略适用场景
RAG 从历史案例库中检索相似户型，参考历史方案生成布局 常见户型、有历史数据的情况
PRODUCT_CONFIG 基于产品配置规则，按照户型参数和家具规格直接计算布局 新户型、无历史数据的情况
为什么双通道

单一策略容易出现盲区。RAG 在有历史数据时效果好，但新户型没有参考；PRODUCT_CONFIG 通用但缺乏个性化。双通道并行 + 择优，保证覆盖率和质量。

5. ThreadLocal 上下文传递

异步任务在不同线程间执行时，如何传递请求级别的上下文信息？

auto-layout-service 使用 AutoLayoutContext（ThreadLocal 模式）来解决这个问题：

// 在请求入口设置上下文
AutoLayoutContext context = new AutoLayoutContext();
context.setUserId(userId);
context.setTaskId(taskId);
AutoLayoutContext.set(context);

// 在任何地方获取上下文
AutoLayoutContext ctx = AutoLayoutContext.get();
String taskId = ctx.getTaskId();
注意

ThreadLocal 在异步线程中会丢失！Processor 的 doAsyncProcess() 提交到线程池时，需要手动传递上下文到子线程。这也是为什么 context/ 目录专门存放上下文类的原因。

6. Manager 层封装

Manager 层是 Processor 与外部服务之间的缓冲层。Processor 只管编排流程，具体的外部调用全交给 Manager。

Manager职责
OpenaiManagerOpenAI API — chat completions、embeddings、图像分析（com.openai SDK）
AiNativeManagerAI Native 图像生成服务（ai-native-service-client）
AutoDesignInfoManager任务 CRUD — 创建、查询、更新 AutoDesign 任务记录
KamManagerKAM 户型服务 — 户型数据查询
LOD200Manager / LOD300Manager不同精度级别的户型处理服务
设计原则

一个 Manager 对应一个外部依赖。如果要接入新的 AI 服务，只需要新建一个 Manager，Processor 层的编排逻辑不需要大改。
