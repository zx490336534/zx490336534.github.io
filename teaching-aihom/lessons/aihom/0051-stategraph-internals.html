051 StateGraph 内部机制

深入理解 StateGraph 的数据结构、编译过程、执行引擎、检查点持久化与条件路由

1. StateGraph 数据结构：节点 + 边 + 状态

StateGraph 本质上是一个有向图，由三个核心要素组成：节点（Node）、边（Edge）和状态（State）。在 ai-native-service 中，它基于 Spring AI Alibaba 的 StateGraph 实现，是整个 Agent 工作流编排的骨架。

┌─────────────────────────────────────────────────────┐
│  StateGraph = (Nodes, Edges, State)                │
│                                                     │
│  Nodes:  { "supervisor", "floorplan_agent", ... }   │
│  Edges:  { "supervisor" → condition → "xxx" }       │
│  State:  { messages, context, step, ... }           │
└─────────────────────────────────────────────────────┘

节点（Node）

每个节点代表一个计算单元。在项目中，节点分为三类：

节点类型实现方式示例
Agent 节点AgentNodeFactory 创建，封装 ChatClient 调用Supervisor、Floorplan_to_Design
Tool 节点工具回调，执行具体业务逻辑FloorplanToStructureTool
条件节点函数式接口，根据状态决定下一步去向CustomSupervisorEdgeAction

在数据库中，节点配置存储在 GraphNodes 表，每个节点记录了类型、关联的 Agent/Tool ID 和参数。

边（Edge）

边定义了节点之间的流转关系。有两种边：

  • 普通边（Direct Edge）：节点 A 执行完，直接跳到节点 B
  • 条件边（Conditional Edge）：根据当前状态动态决定下一个节点，对应 addConditionalEdge() 方法
// 普通边：agent 执行完 → 直接到 tool
graph.addEdge("agent_node", "tool_node");

// 条件边：supervisor 根据意图路由
graph.addConditionalEdge("supervisor", 
    state -> routingFunction(state),   // 路由函数
    Map.of("design", "floorplan_agent",  // 路由表
           "edit",   "image_editor"));

状态（State）

状态是一个在整个图执行过程中持续传递和累积的数据容器。项目中状态通常包含：

  • messages：对话历史（ChatMessage 列表）
  • context：业务上下文（用户信息、场景参数等）
  • step：当前执行步骤
  • 各子 Agent 的输出结果
关键设计

状态的更新遵循归并（Reducer）语义。当节点返回部分状态更新时，系统用 Reducer 函数将其合并到全局状态中。例如 messages 字段使用 add Reducer（追加新消息），而不是替换整个列表。

2. 编译过程：StateGraph → CompiledGraph

StateGraph 是一个可变的构建器（Builder），定义了图的结构。但要执行它，必须先调用 .compile() 将其转化为 CompiledGraph。这个编译过程做了几件关键的事：

StateGraph（可变图定义） → 验证拓扑 → 解析入口/出口 → 注册 Checkpointer → CompiledGraph（不可变执行图）

编译阶段的关键操作：

  1. 拓扑验证 — 检查是否有孤立节点、循环路径是否合法、所有条件边的目标节点是否都存在
  2. 入口解析 — 确定 __START__ 节点（用户定义的第一个节点），作为执行起点
  3. 出口识别 — 识别 __END__ 节点（或没有出边的节点），作为终止条件
  4. Checkpoint 注册 — 如果配置了 Checkpointer，在每个节点执行后自动保存快照
  5. 不可变化 — 编译后的图不允许再添加节点或边，确保运行时一致性
// 在 StateGraphFactory 中的典型编译流程
StateGraph graph = new StateGraph(stateType)
    .addNode("supervisor", supervisorNode)
    .addNode("floorplan_agent", floorplanNode)
    .addConditionalEdge("supervisor", routingFn, routeMap)
    .addEdge("floorplan_agent", "__END__");

CompiledGraph compiled = graph.compile(
    CompileConfig.builder()
        .checkpointer(new MemorySaver())   // 检查点存储
        .build()
);
Factory 模式

项目中 StateGraphFactory 封装了编译过程。它从数据库加载图配置（StateGraphPo + GraphNodesPo），动态构建 StateGraph 并编译。StateGraphLoader 则负责缓存和版本管理，避免重复编译。

3. 执行引擎：stream() 内部逻辑

CompiledGraph.stream() 是整个 StateGraph 的执行入口。它以流式方式逐节点执行，每次执行一个节点后产出一个中间状态。核心循环如下：

// stream() 的伪代码逻辑
currentNode = "__START__"
state = initialState

while (currentNode != "__END__") {
    // 1. 取出当前节点的执行函数
    nodeFn = nodes.get(currentNode)
    
    // 2. 执行节点，获得状态更新
    stateUpdate = nodeFn.invoke(state)
    
    // 3. 归并状态（通过 Reducer）
    state = merge(state, stateUpdate)
    
    // 4. 保存检查点（如果配置了）
    if (checkpointer != null) {
        checkpointer.put(state, currentNode)
    }
    
    // 5. 决定下一个节点
    if (hasConditionalEdge(currentNode)) {
        currentNode = conditionalEdge.get(currentNode).apply(state)
    } else {
        currentNode = directEdge.get(currentNode)
    }
    
    // 6. 产出中间状态给调用方
    yield state  // 流式产出
}

在 ai-native-service 中，StateGraphServiceImpl 调用 stream() 后，将每个中间状态通过 WebSocket 流式推送给前端。这意味着：

  • 每经过一个节点，前端就能收到一次更新（如"正在识别户型..."、"正在生成布局..."）
  • 超时保护：每个节点执行都有超时限制，防止某个 Agent 或 Tool 卡住
  • 异常处理：节点抛异常时，执行引擎可以回退到上一个检查点或直接终止
为什么是 stream 而不是 invoke？

invoke() 只返回最终结果，中间过程是黑盒。stream() 则实时产出每个节点的中间状态，让前端能展示"正在思考..."这样的进度反馈，用户体验更好。项目中几乎全部使用 stream()。

4. 检查点与持久化

检查点（Checkpoint）机制是 StateGraph 实现容错恢复和人机协作的核心。

工作原理

每次节点执行完后，执行引擎会调用 Checkpointer.put() 保存一份当前状态的快照。快照包含：

字段说明
thread_id会话 ID，标识一次完整的图执行
checkpoint_id检查点 ID，支持同一会话多次回退
state当前完整状态的序列化数据
node产生这个检查点的节点名称
metadata附加信息（时间戳、版本号等）

存储后端

项目支持两种检查点存储：

  • MemorySaver — 内存存储，适合开发调试，重启即丢失
  • Redis/数据库存储 — 生产环境使用，通过自定义 Checkpointer 实现持久化到 Redis 或 MySQL

恢复与人机协作

检查点支持两个关键能力：

  1. 故障恢复 — 服务重启后，可以通过 thread_id 加载最近的检查点，从断点继续执行
  2. Human-in-the-loop — 某些节点需要人工审批（如设计方案确认），执行引擎在该节点前暂停，将状态保存为检查点；人工审批后，从检查点恢复并继续执行
// 从检查点恢复执行
config = RunnableConfig.builder()
    .threadId("conv_12345")        // 指定会话
    .checkpointer(checkpointer)   // 指定存储
    .build();

// stream 会自动从最新的检查点恢复
graph.stream(inputState, config);

5. 条件边与路由

条件边是 StateGraph 实现动态路由的关键。在项目中，最核心的条件边就是 Supervisor 的路由决策。

条件边的结构

一个条件边由两部分组成：

  • 路由函数（Routing Function）：接收当前状态，返回一个字符串 key
  • 路由表（Route Map）：key → 目标节点名的映射
// Supervisor 的条件边（简化）
graph.addConditionalEdge(
    "supervisor",                      // 源节点
    state -> {                          // 路由函数
        String intent = classifyIntent(state.messages());
        return intent;                  // 返回 "floorplan" / "image_edit" / "general"
    },
    Map.of(                             // 路由表
        "floorplan",  "floorplan_to_design_agent",
        "image_edit", "image_editor_agent",
        "general",    "general_chat_agent"
    )
);

路由函数的实现：CustomSupervisorEdgeAction

在 ai-native-service 中，CustomSupervisorEdgeAction 实现了路由逻辑。它的流程是：

  1. 获取 Supervisor Agent 上一轮的输出（通常是 JSON 格式的意图分类结果）
  2. 解析意图字段，映射到路由表中的 key
  3. 返回目标节点名

多层路由

项目中不仅 Supervisor 使用条件边，子 Agent 内部也可能有二级路由。例如 Floorplan_to_Design Agent 内部，可能根据户型识别结果的置信度，路由到"需要人工确认"或"自动生成布局"两个不同路径。

路由 vs 硬编码 if-else

条件边的优势在于配置化。路由表存在 Nacos 或数据库中，新增一个子 Agent 只需要添加一条路由记录，不需要改代码重新部署。
