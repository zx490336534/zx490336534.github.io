053 AI 服务集成与模型调用

从 AGENTS.md 中的 OpenaiManager 出发，深入理解如何在 auto-layout-service 中集成 OpenAI / Gemini 等大模型服务

1. 为什么需要 AI 服务集成

在 auto-layout-service 中，AI 不是装饰，而是核心驱动力。根据 AGENTS.md 的架构说明，系统使用了两个 AI 提供商：

提供商Manager 类用途SDK
OpenAIOpenaiManagerChat Completions、Embeddings、图像分析com.openai SDK
AI Native ServiceAiNativeManager图像生成（户型图着色等）ai-native-service-client
核心数据流

以 AutoLayoutWithImageProcessor 为例：先通过 AiNativeManager 着色户型图（coloringLayoutImage()），再通过 OpenaiManager 分析着色后的图片（getLayoutWithImage()），最终构建布局结果。

2. OpenAI SDK 集成

2.1 SDK 选择与配置

项目使用官方 com.openai:openai-java SDK，而非社区库。在 OpenaiManager 中封装了对 OpenAI API 的所有调用。

// OpenaiManager 核心职责
public class OpenaiManager {
    // 1. Chat Completions — 对话补全，用于理解户型图
    chatCompletion(messages, model, ...);

    // 2. Embeddings — 文本向量化，用于语义搜索
    createEmbedding(text, model);

    // 3. Image Analysis — 视觉理解，用于户型图识别
    analyzeImage(imageUrl, prompt);
}

2.2 Chat Completions 调用模式

最常用的调用方式。构造 messages 数组，指定模型和参数，获取 AI 响应：

// 典型调用流程
List<Message> messages = List.of(
    systemMessage("你是一个户型布局分析专家..."),
    userMessage(
        textContent("请分析这个户型的布局"),
        imageContent(floorplanBase64)
    )
);

ChatCompletion result = openaiManager.chatCompletion(
    messages,
    "gpt-4o",           // 模型选择
    0.2,                  // temperature — 越低越确定
    4096                  // max_tokens
);

2.3 多模态调用（Vision）

户型图分析是典型的多模态场景：同时发送文本指令和图片数据。OpenAI 的 Vision API 支持 base64 和 URL 两种图片输入方式。

实际应用

在 getLayoutWithImage() 方法中，系统将 AI Native 着色后的户型图以 base64 编码发送给 GPT-4o，让 AI 识别房间类型、门窗位置等结构信息。

3. Gemini 集成

3.1 为什么还需要 Gemini

OpenAI 不是唯一选择。在实际业务中，我们可能需要：

  • 降本 — Gemini Flash 系列价格远低于 GPT-4o
  • 降延迟 — Google 全球节点覆盖好，亚洲访问延迟低
  • 兜底容灾 — OpenAI 限流或宕机时自动切换
  • 差异化能力 — Gemini 在某些多语言/多模态任务上表现更优

3.2 集成方式

Gemini 提供了与 OpenAI 兼容的 API 端点，大部分场景可以直接复用 OpenAI SDK 的调用模式：

// 方式一：使用 Gemini 原生 SDK
import com.google.genai.Client;

Client client = Client.builder()
    .apiKey(geminiApiKey)
    .build();

GenerateContentResponse response = client.models.generateContent(
    "gemini-2.5-flash",
    contents,
    config
);

// 方式二：使用 OpenAI 兼容端点
// base_url 改为 https://generativelanguage.googleapis.com/v1beta/openai/
// 即可复用 openai-java SDK

3.3 统一抽象层

在实际项目中，推荐通过策略模式抽象不同模型提供商，上层业务代码不感知具体是 OpenAI 还是 Gemini：

public interface LlmClient {
    ChatResponse chat(List<Message> messages, LlmConfig config);
    EmbeddingResponse embed(String text, LlmConfig config);
}

public class OpenAiLlmClient implements LlmClient { ... }
public class GeminiLlmClient implements LlmClient { ... }

// 通过配置切换
@Bean
LlmClient llmClient(LlmProperties props) {
    return switch (props.getProvider()) {
        case OPENAI -> new OpenAiLlmClient(props);
        case GEMINI -> new GeminiLlmClient(props);
    };
}

4. 模型选择策略

不同任务对模型的要求截然不同。盲目使用最贵的模型既浪费钱又增加延迟。

任务类型推荐模型理由
户型图结构分析GPT-4o多模态能力强，空间理解准确
简单文本分类/路由GPT-4o-mini / Gemini Flash速度快、成本低
文本向量化text-embedding-3-small性价比最高
复杂推理/代码生成o3 / Gemini Pro推理深度足够
图像生成AI Native 服务内部服务，无外部 API 费用
选择原则
  • 能用小模型就不用大模型 — 成本和延迟都更低
  • 多模态任务优先选视觉强的模型 — GPT-4o / Gemini Pro Vision
  • 关键路径做好 fallback — 主模型失败时自动降级到备用模型

5. Prompt 管理

5.1 Prompt 的重要性

Prompt 是 AI 应用的"代码"。在 auto-layout-service 中，Prompt 的质量直接决定了户型分析的准确性。

5.2 项目中的 Prompt 管理实践

根据 AGENTS.md，ai-native-service 项目使用 Nacos 配置中心管理 Agent 的 prompt，支持热更新。auto-layout-service 中的 OpenaiManager 也遵循类似模式：

// Prompt 管理最佳实践

// 1. 结构化 — 使用 System + User 分离角色和指令
messages = [
    system("角色定义 + 输出格式约束"),
    user("具体任务描述 + 输入数据")
]

// 2. 版本化 — 每次 prompt 变更记录版本号
@Value("${prompts.layout-analysis.version}")
private String promptVersion;

// 3. 外部化 — prompt 存配置中心，不硬编码
@Value("${prompts.layout-analysis.system}")
private String systemPrompt;

// 4. 模板化 — 使用变量占位符
// "请分析户型图中的 {room_count} 个房间，风格偏好为 {style}"
Prompt 工程要点
  • 明确角色 — 告诉 AI "你是户型布局专家"，比 "请分析这张图" 效果好 10 倍
  • 约束输出格式 — 要求 JSON 输出时给出 schema 示例
  • Few-shot 示例 — 给 1-2 个输入输出示例，比长篇描述更有效
  • 温度控制 — 结构化任务用 0.1-0.3，创意任务用 0.7-0.9

6. Token 用量统计

6.1 为什么统计 Token

AI 调用是按 token 计费的。不统计就无法控制成本，也无法优化。

6.2 Token 计算基础

模型输入价格 (每 1M tokens)输出价格 (每 1M tokens)
GPT-4o$2.50$10.00
GPT-4o-mini$0.15$0.60
Gemini 2.5 Flash$0.15$0.60
text-embedding-3-small$0.02—

6.3 统计实现方式

OpenAI API 响应中自带 usage 字段，记录了本次请求的 token 消耗：

// API 响应中的 usage 字段
{
  "usage": {
    "prompt_tokens": 1250,      // 输入 token 数
    "completion_tokens": 380,   // 输出 token 数
    "total_tokens": 1630        // 总计
  }
}

// 在 Manager 层记录日志
log.info("model={}, prompt_tokens={}, completion_tokens={}, cost=${}",
    model, usage.getPromptTokens(), usage.getCompletionTokens(),
    calculateCost(model, usage));

6.4 成本优化技巧

  • 精简 system prompt — 去掉冗余描述，每次调用都节省 token
  • 控制 max_tokens — 不需要长回复时限制输出长度
  • 缓存 embedding — 相同文本只算一次 embedding
  • 分层调用 — 简单任务用 mini 模型，复杂任务才用 4o
  • 图片压缩 — 发送前降低分辨率，减少 vision token 消耗
成本陷阱

一张 1024x1024 的图片在 Vision API 中大约消耗 765 tokens。如果每个请求都带高分辨率图片，月账单会非常可观。务必做好图片预处理。
