052 双通道并行布局算法

理解 auto-layout-service 如何通过 RAG + PRODUCT_CONFIG 双通道并行执行布局任务，以及结果合并的核心策略

1. 为什么需要双通道

在前面的课程中，我们了解了 auto-layout-service 的 Processor 模式和 Manager 层设计。当系统接到一个布局请求时，它面临一个核心问题：如何在保证布局质量的同时，最大化利用已有数据？

系统中存在两类数据源：

  • 历史案例库 — 存储了大量已有的优秀布局方案，可以通过向量检索找到相似案例
  • 产品配置库 — 存储了产品的标准化配置信息（PRODUCT_CONFIG），包含经过验证的布局规则

单通道执行的问题在于：向量检索可能找到"相似但不完全匹配"的案例，而产品配置虽然精确但缺乏灵活性。双通道并行正是为了融合两者优势。

设计思想

并行发起两个独立的 AI 通道，让它们各自给出布局方案，最后通过合并策略取最优解。这类似于"专家会诊"——多个专家独立诊断，综合意见后给出最终方案。

3. RAG 布局通道：向量检索 + OpenAI

RAG（Retrieval-Augmented Generation）通道是系统中最成熟的布局通道。它的工作分为三步：

Step 1: Embedding — 将查询转化为向量

首先，系统将当前户型的结构特征（房间数量、面积、功能分区等）通过 OpenAI Embedding API 转化为高维向量。在 OpenaiManager 中，调用链路为：

// OpenaiManager 中的 Embedding 调用
public List<Float> getEmbedding(String text) {
    // 调用 OpenAI Embedding API (text-embedding-3-small)
    // 将户型结构描述转化为 1536 维向量
}

Step 2: 向量检索 — 在案例库中寻找相似布局

拿到向量后，在向量数据库中执行相似度搜索（通常是余弦相似度），找到 Top-K 个最相似的历史布局案例。这些案例作为"参考素材"传给下一步的 LLM。

检索策略

检索不是简单地找"最像的"。系统会设定相似度阈值（如 0.75），低于阈值的案例会被过滤掉，避免给 LLM 提供质量不高的参考。

Step 3: OpenAI 生成 — 基于参考案例生成新布局

将检索到的参考案例 + 当前户型需求 + 用户偏好，组装成 prompt 发送给 OpenAI Chat Completions API。LLM 会参考历史案例的布局思路，结合当前户型的特殊性，生成一套新的布局方案。

// 伪代码：RAG 通道的核心流程
List<Float> embedding = openaiManager.getEmbedding(layoutQuery);
List<Case> similarCases = vectorStore.search(embedding, topK=5, threshold=0.75);

String prompt = buildPrompt(currentLayout, similarCases, userPreference);
LayoutResult result = openaiManager.chatCompletion(prompt);

4. PRODUCT_CONFIG 通道：Gemini 驱动

PRODUCT_CONFIG 通道走的是一条完全不同的路径。它不依赖历史案例，而是基于产品标准化配置来生成布局。

什么是 PRODUCT_CONFIG

PRODUCT_CONFIG 是产品团队预先定义的配置数据，包含：

  • 各功能区域的标准家具清单（客厅必须有沙发、茶几、电视柜...）
  • 家具间的空间约束规则（沙发与电视柜距离 2.5m-3.5m...）
  • 不同户型面积段的布局模板
  • 风格适配规则

Gemini 生成流程

PRODUCT_CONFIG 通道选择 Gemini 作为生成模型（区别于 RAG 通道的 OpenAI），流程如下：

// 伪代码：PRODUCT_CONFIG 通道的核心流程
ProductConfig config = productConfigManager.getConfig(areaType, style);
String prompt = buildConfigPrompt(currentLayout, config, constraints);

// 使用 Gemini 模型生成布局
LayoutResult result = geminiManager.generate(prompt);
Gemini 的优势

选择 Gemini 而非 OpenAI 用于此通道，是因为 Gemini 在结构化数据理解和规则遵循方面表现优异，特别适合处理 PRODUCT_CONFIG 中大量的约束条件和标准化规则。

5. 双通道并行执行

两个通道通过线程池并行提交，互不阻塞。在 BaseAsyncProcessor 的异步处理框架下，核心执行逻辑如下：

// 伪代码：双通道并行执行
public LayoutResult doDualChannelLayout(LayoutRequest request) {

    // 并行提交两个通道
    CompletableFuture<LayoutResult> ragFuture =
        CompletableFuture.supplyAsync(() ->
            ragChannel.execute(request),
            executorPool
        );

    CompletableFuture<LayoutResult> configFuture =
        CompletableFuture.supplyAsync(() ->
            productConfigChannel.execute(request),
            executorPool
        );

    // 等待两个通道都完成
    CompletableFuture.allOf(ragFuture, configFuture).join();

    // 合并结果
    return mergeResults(ragFuture.get(), configFuture.get());
}

这种并行设计的关键好处：

  • 总耗时 = max(通道A, 通道B)，而非两者之和
  • 单通道失败不影响另一个（可以降级为单通道结果）
  • 两个通道使用的不同 AI 模型（OpenAI / Gemini），避免了单一模型的偏见
容错设计

如果某个通道超时或异常，系统不会整体失败。它会降级使用另一个通道的结果，并在日志中记录降级原因。这保证了服务的高可用性。

6. 结果合并策略

双通道各自产出布局结果后，需要一个合并策略来决定最终方案。合并不是简单地"二选一"，而是一个多维度评分的过程。

评分维度

维度说明权重
约束满足度布局是否满足户型硬约束（墙、门、窗）高
空间利用率家具覆盖面积 / 可用面积中
动线合理性行走路径是否通畅、符合生活习惯中
风格一致性与用户选择的风格是否匹配低

合并流程

RAG 结果 → 多维评分 → ┌ 比较选择 → 最优方案
CONFIG 结果 → 多维评分 → └

合并策略有三种模式：

  1. 择优模式 — 两个结果各自打分，选总分更高的那个。适用于两个结果差异较大的场景。
  2. 融合模式 — 从 RAG 结果中提取布局创意（如家具摆放角度），从 CONFIG 结果中提取约束合规性，合并为一个新方案。
  3. 降级模式 — 当某个通道失败时，直接使用另一个通道的结果。
合并的核心原则

约束满足度是"一票否决"项。无论 RAG 通道的结果多有创意，如果违反了硬约束（如家具穿墙），该方案会被直接淘汰。这保证了布局的物理可行性。
