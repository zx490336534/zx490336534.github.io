058 离线渲染管线详解

从渲染任务提交到结果回写，完整理解 OfflineRenderStateManager 驱动的离线出图链路

1. 离线渲染管线全景

render-3d 仓库中的离线渲染并不是"点一下按钮等图片出来"这么简单。它是一条由 OfflineRenderStateManager 驱动的异步管线，涉及参数装配、API 提交、轮询等待、结果回写和父页面同步。

用户点渲染 → 参数装配 → API 提交 → 轮询 SnapshotTaskStatus → 结果回写
关键文件

这条管线的核心代码分布在 OfflineRenderStateManager.ts（状态机）、RenderButton/*（参数装配与 UI 入口）和 iframeHelper/*（父页面同步协议）。

2. 渲染任务提交与参数装配

2.1 入口：RenderButton

RenderButton 看起来是一个按钮组件，实际上它是渲染参数的总装配层。点击时，它会收集以下参数：

参数来源说明
currentObsId实时模板当前场景使用的实时模板 ID
lightStyleId模板灯光缓存灯光样式 ID，来自 obsConfigCache
hdriBackgroundId模板背景缓存HDRI 背景 ID
backgroundConfig模板配置背景配置数据
objectShowRuleMap父页面同步对象显示规则，决定哪些物件在渲染图中可见
cameraView场景相机相机位置、角度等属性
hdPermission权限接口是否允许高清渲染

2.2 模板配置缓存机制

fetchAndCacheObsConfig(obsId) 负责拉取并缓存模板配置：

// 伪代码：模板配置缓存逻辑
async fetchAndCacheObsConfig(obsId) {
  if (obsConfigCache.has(obsId)) {
    return obsConfigCache.get(obsId);  // 缓存命中，直接返回
  }
  const config = await fetchObsConfig(obsId);
  obsConfigCache.set(obsId, config);     // 写入缓存
  return config;
}
兜底策略

初始化失败时，系统会回退到 DEFAULT_TEMPLATE_CONFIG.backgroundConfigData。这意味着有些配置错误不会炸页面，而是渲染风格悄悄回到默认值 — 这种静默回退在排查问题时容易被忽略。

2.3 提交前的前置检查

  • 权限校验：检查 hdPermission，低权限用户可能无法使用高清渲染
  • 提交锁：isSubmitting 状态防止重复提交
  • 显示规则合并：objectShowRuleMap 与本地场景状态合并，确定最终提交参数

3. API 调用与任务提交

参数装配完成后，OfflineRenderStateManager 调用渲染接口提交任务。提交成功后，任务进入 renderTasks 列表，同时设置 isSubmitting = false。

// 伪代码：任务提交流程
async submitRender(params) {
  this.isSubmitting = true;
  try {
    const task = await renderAPI.submit(params);
    this.renderTasks.push(task);
    this.startPolling(task.taskId);   // 启动轮询
  } catch (err) {
    errorReporter.report(err);        // 错误归一化上报
  } finally {
    this.isSubmitting = false;
  }
}
想看真实的渲染参数结构？可以直接问 agent：RenderButton 里提交渲染时传了哪些参数。

4. SnapshotTaskStatus 状态机

渲染任务提交后，系统需要知道任务进行到哪一步。SnapshotTaskStatus 是一个状态枚举，驱动着整个轮询和结果回写流程。

// SnapshotTaskStatus 状态转换

  PENDING  ──→  PROCESSING  ──→  SUCCESS
      │              │                │
      │              └──→  FAILED   │
      │                      │        │
      └──────────────────────┘        │
                                      ↓
                              结果回写 + 红点通知
状态含义前端行为
PENDING任务已提交，排队中继续轮询，展示等待态
PROCESSING渲染引擎正在处理继续轮询，展示进度
SUCCESS渲染完成停止轮询，回写结果，设置 hasNewRender = true
FAILED渲染失败停止轮询，上报错误，提示用户重试

4.1 轮询策略

轮询参数

间隔 6 秒，最长 10 分钟。超过 10 分钟仍未完成的视为超时，按失败处理。这个策略在 OfflineRenderStateManager 中硬编码，不走配置。

4.2 hasNewRender 的共享语义

hasNewRender 不只是一个"有没有新渲染完成"的布尔值。它是图册红点和新结果提示的共享业务状态 — 图册组件、侧栏入口和父页面都会读取这个值来决定是否显示红点。

5. 结果回写与父页面同步

5.1 回写流程

渲染成功后，系统需要把结果 URL 回写到业务层：

  1. 从轮询响应中获取渲染结果 URL
  2. 更新 snapshotList，把新结果追加到图册列表
  3. 设置 hasNewRender = true，触发红点通知
  4. 通过 postMessage 通知父页面（如果需要）

5.2 iframe 协议注意事项

协议一致性

修改 postMessage / iframe 协议时，必须同时检查：显示规则（objectShowRuleMap）、任务回写、图册入口和父页面接收端。最常见的症状是"页面还能渲染，但离线参数或图册结果已经和父层脱节"。

6. 错误处理与重试

6.1 错误归一化

utils/errorReporter.ts 是渲染链路的错误归一化中心。所有异常都会被转化为可上报的统一格式，供监控和用户提示使用。

6.2 典型错误场景

场景处理方式用户感知
模板配置拉取失败回退到 DEFAULT_TEMPLATE_CONFIG渲染风格变成默认值，无报错
渲染 API 提交失败errorReporter 上报 + 提示用户弹出错误提示
轮询超时（10 分钟）停止轮询，标记为失败提示渲染超时
轮询接口返回 FAILED停止轮询，上报错误提示渲染失败，可重试
父页面同步显示规则失败使用本地缓存的规则可能与父页面不一致

6.3 重试机制

渲染失败后，用户可以手动点击重试。系统会重新走一遍完整的参数装配流程，确保拿到最新的模板配置、显示规则和相机状态，而不是简单地用旧参数重新提交。

批量出图保护

batchCaptureManager.ts 和 utils/async.ts 负责异步调度和批量出图任务保护。房间自动出图时，系统会按 RoomType 过滤房间，优先使用 smartCameraViewMap 智能视角，没有时回退到 renderRoomCenterView() 计算兜底视角。

7. 核心状态一览

OfflineRenderStateManager 维护的关键状态字段：

字段类型用途
snapshotListArray历史渲染快照列表
