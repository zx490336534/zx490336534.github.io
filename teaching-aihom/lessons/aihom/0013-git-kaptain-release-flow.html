013 Git、Kaptain 与发布分支基础

目标：理解从 Kaptain 需求到功能分支、MR、release 日期分支、上线和回滚的最小工作流。

1. 先理解四个对象

对象作用你要记住什么
Kaptain 事项需求、任务或缺陷的来源。分支名、commit、MR 标题最好带事项 key，例如 COOAI-xxx，方便追溯。只有数字 id 时，先查出 key 和标题。
功能分支你开发需求的隔离分支。从当前团队约定基线拉出，开发完成后提 MR。
发布分支一次上线窗口的集成分支，常见格式是 release/YYYYMMDD。Confluence 中有自动创建 release/YYYYmmdd 的 Git 插件示例。
MR / Pipeline代码评审和自动检查入口。不要绕过 MR 直接推关键分支；上线前看 pipeline 和评审状态。
Kaptain 事项→ 功能分支→ MR 到目标分支→ 合入 release/日期→ 测试验收→ 上线

2. 基于 Kaptain 事项拉分支

Kaptain 链接里可能只有数字 id，也可能直接有 COOAI-xxx 这类 key。开发前先把事项查清楚：key、标题、目标仓库、目标上线日期。具体分支命名以团队当前约定为准；学习时先掌握这个原则：分支名必须能看出事项来源和改动目的。

# 示例：从最新 master 或团队指定基线拉需求分支
git fetch origin
git checkout master
git pull --ff-only
git checkout -b feature/COOAI-1234-add-tool-result

# 提交时也带事项号，方便 GitLab/Kaptain 追踪
git add .
git commit -m "feat(COOAI-1234): add tool result display"
git push -u origin feature/COOAI-1234-add-tool-result

不要凭记忆硬套 master、main、develop。进入具体仓库前，先看团队近期 MR 都合到哪里，以及当前发布分支是什么。

3. 合入 release 日期分支

发布分支通常表达一个上线日期，例如 release/20260617。Confluence 的 Git 插件实践文档里给过自动创建 release/YYYYmmdd 的例子，说明“按日期管理 release 分支”是内部常见做法之一。

# 如果 release 分支已经存在，基于远端创建本地分支
git fetch origin
git checkout -b release/20260617 origin/release/20260617

# 如果需要把功能分支变更带入 release，优先通过 GitLab MR
# 必须本地处理时，先确认团队允许 cherry-pick 或 merge
git cherry-pick <commit-hash>
方式适合场景风险
MR 合入 release常规上线、需要评审和 pipeline。需要处理冲突和评审等待。
cherry-pick 到 release只挑某几个 commit 上线，或从复杂分支里剥离改动。容易漏 commit；必须记录来源。
revert上线后快速回退某个 MR。GitLab 自动 revert 可能因后续提交冲突失败。

4. 回滚和补救的基本判断

Confluence 的 Release 分支回滚规范给了三个层级：

  1. 能用 GitLab Revert 就先用 Revert：最常规，链路清楚。
  2. 能用开关屏蔽就优先开关：如果代码可以通过配置关闭，先降低影响面。
  3. 复杂情况再 cherry-pick 重建分支：找需要剔除 commit 前的节点，逐个 cherry-pick 保留的 commit。

这也是为什么 commit 要小、要能追溯 Kaptain：上线后如果要拆掉某个改动，小 commit 比一个巨大混合 commit 好处理得多。

5. worktree 适合发布联调

Confluence 的 Git Worktree 文档建议：当你同时开发功能、处理 hotfix、验证 release 时，可以用 git worktree 开多个工作目录，避免频繁 stash。

git fetch origin
git worktree add ../ai-home-release-20260617 release/20260617
git worktree add -b feature/COOAI-1234 ../ai-home-COOAI-1234 origin/master
git worktree list

注意：每个 worktree 的 node_modules、.env、IDE 索引通常是独立的。前端仓库首次进入新 worktree 可能需要重新安装依赖。

6. 上线前自检

  1. Kaptain 事项号是否出现在分支、commit 或 MR 中。
  2. MR 目标分支是否正确：功能合主干，发布合 release/日期，hotfix 按团队约定走。
  3. Pipeline 是否通过，评审是否完成。
  4. 后端是否构建通过，前端是否 build / pub:build 通过。
  5. 测试是否在目标发布分支对应环境验收，而不是只验本地分支。
  6. 如果要回滚，是否优先考虑 Revert 或开关屏蔽。
问 agent：“根据这个 Kaptain 号和仓库，帮我检查当前分支、MR 目标分支、release 日期分支是否合理”，并贴 git status、git branch -vv、MR 链接。
