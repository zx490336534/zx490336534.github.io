056 PixiJS 渲染引擎与 Scene2D

掌握 viewer-2d 项目中 PixiJS 核心概念、Scene2D 渲染管线与视图注册机制

1. PixiJS 基础概念

PixiJS 是一个基于 WebGL（自动回退 Canvas 2D）的高性能 2D 渲染引擎。在 viewer-2d 项目中，我们使用内部封装的 @qunhe/pixi.js，它负责将户型数据渲染为可视化的 2D 图形。

为什么选 PixiJS

相比较原生 Canvas 2D API，PixiJS 提供了场景树（类似 DOM 树）、GPU 加速、内置交互（点击/拖拽）和纹理管理，非常适合渲染复杂户型图这种包含大量图元、需要频繁交互的场景。

1.1 Stage — 舞台

Stage 是整个 PixiJS 场景树的根节点。所有要显示的对象都必须挂载到 Stage 的子树上。你可以把它想象成 HTML 中的 <body>，是渲染的起点。

1.2 Container — 容器

Container 是一个可以包含子节点的"分组"对象。它本身不直接绘制像素，但能：

  • 对子节点做统一变换（平移、旋转、缩放）
  • 控制子节点的渲染顺序（z-index 由 children 数组顺序决定）
  • 作为逻辑分组（例如把所有门窗放在一个 Container，房间放在另一个）
// Container 的层级关系示意
Stage
├── RoomContainer        // 房间图元层
│   ├── room_01 (Graphics)
│   └── room_02 (Graphics)
├── DoorWindowContainer  // 门窗图元层
│   ├── door_01 (Sprite)
│   └── window_01 (Sprite)
└── AnnotationContainer  // 标注层
    └── dimension_line (Graphics)

1.3 Sprite — 精灵

Sprite 是基于纹理（Texture）的显示对象，用来渲染图片、图标等位图内容。在 viewer-2d 中，门窗图标、家具图例等通常用 Sprite 渲染。Sprite 是最轻量的显示对象，渲染性能最优。

1.4 Graphics — 矢量图形

Graphics 用于绘制程序化矢量图形：线段、矩形、圆弧、多边形、贝塞尔曲线等。在 viewer-2d 中，房间轮廓、墙体、尺寸标注线等都通过 Graphics API 绘制。

// 典型用法：绘制一个房间轮廓
const room = new PIXI.Graphics();
room.lineStyle(2, 0x333333);
room.beginFill(0xf0f0f0);
room.moveTo(0, 0);
room.lineTo(200, 0);
room.lineTo(200, 150);
room.lineTo(0, 150);
room.closePath();
room.endFill();
类型用途性能示例
Container分组 / 变换无渲染开销房间层、门窗层
Sprite位图渲染最优门窗图标、家具图例
Graphics矢量绘图中等（路径复杂时较慢）房间轮廓、标注线
Text文字渲染中等房间名称、尺寸数值

2. Scene2D 渲染管线

在 viewer-2d 中，Scene2D 不是一个普通的 PixiJS 场景，而是基于 KAF 框架的场景管理系统。它将 PixiJS 渲染能力与状态管理、实体系统、交互系统整合在一起。

关键入口文件

src/app/Scene2D/DfScene2d.tsx 是 Scene2D 的 React 组件入口。它的 onInit 回调中完成视图注册、系统注册和推理能力注册，是排查场景初始化问题的第一入口。

2.1 渲染管线总览

数据变化 (rootState) → StateManager 分发 → Entity 响应 → Drawable 更新 → PixiJS 渲染

整个管线的核心理念是数据驱动：React 视图层和 KAF StateManager 管理业务状态，状态变化触发 Entity（实体）更新，实体负责将自己的数据映射为 PixiJS 的显示对象（Drawable），最终由 PixiJS 完成 GPU 渲染。

2.2 状态与场景的桥梁

RootStateManager（src/app/state.ts）是全局状态的聚合点，它组合了多个子状态：

  • scene2D — 场景相关状态（缩放比、偏移量、激活工具等）
  • selectedControl — 当前选中的图元与变换状态
  • layout — 布局与自动排列状态
  • outside — 与父页面/外部容器的通信状态
  • leftPanel — 左侧面板 UI 状态

React 组件通过 connect() 函数订阅状态变化，而 Scene2D 内部的 Entity 和 System 则直接读取 StateManager 的数据来驱动渲染。

// 简化的数据流向
┌──────────────────────────────────────────┐
│  React 层 (App.tsx, views/)              │
│  connect() ← RootStateManager            │
└──────────────┬───────────────────────────┘
               │ dispatch / setRootState
┌──────────────▼───────────────────────────┐
│  RootStateManager (src/app/state.ts)      │
│  ┌─────────┬──────────┬────────┐         │
│  │scene2D  │selected  │layout  │ ...     │
│  └────┬────┴─────┬────┴───┬───┘         │
└───────┼──────────┼────────┼─────────────┘
        │          │        │
┌───────▼──────────▼────────▼─────────────┐
│  Scene2D / Entity / Drawable              │
│  PixiJS Stage → Container → Graphics     │
└──────────────────────────────────────────┘

3. 视图注册与更新

Scene2D 使用 KAF 框架的视图（View）概念来组织渲染逻辑。每个 View 负责一类图元的创建、更新和销毁。

3.1 视图注册

在 DfScene2d.tsx 的 onInit 中，各种视图被注册到场景中：

// DfScene2d.tsx onInit 中的典型注册
protected onInit() {
  // 注册房间视图
  this.registerView(RoomView);
  // 注册门窗视图
  this.registerView(DoorWindowView);
  // 注册标注视图
  this.registerView(DimensionView);
  // 注册系统（交互逻辑）
  this.registerSystem(SelectSystem);
  this.registerSystem(TransformSystem);
  // 注册推理能力
  this.registerInference(...);
}

3.2 View 的生命周期

阶段方法职责
初始化onInit创建 PixiJS 对象、设置默认样式、注册事件监听
更新onUpdate根据 Entity 数据变化更新 Drawable 的位置、样式、可见性
销毁onDestroy移除 PixiJS 对象、解绑事件、释放资源

3.3 实体与 Drawable 的绑定

每个业务实体（房间、门窗、标注）在 Scene2D 中对应一个或多个 Drawable（PixiJS 显示对象）。实体数据变化时，View 负责同步更新对应的 Drawable。

高风险提醒

修改实体类与 Drawable 的绑定关系属于高风险改动。绑定断裂会导致图元不显示或数据不同步。改动后必须手动验证：图元是否正常渲染、选中/拖拽是否正常、数据回写是否正确。

4. 性能优化

2D 户型渲染涉及大量图元，性能优化是开发中必须关注的重点。

4.1 渲染层面

  • 脏标记（Dirty Flag）：只在数据真正变化时才触发 Drawable 更新，避免每帧全量重绘
  • Container 分层：将不同更新频率的图元放在不同 Container 中，只重绘变化层
  • Graphics 缓存：对不常变化的矢量图形使用 cacheAsBitmap，减少 GPU 绘制调用
  • 纹理图集：将小图标合并为纹理图集（Sprite Sheet），减少纹理切换次数

4.2 交互层面

  • 碰撞检测优化：使用 hitArea 自定义碰撞区域，避免 PixiJS 遍历复杂路径
  • 事件节流：对 mousemove 等高频事件做节流处理，减少不必要的状态更新
  • 可见性裁剪：视口外的图元设置 visible = false，跳过渲染

4.3 状态层面

  • 批量更新：多处数据变化合并为一次 dispatch，避免连锁触发多次渲染
  • 浅比较：StateManager 使用浅比较判断是否需要通知订阅者，减少无效重渲染
最佳实践

新增图元时，优先考虑：1) 是否可以复用已有的 Container 层级；2) Drawable 更新是否可以在 onUpdate 中做增量 diff 而非全量重建；3) 事件监听是否可以挂在父 Container 而非每个子节点上。
