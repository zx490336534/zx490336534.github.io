一条条件更新保护两个并发编辑

看懂版本比较为何要和更新一起发生。

先看场景走一遍读代码复现失败动手练习自测

先看场景

两个人从版本 2 开始编辑。两次保存都先读取到 2；如果比较和写入分开，后到一方会覆盖更早发布。

比较并交换：只在数据仍和预期相符时更新。

走一遍

  1. 为编辑保留基础版本。
  2. 用一条条件更新比较基础版本并写入。
  3. 把零行更新当冲突而非成功。
合成示例 可折叠
import sqlite3

第二遍 · 把代码读懂

代码拆解

两个浏览器都显示版本 2，谁有权把结果写成版本 3？

调用链

  1. 读取基线版本。
  2. 写入时同时验证房间和原版本。
  3. 读受影响行数。
  4. 返回已写或冲突。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

import sqlite3
db = sqlite3.connect(":memory:")
with db:
    db.execute("CREATE TABLE layout(room TEXT PRIMARY KEY, revision INT, shape TEXT)")
    db.execute("INSERT INTO layout VALUES (?, ?, ?)", ("room-A", 2, "initial"))

def try_publish(room, base, shape):
    with db:
        changed = db.execute(
            "UPDATE layout SET revision = revision + 1, shape = ? "
            "WHERE room = ? AND revision = ?", (shape, room, base)
        ).rowcount
    return "written" if changed == 1 else "conflict-or-missing"

def read(room):
    return db.execute(
        "SELECT revision, shape FROM layout WHERE room = ?", (room,)
    ).fetchone()

baseline_a, baseline_b = read("room-A")[0], read("room-A")[0]
assert try_publish("room-A", baseline_a, "chair") == "written"
assert try_publish("room-A", baseline_b, "desk") == "conflict-or-missing"
assert try_publish("room-B", 3, "unknown") == "conflict-or-missing"
assert read("room-A") == (3, "chair")

前端版本是条件，不是结论

两个客户端的基线可以完全相同。数据库里的当前版本才决定一次发布是否可以成功。

比较与替换合成一步

示例用参数化 SQL 在同一条 UPDATE 里比较 room 与 revision，并同步修改数据和版号。单条语句证明原子条件；涉及多表时需要额外事务设计。

不要自动静默合并

冲突并不是网络超时，重试前需要重新读新版本并决定放弃、合并或重新编辑。返回版本差异比连续自动写有用。

复现失败

两个编辑器相同基线
怎么触发：A 写成功后 B 用旧版保存。
怎么判断：B 返回冲突，A 的结果不变。
写不存在房间
怎么触发：提供没有记录的房间。
怎么判断：不新建，不返回写成功。

写下这些测试断言

  • 只有第一次更新成功。
  • 后写没有额外增加版号。
  • 保存内容与更新后的版本属于同一条记录。

这一课带走：有并发时，判断和写入必须作为一次不可分割的更新。

动手练习

从同一版本发起两次发布，第二次收到冲突以后重新读取。

自测

保存前先查询版本，之后无条件写入安全吗？
