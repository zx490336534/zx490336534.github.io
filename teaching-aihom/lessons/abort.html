取消请求与防止旧结果覆盖

同时处理真正的取消和没有被及时取消的迟到响应。

先看场景走一遍读代码复现失败动手练习自测

先看场景

用户连续点两个房间。第一次任务的最慢回调可能在页面切换后仍执行。

AbortSignal：向异步工作传达取消的对象，而非保证远端已经撤销。

走一遍

  1. 新任务开始时取消旧请求。
  2. 捕获本地选择的递增令牌。
  3. 任何结果写入前核验令牌。
合成示例 可折叠
const assert = require("node:assert/strict");

第二遍 · 把代码读懂

代码拆解

为什么已经取消了请求，UI 还是可能恢复到旧选择？

调用链

  1. 显示新选择。
  2. 通知旧读取停止。
  3. 等待当前异步工作。
  4. 仅当前令牌允许写 UI。
JavaScript 示例 可折叠

可复制到 lesson.cjs，再运行 node lesson.cjs。

const assert = require("node:assert/strict");
let generation = 0, controller, shown;
function deferred() {
  let resolve;
  const promise = new Promise(done => { resolve = done; });
  return { promise, resolve };
}
async function restart(fetchLayout) {
  controller?.abort();
  controller = new AbortController();
  const token = ++generation;
  try {
    const value = await fetchLayout(controller.signal);
    if (token === generation) shown = value;
  } catch (error) {
    if (token === generation && error.name !== "AbortError") shown = "error";
  }
}
(async () => {
  const a = deferred(), b = deferred();
  let oldSignal;
  const p = restart(signal => { oldSignal = signal; return a.promise; });
  const q = restart(() => b.promise);
  assert.equal(oldSignal.aborted, true);
  b.resolve("second");
  await q;
  a.resolve("first");
  await p;
  assert.equal(shown, "second");
})().catch(error => { console.error(error); process.exitCode = 1; });

取消的作用范围

AbortController 控制支持该信号的工作。服务已经启动的任务不一定停止，生成按钮的取消语义应单独设计。

双重保护

取消减少无用工作，代际令牌约束结果能否提交。某些非 fetch 处理器忽略信号时，令牌仍然保护页面。

错误也要判归属

旧请求抛错不能覆盖当前请求的成功提示。示例捕获拒绝后同样检查令牌。

复现失败

旧处理器不认取消
怎么触发：第一次请求仍成功返回。
怎么判断：输出还是第二次。
旧请求迟到报错
怎么触发：第二次成功以后第一次拒绝。
怎么判断：不要覆盖当前成功状态。

写下这些测试断言

  • 重新开始后旧信号是 aborted。
  • 忽略信号的旧结果也不能提交。
  • 旧失败和旧成功同样不能覆盖当前代。

这一课带走：把取消理解为节省资源，把令牌理解为拒绝错误写入。

动手练习

让第一次 Promise 忽略 AbortSignal，观察它完成后 UI 是否仍显示第二次结果。

自测

有 AbortController 就能省掉回调归属检查吗？
