写入已成功，完成事件为何可能没发出

用同一事务存版本与待送事件，并练习重发与去重。

先看场景走一遍读代码复现失败动手练习自测

先看场景

后台保存成功后进程立刻退出，客户端仍在等推送；另一种情况是推送已送达但服务还没来得及记已送。

Outbox：存储业务变更时一并写待发送记录，之后另由发送者送出。

走一遍

  1. 在同一事务写布局和待送记录。
  2. 发送器独立读取未发送事件。
  3. 用稳定事件编号在消费端去重。
合成示例 可折叠
import sqlite3

第二遍 · 把代码读懂

代码拆解

如何同时避免保存后丢通知和重发时重复更新？

调用链

  1. 开始事务。
  2. 修改布局并写 outbox。
  3. 发送后记录送达。
  4. 同编号消息在消费端只影响一次结果。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("CREATE TABLE layout(rev INT); "
                 "INSERT INTO layout VALUES(2); "
                 "CREATE TABLE pending(event TEXT PRIMARY KEY, revision INT);")

def save(rev, fail=False):
    with db:
        db.execute("UPDATE layout SET rev = ?", (rev,))
        if fail:
            raise RuntimeError("stop before outbox")
        db.execute("INSERT INTO pending VALUES(?, ?)", (f"done-{rev}", rev))

try:
    save(3, fail=True)
except RuntimeError:
    pass
assert db.execute("SELECT rev FROM layout").fetchone() == (2,)
assert db.execute("SELECT COUNT(*) FROM pending").fetchone() == (0,)
save(3)
event = db.execute("SELECT event FROM pending").fetchone()[0]
consumed = set()
for delivery in (event, event):
    consumed.add(delivery)
assert consumed == {"done-3"}

同一事务消除半个结果

事件与业务行要么同在、要么同无。示例用 SQLite 的失败注入验证回滚，不能把事务跨越到外部消息系统。

重发正常，丢失才不可接受

写入成功而发送器没运行时，待送记录仍在。发送成功后未记送达，重启后可能再次发，所以不能声称严格一次传输。

去重记录需要稳定耐久

本示例用集合表达消费不变量；跨进程真实系统要在数据库中将去重和业务副作用原子提交。

复现失败

同一事务中断
怎么触发：布局写后、待送记录写前抛错。
怎么判断：保留原版本，不出现孤立更新。
确认前中断
怎么触发：同一事件被再次投递。
怎么判断：只能生效一次。

写下这些测试断言

  • 失败注入验证的是事务回滚，不是现场补数据。
  • 重新发送使用稳定同一事件编号。
  • 传输次数可能为二，业务生效次数为一。

这一课带走：让事件记录和业务结果一起落地；允许重发，然后在边界消除重复作用。

动手练习

写两次试验：一次在保存后停发；一次发送后停在确认前。
