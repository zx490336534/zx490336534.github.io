流式事件：断线、乱序与旧响应

给每个事件一个版本，用断线与乱序测试验证恢复。

先看场景走一遍读代码复现失败动手练习自测

先看场景

同一个页面可能有两次生成请求，第一条比第二条更晚完成。只看消息到达时间，会出现旧布局覆盖新布局。

快照：此刻的完整状态。错过了中间几条消息时，重读一次当前状态比猜测之前发生了什么更稳妥。

走一遍

  1. 用任务 ID 判断结果属于哪次运行，事件序号只在同一次运行里比较。
  2. 事件出现缺口时，向服务端重新读快照，而不是猜漏过了什么。
  3. 开始新任务后忽略旧任务消息；终态事件重复到达不得重复执行副作用。
合成示例 可折叠
if (e.taskId !== current.taskId || e.seq <= current.seq) return;
if (e.seq > current.seq + 1) return reloadSnapshot();
applyEvent(e);

第二遍 · 把代码读懂

代码拆解

生成进度先到 1，再到 3，重连时又收到 2。应该接受哪条？

调用链

  1. 服务为任务里的状态事件标上局部序号。
  2. 客户端先排除其他任务、重复或落后的序号。
  3. 遇到缺口时暂停消化新事件，启动一次快照读取。
  4. 只接收当前任务且不倒退的快照；若快照未覆盖缺口，继续补查。
JavaScript 示例 可折叠

可复制到 lesson.cjs，再运行 node lesson.cjs。

const assert = require('node:assert/strict');
const start = { run: 'room-run-A', seq: 1, phase: 'generating', want: 1 };
const syncing = (s) => s.want > s.seq;

function receive(s, event) {
  if (event.run !== s.run || event.seq <= s.seq) return s;
  if (syncing(s) || event.seq !== s.seq + 1) {
    return { ...s, want: Math.max(s.want, event.seq) };
  }
  return { ...s, seq: event.seq, want: event.seq, phase: event.phase };
}

function snapshot(s, state) {
  if (state.run !== s.run || state.seq < s.seq) return s;
  return { ...s, ...state, want: Math.max(state.seq, s.want) };
}

const gap = receive(start, { run: start.run, seq: 3, phase: 'ready' });
assert.equal(gap.phase, 'generating');
assert.equal(syncing(gap), true);
const partial = snapshot(gap, { run: start.run, seq: 2, phase: 'validating' });
assert.equal(syncing(partial), true);
const fixed = snapshot(partial, { run: start.run, seq: 3, phase: 'ready' });
assert.equal(syncing(fixed), false);
assert.equal(receive(fixed, { run: start.run, seq: 3, phase: 'ready' }), fixed);
assert.equal(snapshot(fixed, { run: 'other', seq: 99, phase: 'failed' }), fixed);

任务编号与版本是两道阀门

A 的第 8 条和 B 的第 2 条不属于同一把尺子。代码先比较 run 再比较 seq。否则一个以前的任务只要序号足够大，就能覆盖最新任务。

补查目标记录已看见的最高事件

本例选择不缓存所有事件，而只保存 want。看到第 3 条就记住要补到至少 3；期间如果见到第 5 条，恢复要求推到至少 5。由服务端快照重建状态，而不是把第 3 条的状态字段猜成完整状态。

快照也可能迟到

收快照时不仅校验任务身份，还比较快照序号。快照给的是全量，所以 seq 足够且数据契约满足时可直接替换；不够时维持 syncing。显示层在应用事件前也要检查负载结构。应用层要单飞、退避和设上限，不在每条重复通知上新开请求。

复现失败

缺号
怎么触发：当前为 1，直接收到 3，并暂时只读到序号 2 的快照。
怎么判断：先更新到快照 2，但仍需要再获取一次，不能宣布补齐。
重复终态
怎么触发：快照已经在 3，再收到两条 3。
怎么判断：状态不变；原先的发布动作不触发第二次。
连接切换
怎么触发：切到新任务后，旧任务的快照或事件才到。
怎么判断：都不能覆盖新任务。

写下这些测试断言

  • 序号 1 跳到 3 时，业务结果不直接变为 ready。
  • 快照 2 仍未达到追赶目标，快照 3 能恢复。
  • 回放重复终态或旧任务快照，结果保持不变。

这一课带走：推送改善反应速度；序号和快照决定断线后能否回到正确结果。

动手练习

造出序号 1、3、2、3，验证重新读取快照后没有倒退；再让旧任务晚到一次。
