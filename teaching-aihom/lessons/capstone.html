综合实战：布局生成到故障恢复

先看场景

从一个房间、两件虚构家具和一个假模型开始。每次只改变一个故障条件，再比较任务状态与两种视图。

验收证据：别人按你的步骤能复现，并且能看到预期结果；不是一句「我这边没问题」。

走一遍

  1. 正常路径：提交请求 → 看见任务状态 → 两个视图显示同一个版本。
  2. 恢复路径：连接中断后读取快照，重复完成事件不产生额外版本。
  3. 失败路径：假模型返回越界家具，校验失败后仍可查看旧布局。

代码拆解

调用链

  1. 建一个房间和已有版本 2，准备能切换的假生成器。
  2. 用独立任务编号保留每次调用的受理和完成证据。
  3. 用成功、坏草案、迟到事件、重复终态逐个破坏分支。
  4. 按任务状态、存储版本、二维与三维结果核对验收。

def view_state(revision):
    return {"plan": revision, "preview": revision}

def accept_terminal(state, event):
    if event["run"] != state["run"] or event["seq"] <= state["seq"]:
        return state
    if event["seq"] != state["seq"] + 1:
        return {**state, "status": "snapshot-required"}
    if not event["valid"]:
        return {**state, "seq": event["seq"], "status": "failed"}
    if event["revision"] <= state["views"]["plan"]:
        return {**state, "seq": event["seq"], "status": "failed"}
    return {
        **state, "seq": event["seq"], "status": "ready",
        "views": view_state(event["revision"]), "visible_updates": state["visible_updates"] + 1,
    }

before = {"run": "B", "seq": 1, "status": "generating",
          "views": view_state(2), "visible_updates": 0}
ok = {"run": "B", "seq": 2, "valid": True, "revision": 3}
ready = accept_terminal(before, ok)
assert ready["views"] == {"plan": 3, "preview": 3}
assert accept_terminal(ready, ok)["visible_updates"] == 1
assert accept_terminal(before, {**ok, "run": "A"}) == before
assert accept_terminal(before, {**ok, "seq": 3})["status"] == "snapshot-required"
assert accept_terminal(before, {**ok, "valid": False})["views"] == view_state(2)

先写验收表，再连细节

挑最有价值的观测点：页面当前任务、已展示版号、两张视图各自看到的版号、真正提交次数。只检查「出现绿色成功提示」会漏掉视图不同步或重复写入。

围绕可控输入做单变量对照

先用一条成功事件将版本从 2 切到 3。坏草案的场景只改变有效性，迟到的场景只换身份，重复终态只再次发送同一事件。一次改变越少，失败更容易定位。示例收端把版本号当作两个视图的共同输入锚点；实际测试还要分别从两张视图读取输出。

对照工程保证，不混同运行证据

回放两遍同一事件证明这个接收函数不会重复发布；不能据此宣称数据库跨进程不会重复。断线恢复应另测从旧快照启动、补查成功、旧事件重放三步；写后失联要跑状态图课的同键恢复。把各自验证过的层和未验证的边界记到结果。

复现失败

任务串线
怎么触发：当前运行 B，旧运行 A 先完成。
怎么判断：两张视图都不更新，当前任务仍是 B。
合法事件重放
怎么触发：连续送两遍同一个 B 的终态事件。
怎么判断：两张图一起切到 3，显示更新只发生一次。
结果不合规
怎么触发：用 B 的正确序号，但把草案标记为坏。
怎么判断：显示失败，两个视图都保持 2。
重连消息缺口
怎么触发：跳过第 2 条，直接接到 3。
怎么判断：触发补查而不切图，补到同任务最新快照才能恢复。

写下这些测试断言

  • 同一次成功更新使 plan 与 preview 同时是 3。
  • 重复与串线不产生额外显示更新；上一版仍可查看。
  • 失败和补查是不同状态；两者都不能偷换成成功。
  • 验收报告区分显示更新次数与真正存储提交次数。

这一课带走：交付一张故障说明表：怎么触发、看到什么、验证了哪一层、还有哪一层未验证。
