004 Spring 依赖注入 DI + 三层注解

本节目标：搞懂 Spring 最核心的魔法——对象不用你自己 new，Spring 会"喂"给你。看完后你能对着 AIHom 的一个 Controller + Service，说清"谁把谁注入了谁"。

先讲一个测试工程师最懂的痛点

假设没有 Spring。你写一个 ChatController，它要用到大模型客户端，于是你在构造方法里自己 new 一个：

public class ChatController {
    private final DashScopeChatClient client;

    public ChatController() {
        this.client = new DashScopeChatClient(
            "sk-xxx", "qwen-plus", new HttpExecutor()...);
    }
}
这种写法有三个致命问题

① 耦合死。Controller 死死绑定了 DashScopeChatClient 这个具体实现。哪天要换成 OpenAI，得改这个类的代码。
② 难测试。（这是你的主场）你想对 Controller 写单元测试，但它内部直接 new 了一个真的会去联网调大模型的客户端。你想换成"假的、返回固定结果"的 mock？改不了，因为 new 写死在构造方法里。
③ 重复造。十个类都要用客户端，就 new 十次，配置散落十处。

测试工程师视角：依赖注入 = 测试福音

要解决"难测试"，核心思路是：不要在类内部自己造依赖，而是让外部把依赖传进来。这样测试时，你就能传一个假实现（mock）进去，不用真的去调大模型。这个"由外部传入依赖"的机制，就叫依赖注入（Dependency Injection，简称 DI）。Spring 就是干这件事最成熟的工具。

依赖注入：你只声明"我要什么"，Spring 负责造好递给你

回到 001 课的那段代码，现在你能看懂它最关键的一行了：

@RestController
public class ChatController {

    private final ChatClient.Builder builder;

    public ChatController(ChatClient.Builder builder) {  // ← 这里没 new！
        this.builder = builder;
    }
}

注意看构造方法的参数 ChatClient.Builder builder——Controller 自己从来没有 new 这个 builder。它只是"声明"：我需要一个 ChatClient.Builder。真正把它造好、并塞进来的，是 Spring 容器。你写一个 new ChatController(???) 都不用，Spring 帮你调构造方法、帮你找好参数。

DI 的心智模型（一句话版）

你只管"点菜"，Spring 当"服务员"。Controller 说"我要 ChatClient.Builder"，Spring 就去厨房找有没有这个对象，有就端上来。你不用知道厨房在哪、怎么做。

两种注入姿势：构造注入（推荐） vs 字段注入

把依赖传进来，有两种主流写法：

// 写法 A：构造注入（★ 官方推荐，AIHom 里几乎都是这种）
@RestController
public class ChatController {
    private final ChatService service;

    public ChatController(ChatService service) {   // 通过构造方法传
        this.service = service;
    }
}

// 写法 B：字段注入（老代码里会看到，现在不推荐）
@RestController
public class ChatController {
    @Autowired                                   // 在字段上贴注解
    private ChatService service;            // 没有构造方法，Spring 反射直接塞
}
为什么构造注入更好

① 依赖能写成 final，对象一造好就不会变，更安全；② 不依赖 Spring 也能 new 出来测，直接 new ChatController(fakeService) 就能跑单测——这对测试工程师是天大的好事；③ 一眼看清这个类到底依赖了什么。看 AIHom 代码时，默认按构造注入理解就行。（注：@Autowired 这个词你会经常见，它就是"请 Spring 帮我注入"的开关；Spring 4.3 之后，如果类只有一个构造方法，构造注入可以省略 @Autowired。）

什么是 Bean：被 Spring 容器管理的对象

既然 Spring 要"端菜上桌"，那它厨房里得有菜。这些被 Spring 统一造好、统一保管、随时能拿出来的对象，有一个专门的名字——Bean。

Bean 的大白话定义

Bean = 一个普通的 Java 对象，但它不是你 new 出来的，而是由 Spring 容器创建并管理的。它和普通对象的区别只有一个：谁来管它的生老病死。你自己 new 的，你自己管；Spring 造的，就是 Bean，归 Spring 管。

那 Spring 怎么知道哪些类该变成 Bean？答案是——靠"三层注解"打标签。你给一个类贴上特定注解，Spring 启动时扫到，就把它登记进容器，变成一个 Bean，以后谁需要就注入给谁。

三层注解族：给类贴标签，让它成为 Bean

还记得 001 课那张"三层归属表"吗？里面 @RestController、对象自动被传进来，都归 Spring 那一层。这一节，我们正式讲清 Spring 这一层。

注解用在哪一层大白话
@RestController / @Controller 接口层（接 HTTP 请求） 最外层门面，负责接收 HTTP 请求、返回结果。@RestController = @Controller + 默认返回 JSON。AIHom 几乎全用前者。
@Service 业务逻辑层 真正干活的地方。编排各种操作、写核心业务规则。AIHom 里调大模型、走 Agent 的逻辑都在这层。
@Repository / @Mapper 数据访问层 和数据库打交道的。@Repository 是 Spring 自带；@Mapper 是 MyBatis 的，AIHom 里也常见。
@Component 通用组件 不知道归哪层、但又想被 Spring 管的"工具类"，就用它。是上面几个的"祖宗"——它们本质都是 @Component。
@Configuration 配置类 专门用来"手动造 Bean"的类（通过 @Bean 方法）。第三方库的对象没法贴注解，就靠它在配置类里 new。
一句话记住它们的关系

这五个注解本质都是一回事——告诉 Spring"把这个类注册成一个 Bean"。区别只在语义/角色：贴 @Service 是在跟读代码的人说"这是业务层"，贴 @RestController 是在说"这是接口层"。从"变 Bean"的角度看，它们效果一样。

看懂 AIHom 的依赖关系：一个 Controller + Service

下面是一段贴近 AIHom 真实风格的代码。一个 ChatController（接口层）依赖一个 ChatService（业务层），而 ChatService 又依赖 Spring AI 的 ChatClient。串起来看：

// ① 接口层：接 HTTP 请求
@RestController
@RequestMapping("/ai")
public class ChatController {

    private final ChatService chatService;          // 声明依赖

    public ChatController(ChatService chatService) {  // 构造注入
        this.chatService = chatService;
    }

    @PostMapping("/chat")
    public String chat(@RequestBody String question) {
        return chatService.ask(question);    // 把活儿甩给业务层
    }
}

// ② 业务层：真正调大模型的地方
@Service
public class ChatService {

    private final ChatClient chatClient;          // Spring AI 提供的

    public ChatService(ChatClient chatClient) {  // 构造注入
        this.chatClient = chatClient;
    }

    public String ask(String q) {
        return chatClient.prompt().user(q).call().content();
    }
}

读这段代码时，脑子里要有一张"谁注入谁"的关系图：

Spring 容器造好 ChatClient（Bean）→ 注入给 ChatService（Bean）→ Spring 容器再造好 ChatService（Bean）→ 注入给 ChatController（Bean）→ Spring 容器再造好 ChatController（Bean）→ 准备接 HTTP 请求。

整个链条里，没有任何一个 new。每个类只在构造方法里声明"我要什么"，Spring 按依赖顺序把它们一个个造好、串起来。这就是 DI 的全貌。

测试视角再回味一遍

正因为 ChatController 通过构造方法拿 ChatService，你写单测时完全可以 new ChatController(fakeService)，传一个不联网、秒回固定字符串的假 Service 进去，瞬间就能测接口逻辑——不用起服务、不用调真大模型。这就是 DI 给测试带来的红利。

一个容易混的点（提前打预防针）

你会看到 @Bean 和 @Component / @Service 长得很像，都跟"变 Bean"有关。区别：@Component 类贴在类上，让你自己的类变 Bean；@Bean 贴在 @Configuration 类里的方法上，让"方法的返回值"变 Bean（用来造第三方库的对象）。本节先有个印象，005 课讲自动配置时还会再遇到。
