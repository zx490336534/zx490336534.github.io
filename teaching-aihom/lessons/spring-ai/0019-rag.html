019 RAG 检索增强生成

本节目标：搞懂为什么直接问大模型常常"一本正经胡说"，以及 RAG 如何用"先查资料再答"的两段式流程解决它。课后你能用自己的话讲清楚这两段流程各自干什么。

为什么需要 RAG：大模型其实在"凭记忆答"

先想一个你会遇到的真实现象：你问通义千问"我们公司 AIHom 项目的户型校验规则是什么"，它大概率会一本正经地编一个看起来很合理、实际完全不存在的答案。

这不是模型坏掉了，是因为它的训练数据里根本就没有你们公司的私有资料——户型规范、内部知识库、最新的产品文档，它统统没见过。它只能"凭着自己读过的相似东西"硬猜，这就是业内说的"幻觉"（hallucination）：一本正经地胡说八道。

直接问大模型的两个硬伤

① 不知道私有数据——你公司内部的资料，它从没学过。
② 不知道最新知识——模型有训练截止日期，之后发生的事它都不知道。
硬把私有资料全塞进 prompt？一是塞不下（上下文窗口有限），二是太贵（每次都把整本规范传一遍）。

RAG 一句话定义

RAG = Retrieval-Augmented Generation，检索增强生成。大白话：回答之前，先去你的资料库里把相关的那几段查出来，然后把这几段连同问题一起交给大模型，让它"看着资料"作答。就像你考试允许翻书——不是背全本，是按问题翻到对应页再答。

RAG 全流程：两段，务必画清

RAG 分成两段完全不同的阶段，新人最容易混。一段是提前把资料存进去（离线，做一次或偶尔做），一段是每次提问时实时查（在线，每个用户请求都走）。

第一段：写入（离线，提前准备资料）

把你的私有资料"消化"进向量库，只做一次（或资料更新时再做）

  你的文档（户型规范.pdf / 素材库.md / 内部 wiki）
        │
        ▼
  ┌──────────────┐
  │ ① 分块 Chunk │   // 把长文档切成一小段一小段（如每段 500 字）
  └──────────────┘
        │
        ▼
  ┌───────────────────┐
  │ ② Embedding 向量化 │  // 用向量模型把每段文字变成一串数字（向量）
  └───────────────────┘
        │
        ▼
  ┌────────────────────┐
  │ ③ 存进 VectorStore │  // 把"文字 + 向量"一起存进向量数据库
  └────────────────────┘

第二段：查询（在线，每次提问都走）

用户每次提问，实时走这条链路

  用户问题："小户型能用岛台吗？"
        │
        ▼
  ┌───────────────────┐
  │ ④ Embedding 向量化 │  // 把问题也变成向量（和写入时用同一个模型！）
  └───────────────────┘
        │
        ▼
  ┌─────────────────────────┐
  │ ⑤ 相似度检索 top-k       │ // 在向量库里找和问题最接近的 k 个片段
  │   （比如 top-3 最相关）   │
  └─────────────────────────┘
        │
        ▼
  ┌─────────────────────────┐
  │ ⑥ 拼进 Prompt            │ // 把检索到的片段 + 问题一起塞给大模型
  └─────────────────────────┘
        │
        ▼
  ┌──────────────┐
  │ ⑦ 大模型生成 │   // 看着资料，生成靠谱回答
  └──────────────┘
最关键的一句话

写入和查询必须用同一个 Embedding 模型。否则问题变成的向量和资料变成的向量不在同一个"坐标系"里，相似度就比不了——就像拿中文地址和英文地址比"远近"，没法比。

两个关键组件，缺一不可

组件干什么AIHom 对应
EmbeddingModel 把一段文本变成一个高维向量（一串数字）。文本越相似，向量越接近。 DashScope 提供的向量模型（通义千问体系内，如 text-embedding-v2）
VectorStore 把"文本 + 向量"存起来，并支持按相似度检索 top-k（给一个向量，返回最像的几个）。 常见选型：PgVector（Postgres 插件）/ Milvus / Redis Stack。Spring AI 都有 starter。
这两个名字记牢

以后看 AIHom 代码，只要出现 EmbeddingModel / VectorStore 这两个类型，基本就是在做 RAG。这是 Spring AI 1.1.x 里 RAG 的两个核心抽象。

"相似度检索"的直觉：文本变成空间里的点

把一段文字变成向量，本质是把它放到一个高维空间里某个点。语义相近的文字，点就靠得近。

想象一个简化的二维空间（真实是上千维，但直觉一样）：

        "小户型怎么设计收纳"
              ●  ← 用户问题
             ╱
            ╱   ← 距离近 = 相关
           ●  "小户型收纳技巧十条"      ★ top-1
          ●  "60平米的储物方案"         ★ top-2

                                                  ●  "汽车发动机保养"
                                                  ← 距离远 = 不相关，检索不到

检索 top-k，就是在空间里找离问题最近的 k 个点，把它们对应的原文片段捞出来。模型不需要"懂"语义，几何距离替它懂了。

Spring AI 里它长什么样（只需感受，不必记）

下面是配置的样子，重点感受"DashScope 提供向量模型 + 某个 VectorStore 存"这个组合，不用背 API：

# application.yml —— 配 DashScope 向量模型 + PgVector 向量库
spring:
  ai:
    dashscope:                       # 通义千问（提供文本模型 + 向量模型）
      api-key: ${DASHSCOPE_API_KEY}
    vectorstore:
      pgvector:                      # 用 Postgres 的 PgVector 插件当向量库
        dimensions: 1536            # 向量维度，要和向量模型对齐
        distance-type: COSINE_DISTANCE  # 用余弦相似度比远近
// Java 侧：注入两个核心抽象，Spring AI 自动装配好实现
@RestController
public class RagController {

    private final EmbeddingModel embeddingModel;   // 文本 → 向量（DashScope 实现）
    private final VectorStore vectorStore;        // 存向量 + 相似度检索（PgVector 实现）
    private final ChatClient chatClient;           // 最后负责生成回答

    // 构造方法注入，省略

    @GetMapping("/rag")
    public String ask(@RequestParam String q) {
        // ⑤⑥ Spring AI 把"检索 + 拼 prompt"封装成了简洁的链式调用
        return chatClient.prompt()
            .user(q)
            .defaultAdvisors(new QuestionAnswerAdvisor(vectorStore))
            .call()
            .content();
    }
}
这里你只需记住一件事

QuestionAnswerAdvisor(vectorStore) 这一行，就是 Spring AI 把"⑤ 检索 + ⑥ 拼 Prompt"两步打包好的开关。加上它，每次提问就自动先去向量库查资料、再喂给模型。具体细节后面的实战课（0061-aihom-hands-on）会动手跑。

联想 AIHom：哪类功能会用到 RAG

用 RAG 的判断标准很简单："这个答案大模型本来不知道，但在我们公司资料里有"。AIHom 里大概率出现的场景：

  • 知识库问答——运营整理的常见问题、设计规范，让 AI 查着答，而不是凭空编。
  • 素材库检索——给一段需求描述，去素材库里找匹配的模型/贴图/案例。
  • 户型 / 设计规范——"这个户型能不能放双人床"，先查规范条款，再让模型基于条款作答。
  • 历史工单 / case 复用——相似问题找历史解决方案。

反过来，"常识问答""翻译""润色"这类大模型本来就会的，就不需要 RAG，直接问更快更便宜。
