018 Tool Calling + MCP

本节目标：搞懂大模型为什么只会"说话"不会"动手"，Tool Calling 怎么补上这个能力；MCP 是什么、为什么像 USB-C；以及 AIHom 为什么把 Tool 委托给前端执行——一个非常有意思的架构选择。

大模型有个致命短板：它只会"说话"

前面几课你已经能让通义千问聊天、流式输出、返回结构化 JSON 了。但想象一个真实场景：用户在 AIHom 里问 "帮我看一下订单 1024 的状态"。

大模型能干啥？它只能猜——"订单 1024 可能是已发货、也可能是待付款……"。它查不到你的真实数据库，调不了公司内部的订单接口，更画不出一张 2D 户型图。

说白了：大模型是一个被关在小黑屋里、只读过公开互联网的超级大脑。它没有手、没有眼睛、够不着你公司的任何系统。

Tool Calling 一句话定位

Tool Calling（函数调用）让你把自己的 Java 方法"递"给大模型，模型自己判断什么时候要调、传什么参数。模型负责决策，你的方法负责执行，结果再喂回模型继续生成回答。模型从"只会说"升级成"会动手"。

第一步：用 @Tool 声明一个工具

在 Spring AI 1.1.x 里，声明一个工具非常直白——写一个普通 Java 方法，加上 @Tool 注解，写清楚这个工具是干嘛的（这句话很关键，模型就是靠它决定要不要调用）。

import org.springframework.ai.tool.annotation.Tool;

public class OrderTools {

    @Tool(description = "根据订单号查询订单的当前状态。输入订单号(数字)，返回状态文字。")
    public String getOrderStatus(long orderId) {
        // 这里是普通的 Java 代码：查数据库、调接口，随你
        return orderService.findById(orderId).getStatus();
    }

    @Tool(description = "根据房间尺寸生成一张 2D 平面图。输入宽和高(米)，返回图片地址。")
    public String generateFloorPlan(double width, double height) {
        // 实际的画图逻辑
        return renderService.draw(width, height);
    }
}
小白关键点：description 是写给模型看的

description 不是写给人看的注释，而是模型的说明书。模型用它判断"用户这句话要不要调这个工具、参数怎么填"。描述写得越清楚、越具体，模型调用就越准。这叫 Prompt Engineering for Tools——一种新的提示词工程。

然后在使用 ChatClient 时，把这个工具挂上去：

String answer = chatClient.prompt()
    .user("帮我查一下订单 1024 发货了没")
    .tools(new OrderTools())          // ★ 把工具交给模型
    .call()
    .content();

注意：你没有写任何 if (问题提到订单) { 调 getOrderStatus }。要不要调、怎么调，模型自己决定。这就是 Tool Calling 的魔力。

Tool Calling 的回路：画清这五步

模型调用工具不是一步到位的，而是一个回路。理解这个回路，是本课的核心。想象用户问"订单 1024 发货了没"：

用户提问                          ① "订单 1024 发货了没"
   │
   ▼
大模型思考 ────────────────────────  ② 模型判断：这问题我答不了，需要查订单
   │                                     决定调用工具 getOrderStatus(orderId=1024)
   ▼
你的 Java 方法被执行 ──────────────  ③ Spring AI 自动调用你的 getOrderStatus(1024)
   │                                     返回结果："已发货，顺丰 SF1234"
   ▼
结果喂回大模型 ────────────────────  ④ Spring AI 把工具结果再丢给模型
   │
   ▼
模型生成最终回答 ──────────────────  ⑤ "您的订单 1024 已经发货啦，顺丰单号 SF1234"
测试工程师视角的提醒

注意第 ③ 步——真正的业务逻辑（查数据库、调接口）发生在你自己的 Java 方法里，不在大模型那。以后你排查"为什么工具没被调用""为什么结果不对"，要分清是模型决策错（第②步）还是方法执行错（第③步），这两类 bug 的排查方向完全不同。

回路可以转好几圈

模型不限于调一个工具。它可能调 A，看结果不够，再调 B，甚至调 A 好几次。这个"思考→调用→看结果→再思考"的循环，就是后面 Agent（0011 课）的本质。现在先记住这个回路，Agent 只是把它放大了。

MCP：把工具标准化，像 USB-C 一样

Tool Calling 解决了"模型能不能调你的方法"。但很快出现一个新问题：

每个项目都在重复造工具。A 项目写了个查天气工具，B 项目想要同样的功能，得复制一遍代码。换成 Python 写的应用想用？对不起，Java 工具它用不了。

MCP（Model Context Protocol，模型上下文协议）就是为了解决这个。它把"工具/资源"标准化成一套统一协议，让工具能跨应用、跨语言复用。

最好的类比：USB-C

想想 USB-C 接口出来之前有多乱——安卓 Micro-USB、苹果 Lightning、相机各种专用口，充电器互不通用。USB-C 一统江湖后，一根线充手机、充笔记本、接显示器都行。

MCP 之于 AI 工具，就是 USB-C 之于电子设备：任何 MCP Server（提供工具的一方）都能被任何 MCP Client（使用工具的大模型应用）直接调用，不用关心对方用什么语言写的。

概念类比在 MCP 里的角色
MCP Server USB-C 设备（比如 U 盘） 提供工具/资源的一方。把能力按 MCP 协议暴露出去。
MCP Client USB-C 接口的电脑 使用工具的一方。大模型应用（比如你的 AIHom）作为 Client，去连 Server 拿工具。
MCP 协议 USB-C 电气标准 双方遵守的统一通信规则。具体在 Spring AI 里走 HTTP（SSE/WebMVC）或 stdio 传输。
Spring AI 1.1.x 里 MCP 的位置

Spring AI 把 MCP 当成一等公民：你可以写一个 @Tool 方法，然后通过 starter 自动把它暴露成 MCP Server；也可以让 ChatClient 作为 MCP Client 去连远端的 MCP Server。Tool Calling 和 MCP 在 API 层面是打通的——模型不关心工具是本地方法还是远端 MCP 服务，调用方式一样。

★ AIHom 的架构选择：部分 Tool 由前端执行

这是本课最值得讲的部分，也是 AIHom 区别于普通 Spring AI 项目的关键设计。先看 AIHom 的真实加载方式：

Coops / Nacos 配置
  agent-base.json
  model.json
  prompt-{promptKey}.json
  mcp-servers.json
  agent-skill.json

后端构建 Agent 时加载工具
CustomNacosReactAgentBuilder
  -> CustomNacosMcpGatewayToolsInitializer
  -> ToolCallback 列表
  -> AgentLlmNode / AgentToolNode

更准确地说：AIHom 后端 Agent 会从 Coops/Nacos 读取 MCP Server 配置，把工具转换成 ToolCallback。普通 MCP 工具由后端 callback 执行；如果工具协议是 postmessage，就会创建 FrontendNacosMcpGatewayToolCallback，真正执行交给前端页面。

整个回路长这样：

用户在 AIHom 前端输入           "帮我把这间卧室的墙刷成浅蓝色"
   │
   ▼
前端 ──WebSocket/HTTP──▶ AIHom 后端 Agent
                    │
                    │  AgentLlmNode 把工具的 name/description/inputSchema 发给大模型
                    ▼
               大模型 (通义千问)
                    │
                    │  模型决定调用工具 paintWall(room, color)
                    ▼
               AIHom 后端
                    │
                    │  AgentToolNode 匹配到 postmessage ToolCallback
                    │  PostMessageToolInterceptor 抛出 POST_MESSAGE 中断
                    ▼
前端 (浏览器) ◀──WebSocket tool_call──  收到"执行 paintWall"指令
   │
   │  前端真正执行：操作 Canvas / WebGL 渲染、改 3D 场景材质
   ▼
执行结果 ──WebSocket tool_response──▶ 后端续跑 Agent ──▶ 大模型 ──▶ 最终回答给用户
为什么这么设计？这是本课最关键的理解

因为渲染 2D/3D、操作画布的能力只在前端有。后端是 Java 进程，它画不了图、动不了浏览器里的画布。用户说"把墙刷蓝"，真正能让墙变蓝的代码在前端的 Canvas/WebGL 里。

所以 AIHom 的做法是：大模型仍然只看见普通 ToolDefinition；后端 Agent 负责加载工具、暴露工具定义、匹配 tool_call；遇到 postmessage 工具时，执行体跨越网络边界，落到前端浏览器里。WebSocket 负责承载 tool_call 和 tool_response。

测试工程师视角：这个架构对测试意味着什么

这个设计影响你的测试策略：
• 工具的定义和描述来自 Coops/Nacos 与 MCP Server 详情（要测：模型能不能正确识别工具）；
• postmessage 工具的真正执行在前端（要测：前端收到 WebSocket 指令后渲染对不对）；
• 中间的 WebSocket 通道是新的测试重点（断线重连、消息格式、超时）。

这比传统的"接口测试"复杂一层——你要测的是一个跨前后端、跨网络的工具调用链路。这也是 AIHom 这类 AI Native 应用和普通 Web 应用最大的区别。

本节你获得的胜利

现在你能向同事讲清三件事：Tool Calling 让模型从"只会说"变成"会动手"；MCP 像 USB-C，把工具标准化成跨应用复用的协议；AIHom 的 postmessage Tool 会委托给前端执行，因为真正的渲染能力只在前端。这三句话就是 AIHom 整个 AI 能力链路的地基——下一课讲 RAG，再下一课讲 Agent，都会反复用到这套"模型决策 + 工具执行"的模式。
