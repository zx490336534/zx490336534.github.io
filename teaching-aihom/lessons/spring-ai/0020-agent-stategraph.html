AIHom 全栈学习 · 第 020 课 · Agent 与 StateGraph

020 Agent + StateGraph / Graph

本节目标：看懂 AIHom 的"大脑"是怎么搭出来的。区分 Agent 和一问一答，理解 StateGraph/Graph 用"有向图"来编排 AI 流程，并能在一张图里指出节点、边、状态分别是什么。

先回顾：一问一答 vs 自主 Agent

你在 016 课 学的 ChatClient.prompt().user(q).call().content()，是典型的一问一答：你问一句，模型答一句，结束。它没有"下一步"的概念。

但现实任务不是这样的。比如用户对 AIHom 说："帮我把这个户型图画成 3D"。一个聪明的助手会自己拆步骤：

# 一问一答：一锤子买卖
你 → ChatClient → 模型 → 回答（结束，没有下一步）

# Agent：会自己想"下一步该干嘛"
你 → Agent → 模型: "我得先调用识图工具"
                ↓
          调 识图工具
                ↓
          模型: "识别完成，现在调画图工具"
                ↓
          调 画图工具
                ↓
          模型: "画完了，把结果回复用户"
                ↓
          → 你（结束）
Agent 的一句话定义

Agent 是能自主多步推理、并在需要时调用工具来达成目标的 AI。关键区别在于"自主多步"——它自己决定接下来调模型、调工具、还是直接回用户，而不是你一次性问完就结束。

测试工程师视角

Agent 的"多步"意味着一次对话可能触发好几次模型调用和好几个工具调用。以后你测一个 Agent 接口，看到的耗时是多步累加的——这是排查"为什么这么慢"的起点。

Spring AI Alibaba 的 Agent 框架

回忆 015 课：AIHom 真正的核心是 Spring AI Alibaba 1.1.2.0.5-qh（群核定制版），它扩展了底层的 Spring AI。Agent 框架就在这一层。它能干三件事：

能力谁提供大白话
定义一个 Agent Alibaba 声明一个"有目标的 AI 角色"，给它挂上系统提示词和工具。
挂载工具（Tool / MCP） Alibaba + Spring AI 018 课学过的 Tool Calling / MCP Server，就是给 Agent 用的"手脚"。
多个 Agent 协作（Supervisor 模式） Alibaba 一个"主管 Agent"（Supervisor）负责分配任务给多个"打工人 Agent"，各司其职。AIHom 里就有 Supervisor。
这里点到为止，别深挖源码

Agent 框架的源码细节（怎么注册、怎么路由）对小白现阶段是负担。你只要记住："Agent = 目标 + 提示词 + 工具 + 自主决策"，且 AIHom 用的是 Spring AI Alibaba 的实现就够了。下一节真正的主角，是把这些 Agent 和步骤串起来的东西——Graph。

StateGraph / Graph：AIHom 编排的核心 ★

这是整条学习路线最重要的一节内容。无论 Agent 多智能，它"先干嘛再干嘛"的流程，在代码里是用 StateGraph / Graph 来描述的。Spring AI Alibaba 提供了 StateGraphFactory / StateGraphBuildFactory 这套 API，AIHom 的编排核心就是它们。

核心思路一句话：把复杂的 AI 流程画成一张"有向图"。图里有三种东西：

① 节点（Node）= 一个步骤

每个节点干一件事：调一次模型、调一个工具、做一个判断、或者停下来等人介入（人机交互）。你可以把节点想成流程图里的方框。

② 边（Edge）= 步骤之间的流转

边连接两个节点，表示"做完 A 就去做 B"。最有用的是条件边（Conditional Edge）——满足某个条件走 A，否则走 B。这就是分支判断，像 if/else，但被图化了。

③ 状态（State）= 节点之间传递的"背包"

每个节点处理时，都从 State 里读输入（用户消息、中间结果、工具返回值），处理完再把新结果塞回 State，传给下一个节点。State 像一个在节点之间传递的共享背包。

一个生活类比

想象你在医院看病：节点是"挂号→门诊→抽血→出报告→复诊"，条件边是"报告异常？是→进专项检查，否→直接开药回家"，State 是你手里那个病历本——每经过一个科室就被写上一笔，下一个科室看着它继续。

为什么非要用 Graph，不能堆 if-else 吗？

能，但很快就崩溃。AIHom 这种业务流程的特点是：多步骤、有分支、还要人机交互（比如画完图要用户确认才继续）。如果全写成 if-else 嵌套，几层下来就没人看得懂了。

场景堆 if-else用 Graph 编排
看清整体流程 要在几百行代码里跳来跳去 看一张图，一眼就懂
加一个分支 改一堆嵌套，怕改崩 加一个节点 + 一条边，互不影响
人机交互暂停/恢复 要自己维护状态、自己续上 Graph 框架内置，State 自动带上
多人协作维护 互相踩脚 每人负责几个节点，边界清晰
这就是 StateGraphFactory 在干的事

AIHom 里那些 StateGraphFactory / StateGraphBuildFactory，本质上就是用代码定义这张图：声明有哪些节点、节点之间怎么连、哪个地方要条件分支、State 里装哪些字段。你看懂了这三件事，就读懂了 AIHom 的编排主干。

一张极简 Graph 长什么样

来个具体场景：用户说一句话，助手要先理解意图，判断"要不要画图"，是就调画图工具，否则直接回复。用 Graph 画出来是这样：

┌─────────┐
│  START  │   用户消息进入 State
└────┬────┘
     ▼
┌──────────────────┐
│ 节点 A：调通义千问 │   理解意图，输出 "need_draw=true/false"
│   (understand)    │   写入 State
└────────┬─────────┘
         ▼
   ◇ 条件边: need_draw ?
      ┌───┴───┐
    是▼       否▼
┌──────────┐  ┌──────────┐
│节点 B:    │  │节点 C:    │
│调画图工具 │  │直接回复   │
└─────┬────┘  └─────┬────┘
      ▼               ▼
┌──────────────────────┐
│  节点 D：组装最终回复  │   从 State 取结果 → 回用户
└──────────┬───────────┘
           ▼
       ┌─────┐
       │ END │
       └─────┘

下面是对应的概念性伪代码（不是真实 AIHom 代码，只为让你看清结构）：阅读时对照上面的图，找节点、找边、找条件。

// 概念性伪代码，展示 StateGraph 的"声明式"写法
StateGraph graph = new StateGraph()

    // ① 声明节点（每个节点 = 一个步骤）
    .addNode("understand", node -> {           // 节点 A
        String reply = chatClient.call(state.userMsg);
        state.put("need_draw", parseIntent(reply));
    })
    .addNode("draw", node -> {                  // 节点 B
        String img = drawTool.run(state.userMsg);
        state.put("image", img);
    })
    .addNode("reply", node -> {                  // 节点 C
        state.put("answer", "好的，已理解您的需求。");
    })
    .addNode("finish", node -> {                 // 节点 D
        state.put("finalReply", assemble(state));
    })

    // ② 声明边（先走 understand）
    .addEdge(START, "understand")

    // ③ 条件边：看 need_draw 决定走 B 还是 C
    .addConditionalEdges("understand", state -> {
        return state.get("need_draw")
             ? "draw"      // 是 → 节点 B
             : "reply";    // 否 → 节点 C
    })
    // ④ B 和 C 都汇到 finish，再到 END
    .addEdge("draw",   "finish")
    .addEdge("reply",  "finish")
    .addEdge("finish", END);
图里的元素伪代码里对应归谁管
节点（步骤） addNode("名字", 节点逻辑) Alibaba Graph
普通边（A→B） addEdge(A, B) Alibaba Graph
条件边（满足走 A，否则走 B） addConditionalEdges(节点, 判断函数) Alibaba Graph
状态（在节点间传递） 那个 state 变量，节点往里 put / 从里 get Alibaba Graph
调模型 / 调工具的真实动作 节点 lambda 里的 chatClient.call、drawTool.run Spring AI + Alibaba
读图三步法（拿去拆 AIHom 任何一段编排）

第一步：找出所有 addNode —— 这就是全部步骤；第二步：找出 addEdge 和 addConditionalEdges —— 这就是流程和分支；第三步：盯 state 里 put 了啥、get 了啥 —— 这就是数据怎么流动。三步走完，主干就清楚了。
