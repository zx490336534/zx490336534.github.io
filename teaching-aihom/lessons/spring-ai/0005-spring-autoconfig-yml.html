005 Spring Boot 自动配置 + starter + yml

本节目标：看懂 AIHom 里那句"加一个依赖就能用"的魔法——什么是 starter、自动配置到底在背后做了什么、application.yml 里那一堆 spring.ai 配置项各自管什么，以及 AIHom 为什么要把配置分散到 toad / Nacos / MySQL 三处。

先感受一下"魔法"

上一课讲了"依赖注入"——你不用自己 new 对象，Spring 帮你造好、塞给你。但你可能产生了一个新疑问：那 Spring 凭什么知道要造哪些对象？比如我引入了 Spring AI 的依赖，ChatClient.Builder 就能自动注入进来——可是项目里一行 new ChatClient.Builder() 都没人写，它从哪冒出来的？

这就是本课要拆的第二个魔法：自动配置（Auto Configuration）。它和 starter、application.yml 是一套组合拳，是 Spring Boot "约定大于配置" 理念的全部秘密。

本课三个关键词

starter（引一个依赖拿一整套功能）+ 自动配置（看到依赖就自动装配 Bean）+ application.yml（用配置文件微调行为）。三件事连起来，就是你以后改 AIHom 时 90% 的"开局动作"。

1. starter：一个依赖 = 一整套功能

在传统 Java 项目里，要用某个功能（比如连数据库、做 Web 接口），你得手动引一堆零散的 jar，还得手动调版本号、手动写一堆配置。Spring Boot 把这一切打包成一个名字很有规律的依赖，叫 starter。

规则很简单：带 spring-boot-starter- 前缀的就是官方 starter，名字后面跟的就是它给你准备好的功能。

<!-- pom.xml 里常见的几个 starter -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>   <!-- 引一个 = 拿到 Web 接口能力（含 Jetty/Tomcat）-->
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jdbc</artifactId>  <!-- 引一个 = 拿到数据库连接能力 -->
</dependency>
AIHom 的关键提醒：认准 boot3 版

AIHom 是 Spring Boot 3 项目。很多第三方组件（比如 Nacos、各种 *-starter）会同时维护 Boot 2 和 Boot 3 两套，artifactId 里通常会带 -spring-boot3-starter 或 -boot-starter 这种区分。引入时务必认准 boot3 版本，引成 boot2 版会导致自动配置失效、Bean 装不上——这是新手最常踩的坑之一。

一句话记住 starter：它的本质是"把一组功能相关的依赖 + 默认配置打包"，让你一行依赖搞定全部。这就是"约定大于配置"的第一层含义——Spring Boot 已经替你想好了"做一个 Web 项目大概需要哪些东西"，你只要点头说"要"。

2. 自动配置：看到依赖，自动装 Bean

引了 starter，依赖是进来了。但代码里那些对象（Bean）是谁造的？答案是：Spring Boot 启动时会扫一遍"类路径"（你引的所有依赖），看到哪些依赖就自动帮你装配哪些 Bean。这就是自动配置。

"魔法"的真相（不玄乎）

它本质上就是一段带 @AutoConfiguration 注解的 Java 配置类，里面写着"如果类路径里存在 ChatClient 这个类，就帮我 new 一个 ChatClient.Builder 放进容器"。这些配置类的清单，Spring Boot 3 放在一个叫 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 的文件里（旧版 Boot 2 用 spring.factories，已淘汰）。所以根本没有什么魔法——只是别人提前写好了"如果...就..."的规则。

把它的思考过程翻译成大白话，就是这样的"如果...就..."：

# Spring Boot 启动时的内心戏（伪代码）
if (类路径里有 ChatClient.class) {
    // 检测到引了 Spring AI
    自动造一个 ChatClient.Builder 放进容器;
}
if (配置里有 spring.ai.dashscope.api-key) {
    // 检测到要连通义千问
    自动造一个连通义千问的 ChatModel;
}
if (类路径里有 WebMvc) {
    // 检测到是个 Web 项目
    自动启动一个内置 HTTP 服务器（AIHom 用 Jetty）;
}
对你意味着什么

你引依赖 + 写配置 = Bean 自动就位。这就是为什么第 1 课那段代码里，ChatClient.Builder 能被构造方法直接注入——根本不用你 new。这是 Spring Boot "约定大于配置"的第二层含义：能猜到的默认行为，它替你做了；只有你不想要默认值时，才需要写配置去覆盖。

3. application.yml：给自动配置填空

自动配置能猜默认值，但有些东西它猜不出来——比如你的通义千问 API Key 是什么、用哪个模型、服务跑在哪个端口。这些就需要你在一个叫 application.yml（或 .properties）的文件里填空。

YAML 是一种缩进表示层级的配置格式。Spring AI 的所有配置都以 spring.ai.* 开头——记住这个前缀，以后看到配置就知道它归 Spring AI 管。

# application.yml —— AIHom 风格的真实片段
server:
  port: 8080                          # 服务端口（Jetty 监听）

spring:
  application:
    name: aihom-service             # 服务名，注册到 Nacos 用
  ai:
    dashscope:                        # ★ 通义千问专属前缀
      api-key: ${DASHSCOPE_API_KEY}  # 从环境变量读，不写死
      model: qwen-plus                # 默认用哪个模型
    alibaba:                          # Spring AI Alibaba 扩展配置
      mcp:
        enabled: true                  # 开启 MCP Server 接入

logging:
  level:
    org.springframework.ai: DEBUG     # 调 Spring AI 时看详细日志
配置项归谁管大白话
server.port Spring Boot 内置 HTTP 服务器（Jetty）监听哪个端口
spring.application.name Spring Boot 服务名，注册到 Nacos 时用这个名
spring.ai.dashscope.api-key / model Spring AI Alibaba 通义千问的密钥和默认模型——AIHom 真正调的大模型
spring.ai.alibaba.mcp.enabled Spring AI Alibaba 是否开启 MCP Server 接入（工具调用相关，第 9 课细讲）
logging.level.* Spring Boot 日志级别，排查"为什么调模型失败"时调到 DEBUG
两个新手必须知道的小习惯

① API Key 永远不要写死在 yml 里——用 ${环境变量名} 占位，密钥从环境变量注入。AIHom 也是这么做的。② 配置和代码的关系是"覆盖默认值"——你写了 model: qwen-plus，就是告诉自动配置"别用你猜的默认模型，用我指定的这个"。

4. AIHom 特色：配置为什么分散在三个地方

这是本课最贴近 AIHom 实战的部分。你会发现 AIHom 的配置不全在 application.yml 里——而是按"要不要随环境变 / 要不要动态更新"分成三类，放在不同地方。这不是随意设计，而是工程上的关注点分离：

  • toad环境差异化配置 → 放 toad（公司内部配置中心）。比如开发 / 测试 / 生产用不同的 DashScope Key、不同的下游地址。每个环境一份，启动时拉取。
  • NacosAgent 配置 → 放 Nacos（动态配置中心）。Agent 的提示词、模型参数这类需要不重启就能改的东西放这里——改完即时生效，不用重新发版。
  • MySQL状态图配置 → 放 MySQL。Spring AI Alibaba 的 StateGraph / Graph（020 课重点）编排逻辑持久化在库里，便于版本管理、可追溯。
一句话总结 AIHom 配置分工

application.yml 只放启动时必须的最小配置（端口、服务名、密钥占位）；跟环境有关的去 toad，需要动态更新的去 Nacos，要持久化审计的去 MySQL。这样配置不会乱成一锅粥，改哪里清清楚楚。

测试工程师视角的提醒

以后排查 AIHom 行为异常，先问三个问题：① 这个配置在 yml 还是 toad？（环境对不对）② 是不是 Nacos 动态下发的？（别人改过没）③ 状态图是不是从 MySQL 读的？（库里版本变了没）。养成这个三连问，定位配置类问题会快很多。

关于版本（重要，已从代码核实）

AIHom 真实栈：Java 21 + Spring Boot 3（Jetty）+ Spring AI 1.1.2 + Spring AI Alibaba 1.1.2.0.5-qh + 通义千问（DashScope）。⚠️ Spring AI 虽已发到 2.0.0（2026-06-12，Boot 4.x），与你的项目无关——本课讲的 starter / 自动配置 / application.yml 机制在 1.1.x 完全适用，查配置项请对齐 1.1.x + Alibaba，别被 2.x 教程带偏。
