从一段熟悉的代码说起

还记得 001 课我们看的那段"读代码"吗？就是它：

return builder.build()            // ① 造一个聊天客户端
               .prompt()            // ② 开始组装一次提问
               .user(q)             // ③ 把用户的问题塞进去
               .call()              // ④ 真正去调大模型
               .content();          // ⑤ 取出回答的文字

当时我们说"看不懂很正常，重点不是记住"。这一课，我们要把这一串彻底讲透。讲完你就能照葫芦画瓢，写出带人设的聊天接口。

今天三个主角

ChatClient（聊天客户端，谁去调模型）+ 三种消息角色（SystemMessage / UserMessage / AssistantMessage，一次提问里装什么）+ Prompt（把消息打包成"一次提问"）。记住这三个词，今天的课就拿下了。

主角一：ChatClient —— Spring AI 统一的聊天入口 Spring AI

调大模型最原始的方式是直接 new 一个 ChatModel，然后手动拼参数。但 Spring AI 官方明确推荐：业务代码请用 ChatClient，而不是底层那个 ChatModel。

一句话区分

ChatModel 是"裸"的模型调用，要自己处理更多细节；ChatClient 是在它之上封装的流式 API（Fluent API）——也就是那种 .prompt().user().call() 一路点下去的写法，更顺手、更适合先学。AIHom 真实代码里，Agent 构建链路会把 ChatModel 包成 ChatClient 使用，但模型创建、摘要、标题生成等地方也会直接使用 ChatModelFactory / ChatModel。

所谓 Fluent API（流式 API），大白话就是"一路点下去"：每一步都返回一个新对象，你接着往下点，像流水线一样把一件事串起来。前面那串 .prompt().user().call().content() 就是典型的 Fluent API。你不用记术语，记住"一路点"就行。

怎么拿到一个 ChatClient？两种方式

Spring 会把 ChatClient.Builder 这个"构造器"自动注入进来（004 课讲的依赖注入）。拿到 Builder 后，有两种写法：

// 写法 A：需要时临时 build 一个（适合偶尔用一次）
@RestController
public class ChatController {
    private final ChatClient.Builder builder;   // Spring 自动注入

    public ChatController(ChatClient.Builder builder) {
        this.builder = builder;
    }

    public String chat(String q) {
        ChatClient client = builder.build();   // ← 每次现造一个
        return client.prompt().user(q).call().content();
    }
}

// 写法 B：启动时造好，全局复用（推荐，更高效）
@RestController
public class ChatController {
    private final ChatClient chatClient;       // 直接注入成品

    public ChatController(ChatClient chatClient) {
        this.chatClient = chatClient;
    }
}
写法 B 的前提

要让 Spring 能直接注入一个 ChatClient 成品（而不是 Builder），你得在某个 @Configuration 类里声明一个 @Bean，告诉 Spring"请帮我 build 一个"。这一步我们放在本课最后讲默认配置时一起做——它也是你本节的"小胜利"之一。

主角二：三种消息角色 Spring AI

大模型对话不是只有"你一句它一句"这么简单。一次完整的提问里，可以装三种不同角色的消息，它们各自的作用完全不同：

消息类中文叫法作用（大白话）
SystemMessage 系统消息 给 AI 定人设 / 角色 / 规矩。比如"你是资深室内设计师，用专业但通俗的语言回答"。这一条优先级最高，模型会一直遵守。
UserMessage 用户消息 用户本次问的问题。比如"小户型怎么显大？"。这是每次提问都要有的核心内容。
AssistantMessage 助手消息 AI 之前的回复。把历史对话塞回去，模型才"记得"前面聊过啥——这就是多轮对话的底层原理。
为什么要有 SystemMessage？

同样一个问题"怎么设计客厅"，没有 SystemMessage 时，AI 会给出一个泛泛的回答；加上 SystemMessage("你是群核的资深软装设计师，回答里要点出可执行的搭配建议") 后，回答立刻专业、聚焦、带品牌口吻。人设 = 你给 AI 的"岗位职责说明书"。

多轮对话的本质（重要，为下一课铺垫）

大模型本身是无记忆的——每次提问都是独立的。它"记得"上一轮，是因为我们把上一轮的对话（UserMessage + AssistantMessage）整段重新塞进了下一次提问里。所以在代码层面，多轮对话 = 每次都拼一长串历史消息。这件事怎么做优雅，是下一课《流式 / 结构化 / 记忆》的主题，今天先有个印象。

主角三：Prompt —— 把消息打包成"一次提问" Spring AI

三种消息有了，但大模型一次只接受一坨完整的请求。这坨请求要包含：哪些消息、用什么参数（比如温度 temperature、最大长度 max-tokens）。Prompt 就是把这坨东西打包好的容器。

一个生活类比

想象你寄快递：三种消息是三样物品，Prompt 是那个快递箱——把物品装好、贴上运单（参数）、交给快递员（.call()）。模型收到的是整个箱子，不是散落的物品。

在代码里，Prompt 本质是一个对象，内部就是 List<Message> 加上一些可选参数。但好消息是——你几乎从不手动 new Prompt。Spring AI 提供的 Fluent API（就是 .prompt() 这一步）会自动帮你组装。所以你日常只需要理解它的概念，不用关心它的构造细节。

核心：链式写法拆解 Spring AI

现在我们把这串代码每一环彻底讲透——这是本课最核心的部分，务必看懂：

chatClient
    .prompt()                              // ① 开门：进入"组装提问"模式，返回一个 PromptBuilder
    .system("你是资深设计师，用通俗语言回答")  // ② 加 SystemMessage（定人设，可省略）
    .user("小户型怎么显大？")              // ③ 加 UserMessage（必填，本次的问题）
    .call()                                // ④ 真正发起调用！把 Prompt 打包发给大模型，拿到响应
    .content();                            // ⑤ 从响应里取出"纯文本"回答
环节做什么返回什么
.prompt() 开门进入提问组装模式 一个能继续往下点的 builder
.system(...) 追加一条 SystemMessage（定人设） 同一个 builder（继续点）
.user(...) 追加一条 UserMessage（你的问题） 同一个 builder（继续点）
.call() 真正调大模型，阻塞等待结果 一个 ChatResponse（完整响应）
.content() 从响应里取出纯文本回答 String（直接 return 给前端）
.call() vs .content() 一定要分清

.call() 返回的是完整的响应对象 ChatResponse，里面有回答文本、token 用量、模型名等一堆信息；.content() 是从里面只抠出回答的纯文本。如果你只想拿回答，就 .call().content()；如果你想看 token 用量、做监控，就只 .call() 然后自己取字段。测试工程师排查接口耗时/费用时，盯的就是 ChatResponse 里的 token 信息。

这一串你已经看懂了！

回头看 001 课那段 .prompt().user(q).call().content()——少了 .system(...)，意味着没定人设，其它完全一样。恭喜，从"看不懂"到"讲得透"，你只用了几节课。

进阶：用 @Configuration 设默认人设 Spring Spring AI

问题来了：如果你的项目里每个接口都要用同一个"你是 XX 助手"的人设，难道每次都要写 .system("你是 XX 助手") 吗？当然不用。Spring AI 支持你在启动时就把默认人设烤进 ChatClient，业务代码直接用，人设自动生效。

@Configuration                              // 告诉 Spring：这是一个配置类（005 课讲的）
public class ChatClientConfig {

    @Bean                                       // 告诉 Spring：把这个方法的返回值注册成一个全局可注入对象
    ChatClient chatClient(ChatClient.Builder builder) {
        return builder
                .defaultSystem("你是群核 AIHom 的智能助手，回答专业、简洁、友好。")  // ← 默认人设
                .build();                     // 一次性 build 好
    }
}

这样一来，所有 Controller 里注入的 ChatClient 都自带这个人设。业务代码直接 chatClient.prompt().user(q).call().content() 就行，不用重复写 .system(...)：

@RestController
public class ChatController {
    private final ChatClient chatClient;   // 注入的是上面 @Bean 造好的、带默认人设的

    public ChatController(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    @GetMapping("/ask")
    public String ask(String q) {
        // 人设已在 @Configuration 里设好，这里不用再写 .system(...)
        return chatClient.prompt().user(q).call().content();
    }
}
@Bean 速记（新手容易卡这里）

@Bean 标在方法上，意思是"这个方法返回的对象，请 Spring 帮我管理，以后谁要注入就给谁"。配合 @Configuration，就实现了"全局只造一次、到处都能用"。这比每次自己 builder.build() 高效得多，也统一得多。AIHom 的配置类里这种写法很常见。

本节胜利：一个完整的 /chat 接口 Spring AI

把上面学的全部拼起来，写一个真正能跑的接口——访问 /chat?q=你好，通义千问会以"AIHom 助手"的身份回答你。AIHom 的模型方向是 DashScope / 通义千问 / Alibaba Agent，但代码里也会出现 Spring AI 的 OpenAiChatModel 与 spring.ai.openai.* 配置，这是用 OpenAI-compatible 适配层去接模型服务，不代表业务栈切成了 OpenAI。

第 1 步：pom.xml 依赖（015 课已配好，这里仅确认）

<!-- Spring AI Alibaba DashScope 起步依赖（Spring AI 被它传递引入） -->
<dependency>
    <groupId>com.alibaba.cloud.ai</groupId>
    <artifactId>spring-ai-alibaba-starter-dashscope</artifactId>
</dependency>

第 2 步：application.yml 配置（通义千问）

spring:
  ai:
    dashscope:
      api-key: ${AI_DASHSCOPE_API_KEY}     # 从环境变量读，别硬编码
      chat:
        options:
          model: qwen-plus            # 通义千问模型名（qwen-plus / qwen-max 等）
          temperature: 0.7           # 0~2，越大越发散，越小越确定

第 3 步：默认人设的配置类

package com.qunhe.aihom.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.ai.chat.client.ChatClient;

@Configuration
public class ChatClientConfig {

    @Bean
    ChatClient chatClient(ChatClient.Builder builder) {
        return builder
                .defaultSystem("你是群核 AIHom 的智能助手。回答专业、简洁、友好，遇到不确定要坦诚说明。")
                .build();
    }
}

第 4 步：ChatController —— 真正的接口

package com.qunhe.aihom.controller;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.web.bind.annotation.*;

@RestController                                // 这是 HTTP 接口类
@RequestMapping("/chat")                       // 类级别路径 /chat
public class ChatController {

    private final ChatClient chatClient;         // 注入带默认人设的 ChatClient

    public ChatController(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    @GetMapping                                   // GET /chat?q=你的问题
    public String chat(@RequestParam String q) {
        return chatClient
                .prompt()                         // ① 组装提问
                .user(q)                          // ② 用户的问题（人设已在 @Configuration 里默认设好）
                .call()                           // ③ 调通义千问
                .content();                       // ④ 取出纯文本回答
    }

    @GetMapping("/design")                       // GET /chat/design?q=...
    public String design(@RequestParam String q) {
        // 演示：覆盖默认人设，给这次提问一个更聚焦的角色
        return chatClient
                .prompt()
                .system("你是群核的资深软装设计师，回答要给 3 条可执行的搭配建议。")
                .user(q)
                .call()
                .content();
    }
}

启动后访问：

  • http://localhost:8080/chat?q=你好 → 走默认人设
  • http://localhost:8080/chat/design?q=小户型客厅怎么搭 → 走设计师人设
