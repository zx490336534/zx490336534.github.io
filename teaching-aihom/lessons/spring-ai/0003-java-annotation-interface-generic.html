003 Java 注解、接口、泛型、lambda

本节目标：上一课你认识了"类"和"对象"。这一课拿下另外四个会反复出现的 Java 概念——注解 @、接口 interface、泛型 <T>、lambda 和链式调用。学完你就能独立读懂一段 Spring AI 的方法签名，知道每个符号归谁管。

为什么这四个必须先拿下

把001 课那段 Spring AI 代码再搬过来看一眼：

@RestController
public class ChatController {
    private final ChatClient.Builder builder;          // ← ChatClient 是高层调用入口，Builder 负责构造它

    @GetMapping("/ask")
    public String ask(@RequestParam String q) {
        return builder.build()
                       .prompt().user(q).call().content();   // ← 链式调用
    }
}

里头一口气出现了 注解（@RestController）、Spring AI 类型（ChatClient）、链式调用（.prompt().user().call()）。再翻 Spring AI 文档，方法签名满屏的 Response<T>、ChatClient.Builder<T>——那是泛型。

为什么不能跳过

这四个符号是贯穿整个 Spring AI / Spring AI Alibaba 的"通用词汇"。不认识它们，你看每一行代码都会卡壳；认识了，再长的签名也只是它们的组合。所以这节课不是"Java 进阶"，而是解锁后续所有课的识字课。

1. 注解 @：给代码贴的"小标签"

注解（Annotation）就是写在代码元素上面的、以 @ 开头的标签。它本身不改变你的业务逻辑，只是一段"元信息"——告诉框架或工具："这个类/方法/字段有什么特殊身份，请你按这个身份对待它"。

@RestController                              // 标签：这是一个 HTTP 接口类
public class ChatController { ... }

@GetMapping("/ask")                          // 标签：这个方法响应 GET /ask
public String ask(...) { ... }

@Service                                       // 标签：这是一个业务服务类
public class ChatService { ... }
一句话记住注解

注解是贴标签，不是写逻辑。贴上 @RestController 这个类不会自己变成网页接口——是 Spring 在程序运行时读到这个标签，才帮它装上"接收 HTTP 请求"的能力。逻辑是 Spring 干的，注解只是个信号灯。

注解可以带参数

有些注解后面跟着括号，那是在给标签补充细节：

@GetMapping("/ask")          // 参数 = 路径
@RequestParam("q")         // 参数 = 请求参数名
@Tool(description = "查订单")   // Spring AI 的工具注解，描述这个工具干什么
为 Spring AI 铺路：@Tool

注意上面那个 @Tool——它来自 Spring AI，专门用来把一个普通 Java 方法标记成"大模型可以调用的工具"。AIHom 里写"让 AI 能查订单/查库存"的功能，就是给方法贴 @Tool。具体怎么用，018 课（Tool Calling & MCP）会专门讲，这里你只要记住：注解是 AIHom 里最常见的"配置方式"。

2. 接口 interface：规定"能做什么"的契约

接口（Interface）是一份只规定方法名和返回类型、不写实现的"合同"。谁想签这份合同，就用 implements 关键字承诺"我会把这些方法实现出来"。

// 1. 定义一份契约：谁能"被聊天"。这是教学示例，不是 Spring AI 源码。
public interface MyChatClient {
    String chat(String message);   // 只有签名，没有 { } 实现
}

// 2. 一个类来签合同，并实现它
public class QwenChatClient implements MyChatClient {
    @Override
    public String chat(String message) {
        return "你说：" + message;   // 这里才写真正的逻辑
    }
}

为什么要这么绕？因为它把"做什么"和"怎么做"分开了。调用方只认 MyChatClient 这份合同，至于背后是真的通义千问、还是测试用的假对象——调用方不关心，只要它实现了 chat() 就行。这就是接口抽象的价值。

关键事实：AIHom 里到处都是接口式抽象

别把上面的教学示例误认为 Spring AI 源码：ChatClient 更准确地说是 Spring AI 提供的高层聊天调用入口 / Fluent API。真正需要你形成条件反射的是：AIHom 里大量类型是接口式抽象或抽象入口，比如 ChatModel、EmbeddingModel、ToolCallback、各种 *Service。看到这些名字，先问两件事：它规定了什么能力？真正实现在哪里？

小白答疑：接口 vs 类

• 类（class）：有字段、有方法实现，能 new 出对象。
• 接口（interface）：只有方法签名（合同条款），不能直接 new。必须由某个类 implements 它并提供实现。
所以你不会写 new MyChatClient() 这样的接口实例，而是由某个实现类来 implements 它。到了 Spring 项目里，通常由 Spring 帮你把需要的实现对象塞进来（依赖注入，下一课讲）。

3. 泛型 <T>：类型占位符

泛型（Generics）就是类型上的"填空题"。尖括号 <> 里的字母是一个占位符，等你用的时候再填上具体类型。

// T 是占位符，代表"某种类型"
List<String> names = ...;          // 填成 String：装字符串的列表
List<Integer> ages = ...;          // 填成 Integer：装整数的列表

// Spring AI 里你一定会见到的：
Response<ChatResponse>            // "装着 ChatResponse 的 Response"
ChatClient.Builder<T>          // Builder 的占位类型

为什么要搞占位符？因为同一个容器/方法想兼容多种类型，又不想丢掉类型检查。没有泛型的话，List 只能装 Object，取出来还得强转、容易出错。有了 List<String>，编译器就帮你盯住"这个列表只能放字符串"，省心。

本课对泛型的要求：能读懂，不用会写

作为测试工程师转开发，你现在不需要自己定义泛型类/泛型方法。只要做到：看到 Response<T>、List<Document>、Map<String, Object> 这种写法，知道"尖括号里是它装的内容的类型"就够了。这是读懂 Spring AI 方法签名的最低门槛。

签名片段怎么读
List<String>"字符串列表"——里面每个元素都是 String
Map<String, Object>"键是 String、值是 Object 的映射"——AIHom 配置里超常见
Response<ChatResponse>"装着一个 ChatResponse 的 Response 包装"
ChatClient.Builder<T>"Builder，T 是它的占位类型，用的时候再定"

4. lambda 与链式调用：读懂 Spring AI 的标志性写法

4.1 链式调用 .a().b().c()

链式调用就是一个方法返回的对象，紧接着又调它的方法，串成一串。每个方法都返回"某个对象"，让下一棒继续操作。Spring AI 几乎所有 API 都是这种风格：

// Spring AI 最经典的链式调用
chatClient.prompt()        // 返回一个 PromptBuilder
          .user(q)         // 在上面继续：塞入用户问题，返回自身
          .call()          // 继续在它上面：发起大模型调用，返回 CallResponse
          .content();      // 继续在它上面：取出文本内容，返回 String
怎么读链式调用

从左到右、从上到下，当成一条流水线读：先 prompt() 开工 → user(q) 加料 → call() 加工 → content() 取成品。每一棒都把"半成品"交给下一棒。换行只是为好看，本质上等价于一长行。

4.2 lambda () -> ...

lambda（箭头函数）是一小段"随用随写的匿名函数"。左边 () 是参数，-> 右边是函数体。Spring AI 里它最常出现在"把一段行为当参数传进去"的场景：

// 传统写法：得专门定义一个类/方法
chatClient.prompt(p -> p.user("你好").call());

// Spring AI 里常见的 lambda：自定义一次提问
ChatResponse resp = chatClient.prompt()
    .system("你是一个友好的助手")
    .user(userQuestion -> userQuestion.text(q))   // ← 这就是一个 lambda
    .call()
    .chatResponse();

怎么读 userQuestion -> userQuestion.text(q)？翻译成人话就是："给我一个叫 userQuestion 的东西，我返回 userQuestion.text(q)"。框架会在合适的时机调用你这个迷你函数。

lambda 不必现在精通

你现在只要"看得懂"lambda 的形状（左边参数，箭头，右边表达式），知道它是"一小段临时函数"即可。会不会自己写、能不能玩花活，可以慢慢来。AIHom 里你会反复读到它，读多了自然就会写。

5. 综合实战：拆解一段真实 Spring AI 签名

把今天学的四个概念凑齐，来看一段真正出自 Spring AI 文档风格的方法签名。别怕，我们逐符号拆：

@Tool(description = "根据订单号查订单状态")    // ① 注解，带参数
public String queryOrder(String orderId) { ... }

// 再看一个 Spring AI 的链式调用 + lambda + 泛型：
String answer = chatClient.prompt()
    .user(q -> q.text("把这段翻译成英文"))
    .call()
    .content();

List<String> tools = chatClient.getDefaultTools();  // 泛型 List<String>
符号类别含义
@Tool(description = "...") 注解 给方法贴标签：这是个可被大模型调用的工具，并附上描述
ChatClient（类型） 调用入口 Spring AI 的高层聊天 API，常包在 ChatModel 之上使用
List<String> 泛型 "装字符串的列表"——这里装的是工具名
.prompt().user().call().content() 链式 一串流水线：提问→加料→调用→取结果
q -> q.text("...") lambda 一段临时小函数：给我 q，返回 q.text("...")
看到了吗？没有新东西了

一段看起来挺唬人的 Spring AI 代码，拆到底就是注解 + 接口 + 泛型 + 链式 + lambda这五个老朋友在组合。你今天认识它们，以后再看任何 Spring AI / Spring AI Alibaba 的代码，都可以这么一层层拆开——这就是这节课的全部价值。
