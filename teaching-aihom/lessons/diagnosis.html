按一次运行排查前端到模型的故障

把一条反馈定位为连接、编排、生成或渲染问题。

先看场景

若用户看到「已完成」却没有布局，先验证完成事件的归属和结果结构，再看派生视图。不要先从任意一条报错猜原因。

关联 ID：像快递单号。同一任务经过多个系统时，用一个编号把零散记录拼起来。

走一遍

  1. 给单次运行赋关联 ID，在边界记录阶段、结果和耗时。
  2. 样例日志不记录完整输入、认证信息或用户原文。
  3. 依次验证接口回执、状态转换、结果契约和渲染错误，找到第一个出错的边界。
合成示例 可折叠
run=demo-123 phase=validate outcome=invalid_geometry elapsed_ms=18

第二遍 · 把代码读懂

代码拆解

反馈说「生成成功但没有图」。你能用记录证明哪一步最先失败吗？

调用链

  1. 用同一个运行编号串起浏览器、服务与渲染。
  2. 逐步核对已受理、已生成、已校验、已发布、已显示。
  3. 有显式失败时指向失败阶段；缺记录时标记缺少证据。
  4. 用同一个样例单独复现这一层，再核对上游确实成功。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

STAGES = ("accept", "generate", "validate", "publish", "render")

def first_problem(events, run):
    matching = [e for e in events if e[0] == run]
    latest = {
        phase: outcome
        for _, _, phase, outcome in sorted(matching, key=lambda e: e[1])
    }
    for phase in STAGES:
        outcome = latest.get(phase)
        if outcome is None:
            return (phase, "missing")
        if outcome != "ok":
            return (phase, outcome)
    return (None, "ok")

good = [("R1", n, p, "ok") for n, p in enumerate(STAGES)]
assert first_problem(good[::-1], "R1") == (None, "ok")
render_error = good[:-1] + [("R1", 4, "render", "renderer-error")]
assert first_problem(render_error, "R1") == ("render", "renderer-error")
no_publish = good[:3] + good[4:] + [("R2", 3, "publish", "ok")]
assert first_problem(no_publish, "R1") == ("publish", "missing")

先确定用户所说完成是哪一层

服务可能完成了生成和校验，却没把结果送到当前页面；也可能服务已经发布、是渲染失败。示例按阶段检查，不把后台一个 OK 当作端到端成功。

先按运行分组，再按序号

日志到达顺序不一定是发生顺序。这个示例假定教学记录提供统一、可比的顺序号，仅凭跨进程的本地时钟不能重建同样排序。真实链路可使用串联追踪 span 或分别核对各边界断言。

把缺记录与已经失败区分开

本例遇缺失阶段返回 missing，不因此断言它失败了。关注结构化状态与耗时；避免把整段输入或返还内容复制到日志。重复上报会覆盖阶段摘要，所以本例用最新一条；研究重试时应保留 attempt，避免用成功的第二次掩盖第一次异常。

复现失败

渲染器失败
怎么触发：上游记录齐全且成功，渲染记录为 renderer-error。
怎么判断：首个故障定位到 render，不能归因给模型。
发布证据缺失
怎么触发：删掉当前运行的发布记录，另一个运行恰好有同阶段成功。
怎么判断：依然返回当前发布证据缺失，不借用其他运行。

写下这些测试断言

  • 乱序收集不改变按运行与阶段得出的判断。
  • 缺证据时返回 missing 而不是臆造失败原因。
  • 其他运行的同名阶段不能用来补当前链路。

这一课带走：好排查不是收集更多文本，而是在正确的那次运行上找到第一处不满足契约的边界。

动手练习

分别模拟参数非法、模型超时、渲染失败。每次只用状态和日志说清出错边界。
