一次交互如何走完整条链路

从用户点击「生成布局」开始，找到浏览器、服务端和渲染器各自负责什么。

先看场景走一遍读代码复现失败动手练习自测

先看场景

在虚构的 RoomLab 中，浏览器先提交一个布局请求，服务端立刻返回任务编号。收到结果后，浏览器先更新模型，再让二维平面图和三维预览从同一份模型取数据。

回执：像点完外卖拿到订单号。订单号说明已受理，不说明饭已经送到。

走一遍

  1. 在接口层确认请求被接受，不把「已接收」当成「已完成」。
  2. 拿到任务编号后，用它串起状态事件和最终结果。
  3. 两个视图不互相传草稿，都只读同一个已确认版本。

第二遍 · 把代码读懂

代码拆解

点一次「生成布局」，为什么页面先出现排队提示，而不是立刻画出新布局？

调用链

  1. 页面把此次点击标成一个独立操作，同时保留当前布局。
  2. 服务确认收单，返回可查询的任务编号；此时没有新布局可显示。
  3. 页面接收结果时核对任务编号与当前操作。
  4. 结果通过检查后，二维和三维从同一个新版本更新。
JavaScript 示例 可折叠

可复制到 lesson.cjs，再运行 node lesson.cjs。

const assert = require('node:assert/strict');
const initial = { click: 0, pending: null, state: 'idle', revision: 2 };
const send = (s) => ({ ...s, click: s.click + 1, pending: null, state: 'sending' });

function accept(s, click, id) {
  if (s.click !== click || s.state !== 'sending') return s;
  return { ...s, pending: id, state: 'queued' };
}

function finish(s, result) {
  if (s.state !== 'queued' || result.id !== s.pending) return s;
  if (!result.ok || !Number.isInteger(result.revision) || result.revision <= s.revision) {
    return { ...s, state: 'failed', pending: null };
  }
  return { ...s, pending: null, state: 'ready', revision: result.revision };
}

const a = send(initial);
const b = send(a);
assert.equal(accept(b, a.click, 'old').pending, null);
const queued = accept(b, b.click, 'sample-2');
assert.equal(queued.revision, 2);
assert.equal(finish(queued, { id: 'old', ok: true, revision: 9 }), queued);
assert.equal(finish(queued, { id: 'sample-2', ok: false }).revision, 2);
const ready = finish(queued, { id: 'sample-2', ok: true, revision: 3 });
assert.equal(ready.revision, 3);

先看 UI 里两样东西：任务和布局

任务表示这次生成做到哪一步，布局表示用户此刻正在看的图。示例用 pending 记录任务编号，revision 记录布局版本。只要服务还没产生可用结果，即使任务已排队，也不该把版本 2 清成空白。

收单与完成更新不同字段

accept 先判断响应是不是当前点击。如果响应属于较早的点击，不更新 pending。应用在发请求前先递增 click，把点击编号保存到请求的回调中。这个编号用于本页防止旧回调覆盖，不是后台任务编号。

按身份和结果类型决定是否发布

finish 只接收当前任务的结果；失败时只更新任务状态，成功且版本不倒退时同时更新布局版本。示例的 revision 只表示同一房间里的版本，真实应用还应校验当前房间，切图前也应校验结果结构。页面在实际提交前可用订阅后的快照覆盖可能过早到达的通知。

复现失败

旧回执迟到
怎么触发：先发 A 再发 B，最后收到 A 的回执。
怎么判断：页面继续等待或展示 B，A 不能改当前任务。
新任务失败
怎么触发：后台回失败，或者回传无法使用的版本。
怎么判断：任务进入失败，但两张视图仍显示版本 2。
完成消息先于订阅
怎么触发：模拟切换网络，接收回执之后才接上消息。
怎么判断：订阅后以同任务快照补齐进度，不假设当前仍在排队。

写下这些测试断言

  • 收到回执以后，版本仍是 2。
  • 旧任务报告更大的版本，也不能更新当前运行。
  • 失败不抹掉已确认布局，成功才切到版本 3。

这一课带走：先认清是哪个请求、哪个任务，再问有无足够信息替换布局。
