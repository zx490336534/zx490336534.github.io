Agent 状态图：可恢复不等于可重试

把生成、校验、提交做成明确节点，避免恢复时重复写入。

先看场景走一遍读代码复现失败动手练习自测

先看场景

示例流程先产生草案，再走约束校验，最后写入版本。模型输入不稳定，数据库提交和工具调用也有各自的失败方式。

幂等：同一件事重做，不应该多产生一条结果。连按两次保存，不等于要保存两个版本。

走一遍

  1. 保存足以恢复的状态，例如草案编号和最近完成的步骤，而非只保存聊天文本。
  2. 读取可以有界重试；写操作先定义幂等键并验证冲突语义。
  3. 区分已知失败、已知成功、结果未知。写入后丢失响应时先查询，不直接发起另一次写入。
合成示例 可折叠
draft → validate → confirm → commit
                    ↘ correct → validate

第二遍 · 把代码读懂

代码拆解

确认保存后网络断了。下一位执行者如何知道该补写，还是只该找回已写入的结果？

调用链

  1. 生成草案并保存草案引用。
  2. 验证草案和用户确认，固定本次操作身份。
  3. 保存前先按操作身份寻找已有结果。
  4. 写入结果未知时停止盲目追加；恢复时同键查询或幂等写。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

class DemoStore:
    def __init__(self):
        self.rows = {}

    def commit_once(self, key, shape, lose_reply=False):
        if key not in self.rows:
            self.rows[key] = (len(self.rows) + 3, shape)
        elif self.rows[key][1] != shape:
            raise ValueError("same operation, different shape")
        if lose_reply:
            raise TimeoutError("reply lost after write")
        return self.rows[key]

def commit(store, run, draft_id, shape, *, checked, confirmed, lose_reply=False):
    if not checked or not confirmed:
        return ("blocked", None)
    key = (run, draft_id)
    try:
        result = store.commit_once(key, shape, lose_reply)
    except TimeoutError:
        return ("unknown", None)
    return ("done", result[0])

store = DemoStore()
shape = (1, 2)
assert commit(store, "R", "D", shape, checked=True, confirmed=False) == ("blocked", None)
assert commit(store, "R", "D", shape, checked=True, confirmed=True, lose_reply=True)[0] == "unknown"
assert commit(store, "R", "D", shape, checked=True, confirmed=True) == ("done", 3)
assert len(store.rows) == 1

草案与提交记录不能混成一份

草案是模型建议，提交是可被别的用户操作看到的变更。checkpoint 只用于保存执行进度，不等同于所有副作用都已发生。示例把用户确认与草案校验作为前置条件，不根据模型一句「可以提交」判断。

同一业务动作只发一个身份

key 由任务与草案组成，是示例中稳定不变的身份。真实服务应把键绑定资源、作用域以及请求语义；同键却换内容通常应拒绝，而非悄悄拿旧结果成功返回。应用层的先查只能避免已知重复，数据库仍需唯一约束或等价原子写入，避免两个执行者同时通过检查。

用想知道的事实分支

正常写入返回新版本；响应丢失时运行停在 unknown。示例把故障放在写入之后，以便验证重跑时没有第二条记录。线上只有读取可靠源或得到已存在的幂等响应，才可以结束未知状态；读取不到而系统可能仍在执行时，应保留待确认。

复现失败

写后响应丢失
怎么触发：先保存再抛出超时，随后同键恢复一次。
怎么判断：最初状态为未知，恢复后找回版本 3，保存记录仍只有一条。
恢复请求改了草案
怎么触发：保留同一个执行编号和草案 ID，但改坐标。
怎么判断：判定身份冲突；不会覆盖已记录结果。
没有用户确认
怎么触发：草案校验通过，但确认尚未发生。
怎么判断：写操作完全不发生。

写下这些测试断言

  • 确认前记录数是 0。
  • 超时确实发生在保存后，而非保存前。
  • 恢复拿到同一版本，持久化次数仍是 1。

这一课带走：恢复用来找回流程和结果；副作用是否能再做，要靠业务身份与存储约束回答。

动手练习

模拟「保存成功但响应丢失」，用同一个运行编号查询；断言只有一条已保存记录。

自测

恢复时知道请求发出，但不知道数据库有没有写成功，最安全的第一步？
