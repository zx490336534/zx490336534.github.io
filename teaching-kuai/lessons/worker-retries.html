构建稳定的执行系统 · 第 09 课 · 约 41 分钟

执行器重试：有预算、有分类、有幂等

为暂时性失败设计有上限的重试，保留第一次的错误证据。

先看场景走一遍读代码复现失败动手练习自测

先看场景

写预约时，服务端成功保存但响应丢了；执行器重试如果用新编号，就会多写一条。

幂等键：重试仍携带同一个逻辑操作标识；接收方把同一标识与请求内容绑定，只承认一次副作用。

走一遍

  2. 给请求分配稳定的逻辑标识。
  3. 预算内按计划等待后再尝试，并保留失败分类。

调用链

  1. 先划分终态错误和暂时错误。
  2. 给请求分配稳定的逻辑标识。
  3. 预算内按计划等待后再尝试，并保留失败分类。
  4. 服务确认重复写只是取回旧结果。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

class Transient(Exception):
    pass

saved, attempts, delays = {}, [], []

def write(key, value):
    attempts.append(key)
    if key in saved:
        if saved[key] != value:
            raise ValueError("idempotency conflict")
        return saved[key]
    saved[key] = value
    raise Transient("response lost after commit")

def run(key, value, max_attempts=3):
    for i in range(max_attempts):
        try:
            return write(key, value)
        except Transient:
            if i + 1 == max_attempts:
                raise
            delays.append(2 ** i)
    raise ValueError("empty retry budget")

assert run("demo-key", "slot-1") == "slot-1"
assert len(saved) == 1
assert attempts == ["demo-key", "demo-key"]
assert delays == [1]

把失败细分成可重试和不可重试

输入验证不该重试，网络超时可重试但不表示未发生写入。有限次数以包含首次调用的总尝试数表示；示例显式记录等待预算但不实际睡眠。

谁来保证不重写

执行器传 stable-key，接收服务要持久化键与请求内容，拒绝同键不同内容。内存 dict 只说明行为，真实实现要用可靠存储和事务保护目标操作与幂等记录。

预算、分类与抖动

生产中也设总截止时间，叠加退避和少量随机抖动，避免多个执行器同步施压。把预算耗尽硬失败和业务拒绝分别计入报告；不要因为最终成功而抹掉第一次响应丢失。

复现失败

提交成功却无回执
怎么触发：首次保存后抛暂时错误。
怎么判断：第二次返回同一结果，不新增预约。
同键不同载荷
怎么触发：把预约槽位改掉但使用原键。
怎么判断：拒绝并停止重试；原值仍在。

写下这些测试断言

  • 暂时错误不等于没有副作用。
  • 同键同载荷得到同一结果。
  • 预算设为一时不发第二次请求。
  • 逻辑操作重复提交不会多一条记录。

这一课带走：重试只是重新尝试拿到结果；把潜在副作用和状态冲突当成一等问题处理。
