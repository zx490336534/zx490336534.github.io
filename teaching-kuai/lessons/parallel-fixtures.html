并行用例的数据隔离：谁创建，谁清理

让同一条用例开多个执行器时，不争抢数据，也不清掉别人的结果。

先看场景走一遍读代码复现失败动手练习自测

先看场景

两条用例都要创建一个名为 review 的临时预约。串行时各自通过，跑到同一批次里却相互覆盖，一个执行器清理时还影响另一个。

用例夹具：测试开始时准备数据、结束后清理数据的一段可复用逻辑。

走一遍

  1. 给每次测试调用生成独立作用域，而不是拿用例名称做全局唯一键。
  2. 在创建时保存真正拿到的资源标识。
  3. 正常结束和断言异常都走清理；清理只能删除自己创建的标识。
合成示例 可折叠
namespace = (run_id, worker_id, case_attempt_id)

第二遍 · 把代码读懂

代码拆解

串行回归都过了，一并行就偶尔找不到数据，应该先查哪里？

调用链

  1. 在每个执行尝试生成作用域，并在夹具中保存。
  2. 写入时绑定资源和作用域，读取也使用同一组键。
  3. 并行执行相同显示名的用例，验证彼此不可见或不互相覆盖。
  4. 在异常路径同样释放本次资源，核对另一个用例的记录仍存在。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

from contextlib import contextmanager

rows = {}

@contextmanager
def booking(scope, display_name):
    resource = (*scope, display_name)
    if resource in rows:
        raise ValueError('fixture_collision')
    rows[resource] = {'status': 'reserved'}
    try:
        yield resource
    finally:
        rows.pop(resource, None)

with booking(('run-1', 'worker-A', 'attempt-1'), 'review') as a:
    try:
        with booking(('run-1', 'worker-B', 'attempt-1'), 'review') as b:
            assert a != b and len(rows) == 2
            raise RuntimeError('intentional test failure')
    except RuntimeError:
        assert a in rows and b not in rows
    with booking(('run-1', 'worker-B', 'attempt-2'), 'review') as retry:
        assert retry != b and a in rows
    assert a in rows
assert not rows

名称和所有权分开

名称为人服务，并不适合做清理条件。资源标识至少包含运行、执行器和尝试；演示以元组表示隔离。相同用例重试需要新尝试身份，避免旧清理动作影响新运行。

清理绑定主流程退出

contextmanager 的 finally 段即使断言失败也会执行。真实进程被杀时 finally 不保证运行，因此需要按创建范围、租约或过期策略定期对账，而非直接全库删同名记录。

把隔离验证成契约

用嵌套调用模拟两个生命周期交错：当 B 出错退出时 A 尚在运行。断言清理只影响 B；不必等待真实线程竞速，仍可稳定捕捉共享命名空间错误。

复现失败

多个用例放进同一个作用域
怎么触发：把作用域简化为 display_name，把同名运行嵌套。
怎么判断：第二个创建发生冲突；夹具应该隔离而不是覆盖。
清理按名称
怎么触发：在 B 退出时删除所有名为 review 的行。
怎么判断：A 的记录应该仍在，断言会暴露越界清理。
重试复用身份
怎么触发：给第二次尝试继续使用 attempt-1。
怎么判断：新旧操作无法区分；验收要求重试身份不同。

写下这些测试断言

  • 同时运行的两条用例可以使用同一个显示名。
  • 抛错后及时清理本次资源，其他用例保持可运行。
  • 重试使用新身份；全部退出后没有临时记录。

这一课带走：先定义资源属于哪次执行，再让创建、读取、清理都遵守同一个范围。

动手练习

写一个用例故意抛错，再和另一条模拟用例交错运行；检查出错后的清理没有破坏其他会话。
