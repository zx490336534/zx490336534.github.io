先看场景

同一预约规则有几个改写版本。如果把改写随机分到不同集合，开发阶段会提前看见盲测内容。

按组切分：把同一来源及其改写看作一个组，在组层面分配到集合，而不是对每行独立随机分配。

  2. 对整个来源组做开发与留出切分。

Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

from hashlib import sha256
import json

def fingerprint(samples):
    ids, split_by_group = set(), {}
    for sample in samples:
        key, group, split = (sample["id"], sample["group"], sample["split"])
        if key in ids:
            raise ValueError("duplicate sample ID")
        if split not in {"train", "dev", "holdout"}:
            raise ValueError("unknown split")
        if split_by_group.setdefault(group, split) != split:
            raise ValueError("group leakage")
        ids.add(key)
    data = sorted(samples, key=lambda row: row["id"])
    encoded = json.dumps(data, ensure_ascii=False, sort_keys=True,
                         separators=(",", ":")).encode("utf-8")
    return sha256(encoded).hexdigest()

rows = [
    {"id": "q1", "group": "queue", "split": "dev", "expect": "wait"},
    {"id": "q2", "group": "queue", "split": "dev", "expect": "wait"},
    {"id": "s1", "group": "slot", "split": "holdout", "expect": "read"},
]
assert fingerprint(rows) == fingerprint(list(reversed(rows)))
assert fingerprint(rows) != fingerprint([*rows[:2], {**rows[2], "expect": "deny"}])

先定义来源组

完全相同的文本去重还不够：同一个工单的对话变体、同一预约约束的改写都可能泄漏。示例要求同一 group 只能有一个 split；组的由来要能解释，真实数据还需近似重复检查。

规范化指纹是复核入口

排序按样本 ID，序列化稳定后再做哈希。调整行顺序不改变标识；改预期、规则来源或 split 会改变。在报告中再保存评分规范标识、运行配置和评估集用途，指纹本身不保证标签正确。

盲测结果只用于少数决策

开发可以看开发子集的逐项错误；留出用作阶段性复核，不要边试提示词边逐题看盲测分。如果频繁查看留出分，逐渐会把它优化成开发集，应另建新的独立留出。

复现失败

变体跨切分
怎么触发：把 q2 调到 holdout。
怎么判断：同源组跨集合被拒绝。
重复编号
怎么触发：追加另一条 id=q1 的记录。
怎么判断：拒绝数据，不让结果字典悄悄覆盖。

写下这些测试断言

  • 同组不跨集合。
  • 只重排记录不会改变指纹。
  • 修改预期会改变指纹。
  • 用不同数据或不同规则的成绩不得直接归因模型。

这一课带走：数据集版本要能证明究竟评了什么，切分要保护你还没看过的检验题。
