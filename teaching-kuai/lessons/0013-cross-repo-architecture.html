🔗 三仓库协作架构

专题 数据流 · 接口契约 · 版本兼容性

Kuai 测试平台由 3 个独立仓库组成，它们通过 HTTP API 和 MCP 协议紧密协作。本课从全局视角梳理三仓库的协作关系、完整数据流路径、接口契约规范和版本兼容性注意事项。

🔄 二、完整数据流路径

以「用户在前端发送一条消息，Agent 调用工具并返回结果」为例，追踪完整数据流：

Step 1：用户输入 → 前端

用户在 Chat 页面输入消息，前端 React 组件捕获输入，通过 Redux dispatch 更新会话状态。

// 前端发送消息
const sendMessage = async (content: string) => {
  dispatch(addMessage({ role: 'user', content }));
  const response = await fetch('/api/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ sessionId, content }),
  });
  // 处理流式响应...
};
Step 2：前端 API Route → LangChain Agent

Next.js API Route 接收请求，调用 LangChain Agent 系统处理。Agent 根据用户的 Prompt 和可用工具列表决定是否调用 MCP 工具。

// Next.js API Route: /api/chat/route.ts
const agent = createReactAgent({
  llm: model,
  tools: mcpTools,    // 从 MCP 服务加载的工具列表
  prompt: systemPrompt,
});
const stream = await agent.stream({ messages });
Step 3：Agent → MCP 服务 (kuai-service-py)

Agent 决定调用某个 MCP 工具时，通过 MCP 协议（SSE 或 StreamableHTTP）向 kuai-service-py 发起调用。

# kuai-service-py 接收 MCP 工具调用
@app.post("/mcp/{server_name}/tools/{tool_name}")
async def call_tool(server_name: str, tool_name: str, params: dict):
    server = server_manager.get(server_name)
    result = await server.call_tool(tool_name, params)
    return {"result": result}
Step 4：前端 → Java 后端 (kuai-service)

当需要 Prompt 管理、LLM 评估、知识库检索等核心业务时，前端直接调用 kuai-service 的 REST API。

// 前端调用 Java 后端
const prompts = await fetch('http://kuai-service/api/prompt/list');
const evaluation = await fetch('http://kuai-service/api/evaluate/run', {
  method: 'POST',
  body: JSON.stringify({ promptId, model, testCases }),
});
Step 5：后端处理 → 数据库 → 响应返回

Java 后端通过 MyBatis-Plus 操作 MySQL，完成业务逻辑后返回 JSON 响应，前端更新 UI。

// Java 后端处理
@GetMapping("/api/prompt/list")
public Result<List<PromptDTO>> list() {
    List<PromptEntity> list = promptService.list();
    return Result.success(list.stream()
        .map(this::toDTO).collect(Collectors.toList()));
}
关键点：三条数据通路并存 —— 前端 ↔ Java 后端（REST API）、前端 ↔ Python MCP 服务（MCP 协议）、Java 后端 ↔ Python 后端（共享数据库）。

📋 三、接口契约

三仓库之间的协作依赖清晰的接口契约。以下是核心规范：

1. REST API 统一返回格式（Java 后端）

{
  "code": 200,         // 200=成功, 其他=错误码
  "message": "success",
  "data": { ... }      // 业务数据
}

2. 前端请求规范

规范说明
Base URLJava 后端：/api/*，Python MCP：/mcp/*
认证方式Header: Authorization: Bearer <token>
Content-Type统一使用 application/json
分页参数page（从 1 开始）、size（默认 10）
时间格式ISO 8601：2024-01-01T00:00:00Z

3. MCP 工具接口契约

// MCP 工具定义格式
{
  "name": "tool_name",
  "description": "工具描述，供 Agent 理解用途",
  "inputSchema": {
    "type": "object",
    "properties": {
      "param1": { "type": "string", "description": "参数说明" }
    },
    "required": ["param1"]
  }
}

4. 错误码规范

HTTP 状态码业务码含义
200200成功
4004001参数校验失败
4014002未授权 / Token 过期
4044004资源不存在
5005001服务器内部错误

⚠️ 四、版本兼容性注意事项

核心原则：三仓库独立发版，但接口契约必须向前兼容。任何破坏性变更需要协调发布。

1. API 版本管理

  • 新增字段：向后兼容，旧版前端忽略未知字段即可
  • 删除字段：必须先标记 deprecated，等所有消费方迁移后再删除
  • 修改字段类型：视为破坏性变更，需要版本号升级

2. 数据库 Schema 变更

  • 新增列：使用 ALTER TABLE ... ADD COLUMN，设置默认值
  • 删除列：先确认无代码引用，再执行删除
  • Java 和 Python 后端共享数据库，Schema 变更需同步通知

3. MCP 协议兼容性

  • 工具签名（name + inputSchema）变更需同步更新前端 Agent 的工具缓存
  • 新增工具：无需前端改动，Agent 自动发现
  • 删除工具：需确认前端无硬编码依赖

4. 协调发版流程

1. 接口变更方 → 更新 API 文档 + 通知协作方
2. 协作方 → 适配新接口（可先兼容新旧两版）
3. 变更方 → 合并代码、部署
4. 协作方 → 合并适配代码、部署
5. 验证 → 端到端功能测试
遇到不懂的地方？直接问 Agent。比如：「kuai-service 和 kuai-service-py 的数据库表结构有哪些？」或「前端调用后端 API 的认证流程是怎样的？」

📝 Quiz

Q1：当前端需要调用 MCP 工具时，请求的完整路径是什么？

  • A. 前端 → kuai-service (Java) → kuai-service-py (Python)
  • B. 前端 → LangChain Agent → kuai-service-py (Python) 通过 MCP 协议
  • C. 前端直接访问 MySQL 数据库
  • D. 前端 → kuai-service-py → kuai-service → 数据库

✅ 答案：B — 前端通过 LangChain Agent 系统，使用 MCP 协议（SSE/StreamableHTTP）直接调用 kuai-service-py 的 MCP 工具。

Q2：三仓库之间的 REST API 统一返回格式中，成功响应的 code 值是什么？

  • A. 0
  • B. 1
  • C. 200
  • D. 2000

✅ 答案：C. 200 — kuai-service 使用 Result<T> 包装返回值，成功时 code 为 200。

Q3：当需要删除一个已有的 REST API 字段时，正确的做法是？

  • A. 直接删除，前端自行适配
  • B. 先标记 deprecated，通知协作方迁移，确认无引用后再删除
  • C. 同时修改三个仓库的代码并一起发布
  • D. 不允许删除任何字段

✅ 答案：B — 接口向前兼容原则要求先标记废弃，等所有消费方完成迁移后再正式删除。
