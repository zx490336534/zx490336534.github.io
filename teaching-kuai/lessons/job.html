一次回归如何从提交跑到结果

先看清浏览器、任务服务和执行器三个角色。

先看场景走一遍读代码复现失败动手练习自测

先看场景

虚构的 CaseLab 接收一批测试用例。浏览器创建运行，任务服务管理状态，执行器回传单条结果。最后由聚合层按明确规则给出结果。

执行异常：例如浏览器没启动，测试压根没走到检查点；与业务返回了错误结果不同。

走一遍

  1. 创建请求返回运行 ID，而不是等待所有用例跑完。
  2. 不要把执行错误当断言失败；两者对应不同的修复方向。
  3. 任务终态要能解释每个用例的结果，包括跳过和未执行。

第二遍 · 把代码读懂

代码拆解

点了「运行预约回归」，页面立刻出现绿色提示。它是在说「收到任务」，还是「所有用例都通过了」？

调用链

  1. 界面提交固定的用例集合，拿到运行编号与 queued 状态。
  2. 执行器领取批次，状态推进到 running。
  3. 逐条记录通过、业务断言失败和执行故障。
  4. 计划集合中的结果到齐，才展示最终统计。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

from collections import Counter

state = "queued"
expected = {"reserve", "repeat", "busy"}
results = {}

def record(case_id, outcome):
    global state
    if case_id not in expected:
        raise ValueError("unknown case")
    if outcome not in {"pass", "assertion_fail", "infra_error"}:
        raise ValueError("bad outcome")
    if case_id in results:
        if results[case_id] != outcome:
            raise ValueError("conflicting result")
        return
    if state != "running":
        raise ValueError("run not active")
    results[case_id] = outcome
    if set(results) == expected:
        state = "finished"

assert state == "queued"
state = "running"
record("reserve", "pass")
record("reserve", "pass")
assert state == "running"
record("repeat", "assertion_fail")
record("busy", "infra_error")
assert state == "finished"
assert Counter(results.values()) == {
    "pass": 1, "assertion_fail": 1, "infra_error": 1}

先分清两类状态

运行状态回答「流程到哪了」；用例结果回答「执行时看见什么」。一条业务断言失败，不妨碍整批走到 finished。界面收到 202 可以显示已接收，不能据此显示已通过。

先记明细，再算结论

record 用用例 ID 记录事实。完全相同的重发会被吸收，同一尝试里相互冲突的结果显式报错。如果直接在回调中增加通过计数，一条重复消息就能把通过数抬高。

用集合判断何时收口

比较预期用例 ID 和实际结果 ID，而不是比较通过率。生产存储需要对上报做原子去重，再按明细聚合；示例只演示单进程状态逻辑。后续若允许重跑，可用尝试号保存多次结果，不使用最后到达者覆盖原结果。

复现失败

重复回报
怎么触发：第一条通过结果提交两次。
怎么判断：明细只有一条，批次继续等待。
执行器没初始化
怎么触发：一条返回 infra_error，另一条返回 assertion_fail。
怎么判断：两类分别展示，不能标成两条业务断言失败。
结果串批
怎么触发：上报不属于这次运行的用例 ID。
怎么判断：拒绝，原有进度不变。

写下这些测试断言

  • 启动前是 queued；领取后才是 running。
  • 三条计划的明细到齐才 finished。
  • 三种结果各计一次。
  • 冲突回报不能改写原值。

这一课带走：看懂一次运行何时结束后，下一课接入调度：相同触发来了两次，也只做这一批。
