📦 1. Redux Toolkit 状态管理

项目使用 Redux Toolkit (RTK) 作为全局状态管理方案，通过 configureStore 创建 Store，使用 createSlice 模式按业务模块组织 Reducers。

1.1 Store 架构

src/ ├── app/ │ ├── layout.js ← 根布局，包含 Redux Provider │ └── providers.js ← configureStore 创建 Store 实例 │ ├── store/ │ ├── index.js ← 统一导出所有 Reducers │ └── modules/ │ ├── config.js ← 配置状态（模型配置、全局设置） │ ├── user.js ← 用户状态（登录信息、权限） │ ├── moon.js ← Moon 服务状态 │ └── kaptain.js ← Kaptain 项目管理状态

1.2 Store 创建（providers.js）

// src/app/providers.js
'use client';
import { Provider } from 'react-redux';
import { configureStore } from '@reduxjs/toolkit';
import { reducers } from '@/store';

const store = configureStore({
  reducer: reducers,
});

export function Providers({ children }) {
  return <Provider store={store}>{children}</Provider>;
}

1.3 Reducers 统一导出

// src/store/index.js
import configReducer from './modules/config';
import userReducer from './modules/user';
import moonReducer from './modules/moon';
import kaptainReducer from './modules/kaptain';

export const reducers = {
  config: configReducer,
  user: userReducer,
  moon: moonReducer,
  kaptain: kaptainReducer,
};

// 单独导出便于按需使用
export { configReducer, userReducer, moonReducer, kaptainReducer };

1.4 Slice 模式示例

// src/store/modules/user.js
import { createSlice } from '@reduxjs/toolkit';

const userSlice = createSlice({
  name: 'user',
  initialState: {
    userInfo: null,
    isLoggedIn: false,
  },
  reducers: {
    setUserInfo(state, action) {
      state.userInfo = action.payload;
      state.isLoggedIn = true;
    },
    clearUser(state) {
      state.userInfo = null;
      state.isLoggedIn = false;
    },
  },
});

export const { setUserInfo, clearUser } = userSlice.actions;
export default userSlice.reducer;

1.5 在组件中使用

// 页面组件
'use client';
import { useSelector, useDispatch } from 'react-redux';

export default function MyPage() {
  const { userInfo, isLoggedIn } = useSelector(state => state.user);
  const dispatch = useDispatch();

  return (
    <div>
      {isLoggedIn ? `欢迎, ${userInfo.name}` : '请登录'}
    </div>
  );
}
注意：Redux 数据存储在内存中，页面刷新后会丢失。需要持久化的数据应存储在 localStorage 或后端。可以考虑使用 redux-persist 中间件。

🗄️ 2. 会话存储（MongoDB）

Agent 的对话历史通过 ConversationStore 持久化到 MongoDB 的 agent_conversations 集合中。

2.1 ConversationStore 核心 API

// src/lib/agents/conversationStore.js
import { conversationStore } from '@/lib/agents/conversationStore';

// 创建会话
const conv = await conversationStore.createConversation({
  agentId: 'code-assistant-agent',
  userId: 'user-123',
  initialMessage: { role: 'user', content: '你好' },
});

// 获取会话
const existing = await conversationStore.getConversation('conv-xxx');

// 添加消息
await conversationStore.addMessage('conv-xxx', {
  role: 'assistant',
  content: '你好！有什么可以帮你的？',
});

// 批量添加消息
await conversationStore.addMessages('conv-xxx', [userMsg, assistantMsg]);

// 按 Agent 查询
const conversations = await conversationStore.getConversationsByAgent(
  'code-assistant-agent',
  { limit: 20, skip: 0 }
);

// 按用户查询
const userConvs = await conversationStore.getConversationsByUser(
  'user-123',
  { agentId: 'code-assistant-agent', limit: 10 }
);

// 删除会话
await conversationStore.deleteConversation('conv-xxx');

2.2 MongoDB 索引策略

// 应用启动时确保索引存在
await conversationStore.ensureIndexes();
// 创建以下索引：
// - { id: 1 }        — 唯一索引，会话 ID 查询
// - { agentId: 1 }   — 按 Agent 查询
// - { userId: 1 }    — 按用户查询
// - { updatedAt: -1 } — 按更新时间排序

🌊 3. chatStreamHandler 流处理

chatStreamHandler.js 是整个 Agent 对话系统的核心引擎，它同时服务于 /api/agents/[id]/chat（普通对话）和 /api/share/[shareId]/chat（分享对话），实现了 Agent 任务与 HTTP 连接的完全解耦。

3.1 核心架构：后台执行

浏览器请求 ──► chatStreamHandler │ ├──► agent.streamEvents() ← LangGraph 事件流 │ │ │ ▼ │ AsyncQueue 广播（一对多分发） │ │ │ ┌────┴────┐ │ ▼ ▼ │ AI SDK 后台 DB 持久化 │ 流(前端) 管道(MongoDB) │ │ │ │ ▼ ▼ │ 前端展示 增量写入 │ (可断开) (始终运行) │ └──► 返回 Response 浏览器关闭？ ──► AI SDK 流断开，但后台 DB 管道继续运行直到完成

3.2 AsyncQueue — 解耦生产者和消费者

AsyncQueue 是自实现的异步队列，用于将 Agent 事件广播给多个消费者：

class AsyncQueue {
  push(value)   // 生产者推入事件
  end()         // 标记结束
  throw(error)  // 标记错误
  [Symbol.asyncIterator]()  // 支持 for await...of 消费
}

// 广播：一个源 → 多个消费者
function broadcastAsyncIterable(source, count) {
  const queues = Array.from({ length: count }, () => new AsyncQueue());
  // 后台消费源并分发到所有队列
  // 任一消费者断开不影响其他消费者
  return queues;
}
关键设计：当浏览器关闭时，AI SDK 流断开（消费者 1 消失），但后台 DB 持久化管道（消费者 2）不受影响，Agent 任务继续执行并写入数据库。用户重新进入页面后可以看到已完成的结果。

3.3 事件处理

chatStreamHandler 处理以下 LangGraph 事件类型：

事件处理方式
on_chat_model_streamAI 生成的文本流，实时推送到前端
on_tool_start工具开始执行，更新前端进度
on_tool_end工具执行完成，提取输出结果
on_tool_error工具执行失败，记录错误信息
on_chain_start/endAgent 链执行进度

💾 4. 增量持久化

增量持久化是项目的核心特性之一：流式响应实时节流写入 MongoDB，支持断线恢复。

4.1 持久化管道（persistInBackground）

// 后台持久化状态
const state = {
  content: '',           // 累积的 AI 回复文本
  toolCalls: [],         // 工具调用记录 { id, name, input, output, status }
  parts: [],             // 有序的 parts 数组（交错的 text 和 tool）
  todos: [],             // 待办事项
  lastDbUpdate: 0,       // 上次 DB 写入时间戳
  currentTextSegment: '', // 当前文本段落（两个工具调用之间的文本）
};

4.2 节流写入策略

const DB_UPDATE_INTERVAL_MS = 500;  // 500ms 节流间隔

async function flushToDb(force = false) {
  const now = Date.now();
  // 非强制模式下，500ms 内只写一次
  if (!force && now - state.lastDbUpdate < DB_UPDATE_INTERVAL_MS) return;
  state.lastDbUpdate = now;

  await chatHistoryService.updateMessage(sessionId, messageKey, {
    content: state.content,
    toolCalls: state.toolCalls,
    parts: [...state.parts],
    todos: [...state.todos],
    streaming: true,  // 标记为流式进行中
  });
}

4.3 流式结束时的最终写入

async function finalize(isError = false) {
  flushTextSegment();  // 刷出最后的文本段落

  await chatHistoryService.updateMessage(sessionId, messageKey, {
    content: state.content,
    toolCalls: state.toolCalls,
    parts: [...state.parts],
    todos: [...state.todos],
    streaming: false,  // 标记流式完成
  });

  return {
    status: isError ? 'error' : (signal?.aborted ? 'aborted' : 'completed'),
    assistantMessage: { key: messageKey, role: 'assistant', content: state.content, ... },
  };
}

4.4 Parts 交错顺序

持久化的 parts 数组保留了 AI 回复的原始交错顺序：

// 示例：AI 先输出文本，然后调用工具，再输出文本
parts = [
  { type: 'text', text: '让我帮你分析这段代码...' },
  { type: 'tool', toolCallId: 'tc-1', name: 'ask_claudecode', status: 'done', ... },
  { type: 'text', text: '分析结果如下：...' },
  { type: 'tool', toolCallId: 'tc-2', name: 'getMCPTools', status: 'done', ... },
  { type: 'text', text: '以上是完整的分析报告。' },
]
断线恢复：当用户重新进入聊天页面时，系统从 MongoDB 加载消息历史。如果某条消息的 streaming: true，说明任务仍在进行中，前端可以重新订阅进度。

🔗 5. 数据流全景

将 Redux、MongoDB、chatStreamHandler 串联起来，整体数据流如下：

用户输入 │ ▼ 前端 Redux Store (即时 UI 状态) │ ▼ POST /api/agents/[id]/chat │ ▼ chatStreamHandler ├──► Agent 执行 (LangGraph) │ │ │ ├──► MCP 工具调用 │ ├──► ClaudeCode 分析 │ └──► 其他工具 │ ├──► AsyncQueue 广播 │ ├──► AI SDK Stream ──► 前端实时展示 │ └──► persistInBackground ──► MongoDB 增量写入 │ └──► finalize() ──► MongoDB 最终写入 (streaming: false) 用户刷新/重连 │ ▼ MongoDB 加载历史 ──► 前端恢复展示

📝 Quiz — 测测你理解了多少

Q1：Redux Store 在哪里创建？
✅ 正确答案：B
Store 实例在 src/app/providers.js 中通过 configureStore 创建。而 src/store/index.js 只负责导出 Reducers 配置，layout.js 中引入 Providers 包裹应用。
Q2：chatStreamHandler 的 AsyncQueue 设计有什么好处？
✅ 正确答案：B
AsyncQueue 实现了一对多广播：AI SDK 流（前端）和后台 DB 持久化管道各自独立消费事件。浏览器关闭时前端消费者断开，但 DB 管道继续运行，确保 Agent 任务结果不会丢失。
Q3：增量持久化的节流间隔是多少？
✅ 正确答案：B
DB_UPDATE_INTERVAL_MS = 500，即每 500ms 最多写入一次 MongoDB。这个间隔在实时性和性能之间取得了平衡：用户能快速看到进展，同时避免过于频繁的数据库写入。流式结束时会强制执行一次最终写入。
