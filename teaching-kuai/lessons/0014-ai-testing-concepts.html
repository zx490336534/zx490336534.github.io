🧪 AI 测试核心概念

专题 Prompt 管理 · LLM 评估 · 知识库

Kuai 测试平台的核心价值在于 AI 测试能力。本课深入讲解三大核心概念：Prompt 管理（版本化、A/B 测试）、LLM 评估（DeepEval、自动评分）、知识库（RAG、向量检索），帮助你理解平台的 AI 测试方法论。

📝 一、Prompt 管理

Prompt 是 AI 应用的核心资产。Kuai 平台提供了完整的 Prompt 生命周期管理能力。

1.1 Prompt 版本化

每个 Prompt 都有版本历史，支持回滚、对比和审计。

版本化的核心概念
概念说明
Prompt 模板包含变量占位符的文本，如 {{user_input}}
版本号每次修改自动递增，支持语义化版本（v1.0.0）
标签标记版本用途：production、staging、experiment
变更日志每次修改的说明，记录改了什么、为什么改
// kuai-service 中的 Prompt 版本模型
public class PromptVersion {
    private Long id;
    private Long promptId;        // 所属 Prompt
    private Integer version;      // 版本号
    private String content;       // Prompt 内容（支持模板变量）
    private String label;         // 标签：production / staging
    private String changeLog;     // 变更说明
    private Date createTime;
}

// API 示例
GET  /api/prompt/{id}/versions           // 获取所有版本
POST /api/prompt/{id}/versions           // 创建新版本
GET  /api/prompt/{id}/versions/latest    // 获取最新版本

1.2 A/B 测试

通过同时运行多个 Prompt 版本，用数据驱动决策哪个版本效果更好。

A/B 测试流程
  1. 创建实验：选择基准版本（A）和实验版本（B）
  2. 分配流量：如 50/50 或 80/20 的流量分配
  3. 收集数据：记录每个版本的用户满意度、准确率、响应时间
  4. 统计分析：使用统计检验判断差异是否显著
  5. 决策上线：胜出版本标记为 production
// A/B 测试配置
{
  "experimentName": "customer-service-v2-test",
  "promptId": 42,
  "variants": [
    { "version": 3, "label": "control",   "weight": 50 },
    { "version": 4, "label": "treatment", "weight": 50 }
  ],
  "metrics": ["accuracy", "user_satisfaction", "latency"],
  "sampleSize": 1000,
  "status": "running"
}
最佳实践：每次只改一个变量（如系统提示 vs 用户提示前缀），这样才能准确归因。同时测试多个变量会混淆结果。

📊 二、LLM 评估

LLM 的输出是非确定性的，传统测试方法（断言精确匹配）不适用。Kuai 平台采用多层次评估体系。

2.1 评估维度

维度说明评估方法
相关性回答是否切题LLM-as-Judge / 人工评分
准确性事实是否正确与标准答案对比
安全性是否包含有害内容安全检测规则 + LLM 审查
幻觉率是否编造不存在的信息DeepEval FaithfulnessMetric
格式合规输出格式是否符合要求正则 / JSON Schema 校验

2.2 DeepEval 集成

DeepEval 是 Kuai 平台使用的核心 LLM 评估框架，提供开箱即用的评估指标。

# DeepEval 评估示例
from deepeval import evaluate
from deepeval.metrics import (
    FaithfulnessMetric,      # 幻觉检测
    AnswerRelevancyMetric,   # 回答相关性
    ContextualPrecisionMetric,  # 上下文精确度
)
from deepeval.test_case import LLMTestCase

# 定义测试用例
test_case = LLMTestCase(
    input="什么是 RAG？",
    actual_output="RAG 是检索增强生成...",
    retrieval_context=["RAG (Retrieval-Augmented Generation) 是一种..."]
)

# 运行评估
metric = FaithfulnessMetric(threshold=0.7)
evaluate([test_case], [metric])

2.3 自动评分机制

Kuai 平台的自动评分流程
  1. 准备测试集：input + expected_output 对，存储在评估数据集中
  2. 批量运行：将测试集发送给目标 LLM，收集 actual_output
  3. 自动评分：使用 DeepEval 指标自动打分（0-1）
  4. 生成报告：汇总各维度得分，标注异常用例
  5. 回归对比：与历史版本对比，检测质量退化
// kuai-service 评估 API
POST /api/evaluate/run
{
  "promptId": 42,
  "version": 3,
  "model": "gpt-4",
  "datasetId": "customer-faq-v1",
  "metrics": ["faithfulness", "relevancy", "format"]
}

// 返回评估报告
{
  "runId": "eval-20240101-001",
  "scores": {
    "faithfulness": 0.92,
    "relevancy": 0.87,
    "format": 0.95
  },
  "totalCases": 100,
  "passedCases": 88,
  "failedCases": [
    { "caseId": 23, "issue": "hallucination", "score": 0.3 }
  ]
}
注意：LLM-as-Judge 本身也可能出错。建议对评估结果进行人工抽检，尤其是低分用例和边界用例。

📚 三、知识库（RAG）

RAG（Retrieval-Augmented Generation）是让 LLM 基于外部知识回答问题的关键技术。Kuai 平台内置了知识库管理功能。

3.1 RAG 工作原理

┌──────────────┐     ┌──────────────────┐     ┌──────────────┐
│  用户提问     │────▶│  向量检索         │────▶│  Top-K 文档   │
│ "什么是X?"   │     │  (Embedding +    │     │  相关片段     │
│              │     │   相似度搜索)     │     │              │
└──────────────┘     └──────────────────┘     └──────┬───────┘
                                                     │
                                                     ▼
                     ┌──────────────────┐     ┌──────────────┐
                     │  LLM 生成回答     │◀────│  组装 Prompt  │
                     │  (基于检索结果)   │     │  "根据以下    │
                     │                  │     │   内容回答"   │
                     └──────────────────┘     └──────────────┘

3.2 向量检索流程

Step 1：文档入库（Indexing）

将文档切分为 chunks，通过 Embedding 模型转为向量，存入向量数据库。

// 文档处理流程
原始文档 → 分块（Chunk） → Embedding → 向量数据库

// 分块策略
- 按段落分块（推荐，保持语义完整性）
- 每个 chunk 约 500-1000 tokens
- chunk 之间有 10-20% 的重叠，避免信息丢失
Step 2：查询检索（Retrieval）

用户提问时，将问题转为向量，在向量数据库中搜索最相似的 Top-K 个 chunks。

# 检索示例
query_embedding = embed_model.encode("什么是 RAG？")
results = vector_db.search(query_embedding, top_k=5)

# 返回最相关的 5 个文档片段
[
  { "content": "RAG 是检索增强生成...", "score": 0.95 },
  { "content": "RAG 的核心思想是...",   "score": 0.89 },
  ...
]
Step 3：增强生成（Generation）

将检索到的文档片段注入到 Prompt 中，让 LLM 基于这些内容生成回答。

// 组装 RAG Prompt
system: "你是一个知识助手。请根据以下参考内容回答用户问题。
         如果参考内容中没有相关信息，请明确说明。"

context: "
[来源1] RAG 是 Retrieval-Augmented Generation 的缩写...
[来源2] RAG 的核心组件包括：检索器、生成器...
"

user: "什么是 RAG？它的核心组件有哪些？"

3.3 Kuai 平台知识库 API

// 知识库管理 API
POST /api/kb/create              // 创建知识库
POST /api/kb/{id}/documents      // 上传文档
POST /api/kb/{id}/query          // 查询知识库
GET  /api/kb/{id}/documents      // 获取文档列表
DELETE /api/kb/{id}/documents/{docId}  // 删除文档
RAG 调优要点：
  • 分块大小：太小丢失上下文，太大引入噪声
  • Top-K 值：通常 3-10，太多会超出 LLM 上下文窗口
  • Embedding 模型选择：中文场景推荐 text2vec 或 BGE 系列
  • 混合检索：向量检索 + 关键词检索（BM25）结合效果更好
遇到不懂的地方？直接问 Agent。比如：「DeepEval 的 FaithfulnessMetric 是怎么计算的？」或「RAG 的分块策略应该怎么选择？」

📝 Quiz

Q1：Prompt A/B 测试中，为什么每次只建议改一个变量？

  • A. 因为系统限制只能改一个
  • B. 因为同时改多个变量无法准确归因效果差异
  • C. 因为改多个变量会导致 API 报错
  • D. 因为 LLM 只能理解单变量的 Prompt

✅ 答案：B — 控制变量法是实验设计的基本原则，同时改多个变量会导致无法判断是哪个变量引起的效果变化。

Q2：DeepEval 的 FaithfulnessMetric 主要检测什么问题？

  • A. 回答是否流畅
  • B. 回答是否包含幻觉（编造的信息）
  • C. 回答是否安全
  • D. 回答是否快速

✅ 答案：B — FaithfulnessMetric 检测 LLM 输出是否忠于给定的上下文/检索结果，即是否产生了幻觉。

Q3：RAG 系统中，文档分块（Chunking）时为什么要设置重叠（Overlap）？

  • A. 为了增加存储空间利用率
  • B. 为了加快检索速度
  • C. 为了防止分块边界处的信息丢失
  • D. 为了让 Embedding 模型更准确

✅ 答案：C — 分块边界处的关键信息可能被切断，设置 10-20% 的重叠可以确保跨块的语义完整性。
