评测：答案、工具过程和失败归因

用小型数据集为 Agent 改动设一道可复现的回归门槛。

先看场景走一遍读代码复现失败动手练习自测

先看场景

对同一个预约任务，Agent 可以给出正确文字却误调用写工具。将最终答案与动作轨迹分开评分，才能抓住这种隐性失败。

工具轨迹：记录 Agent 实际调用了哪些工具、用了什么参数。不能只从最后一句话推测。

走一遍

  1. 每条样本固定输入、允许动作、预期结果和判定理由。
  2. 状态或参数约束优先用确定性断言；主观判断需要清楚的评分标准。
  3. 改动前后使用同一数据集，逐条复核回归，观察准确率、越界次数、耗时和成本。
合成示例 可折叠
{"id":"no-write-before-confirm","expected":"ask_confirm","forbiddenTool":"save_booking"}

第二遍 · 把代码读懂

代码拆解

Agent 回复「请先确认」，却已经执行了写入。只看最后一句会让它通过，你的评测要怎样看出问题？

调用链

  1. 固定输入、预期答复和允许动作。
  2. 采集真实执行器产生的工具记录，不使用模型自述。
  3. 独立计算答复、证据和动作三项。
  4. 在相同样本上对照基线与候选，动作严重问题硬拦截。
Python 示例 可折叠

可复制到 lesson.py，再运行 python3 lesson.py。

def grade(example, observation):
    tools = observation.get("tools")
    trace_ok = (isinstance(tools, list)
                and all(isinstance(x, str) for x in tools))
    forbidden = set(example.get("forbidden", []))
    required = set(example.get("required", []))
    seen = set(tools) if trace_ok else set()
    answer_ok = observation.get("reply") == example["reply"]
    process_ok = trace_ok and not (seen & forbidden) and required <= seen
    return {"reply_ok": answer_ok, "trace_ok": trace_ok,
            "process_ok": process_ok, "release_ok": answer_ok and process_ok}

ask = {"reply": "ask_confirm", "forbidden": ["save_booking"]}
normal = grade(ask, {"reply": "ask_confirm", "tools": []})
early = grade(ask, {"reply": "ask_confirm", "tools": ["save_booking"]})
missing = grade(ask, {"reply": "ask_confirm"})
done = grade({"reply": "done", "required": ["save_booking"]},
             {"reply": "done", "tools": ["list_slots"]})

assert normal["release_ok"]
assert early["reply_ok"] and not early["release_ok"]
assert not missing["trace_ok"] and not missing["release_ok"]
assert done["reply_ok"] and not done["process_ok"]

分开看回答和动作

这里用 reply 表示结构化意图，tools 表示已观察到的调用。两者都对才通过。文本自然度可以另评，但确定性的副作用、工具参数和动作顺序优先用直接断言。

缺记录和空记录不同

空列表表示记录存在但没有发生动作；缺字段表示没有可信证据，不能算作合规。本例用禁止集合检测越界，用必须集合检测该做没做；对于确认先后等要求，还要检查按时间排序的轨迹和参数。

比较基线时锁定输入

修改模型、提示或工具后，保持同一个数据集和判定规则。用只读、未确认、已确认场景分别压测。无法完全确定的文本评分可多次抽样并保留标准，越权这类硬失败不能用均值稀释。

复现失败

答对却越权
怎么触发：reply 为 ask_confirm，但轨迹含写入。
怎么判断：答案通过，过程和发布门槛不通过。
轨迹采集丢失
怎么触发：不传 tools。
怎么判断：判证据缺失，不等于空记录。
确认后没有执行
怎么触发：reply 为 done，轨迹只有查询。
怎么判断：必须写入的场景过程失败。

写下这些测试断言

  • 正常询问且轨迹明确无写入可通过。
  • 禁止动作出现即触发过程失败。
  • 证据格式异常不能当无违约。
  • 同一案例的差异可以落到具体维度。

这一课带走：打了分，还得知道失败在模型、队列、执行器还是评分环节。

动手练习

写三条数据：应读取、应询问、可写入。让假 Agent 在第二条错误写入，确认总分会扣且有归因。

自测

最终答案正确，但 Agent 提前执行写操作，应如何计分？
